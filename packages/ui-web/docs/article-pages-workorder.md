# 記事系ページ型 作業指示書 — `article-list` / `article-detail`

設計の正本は [composition-redesign.md](./composition-redesign.md) §3-1（2026-08-14 の追記）。
実測の正本は [docs/research/research-news-blog.md](../../../docs/research/research-news-blog.md)（`[NB]`）。
運用は Stage 2〜5 と同じ（縦切りスライス・PR ごとにユーザー承認でマージ・プレビュー目視）。

**Stage 3 の作業指示書（[stage3-workorder.md](./stage3-workorder.md)）は全スライス完了済みのため、
ページ型の追加はこの独立した作業指示書で管理する。**
`case-study-detail`（6つ目のページ型）は Stage 3 完了後に単発スライスで入れたが、
その経緯は `research-case-study-detail.md` §6 に残っている。今後は本書の形式に寄せる。

## 0. スコープ

**対象**: お知らせ / ブログの一覧・記事ページ（`article-list` / `article-detail`）。
`composition-redesign.md` §3-1 のページ型を 6 種 → **8 種**にする。

**対象外**:

| 除外するもの                     | 理由                                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **資料ライブラリ（資料DL一覧）** | **実測0。** `composition-redesign.md` 末尾の未決着 **#10**。第2弾調査で別途扱う                                  |
| **セミナー / イベントの一覧・詳細** | **実測0。** 同 **#11**。日時・申込・開催状態という記事系に無い語彙を持ち、構造が遠いと想定される               |
| ContentHub（LP末尾の回遊セクション） | 別トラックで先行実装中。ただし**カード語彙は本書の `ArticleListItem` に合わせること**（§2 の決定事項）        |
| 記事の CMS 連携・データ取得       | このシステムは表示層のみを配る。データの出どころは利用者側の責務                                                 |

**「セミナーも `article-list` の `kind` に足せば済むのでは」という誘惑に乗らないこと。**
実測が1件も無い。`case-study-detail` が一度「データが無いから作らない」と保留され、
実地調査を経て解除された前例に従う。

## 1. 狙い

LP 末尾のコンテンツ回遊（`[LP]` 9/12）が指す遷移先のうち、
事例記事以外（お知らせ・コラム）を受け取るページ型が存在しない。
ContentHub を実装しても、リンク先が宙に浮く。

事業側の要請はより直接的である。**Polastack のコーポレートサイト立ち上げに
プレスリリース面が必須**であり、これが `news` を先行させる理由になっている（§3）。

実測上の期待値は `case-study-detail` より高い。

- サイト内一貫性 **95.0%**（事例記事 97.6% とほぼ同水準にフォーマット化されている）
- **本数が1桁多い。** SmartHR Mag.・HR大学 の規模を考えると、
  1本ごとにレイアウトを判断させたときの損失が最も大きいコンテンツである

## 2. 決定事項（設計文書・CEOレビューからの確定分）

| 項目                             | 決定                                                                                                                                                |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| ページ型の数                     | **+2**（`article-list` / `article-detail`）。News/ブログで4型に割らない                                                                             |
| News とブログの分け方            | **`kind: 'news' \| 'blog'` の判別ユニオン。** 両方 optional の1型にすると「著者と目次を持つ News」という実測に無い構成が型で許される（実測 0/12）  |
| `tone`                           | 両型とも **`trust`**。**これは実測ではなく判断**（`research-news-blog.md` §6-1）。実装後に見直す余地あり                                          |
| `ArticleSupervisor`（監修者）    | **採用する。** 実測は 1/7 サイト（HR大学）と少数だが、税務・労務・会計の規制領域で有資格者による監修の明示が信頼性の要件になるため、経営判断で入れる |
| 末尾 CTA                         | **必須にしない。** 事例記事は 27/27 だったが記事系は News 7/12・ブログ 11/15。SmartHR ニュースは 0/3                                                |
| 一覧への戻り導線                 | **必須にしない。** News 10/12・ブログ 11/15（事例記事は 27/27 で必須だった）                                                                        |
| カード部品                       | **`ArticleCard` を新設。`CaseCard` は変更しない。** 記事カードは会社名・数値バッジを持たず語彙が違う                                                |
| ContentHub との関係              | **ContentHub のカード語彙を `ArticleListItem` に合わせる**（逆ではない）。`CaseStudyMeta` を一覧と記事で共有したのと同じ効き方を狙う               |
| 読み幅                           | `case-study-detail` の実装値（`max-width: 46.5rem`）を**暫定流用**。ただしブログは §4 のゲートを通すまで確定しない                                  |
| 日付の表示書式                   | **システム側が決める。** 実測が4通りに割れており（`2026.07.07` / `2026-08-14` / `2025/12/19` / `2026年07月14日`）正規化の余地がある。値は ISO で受ける |
| ラベル                           | すべて Props で注入（`ArticleListLabels` / `ArticleDetailLabels`）。関連記事の見出しは**実測で12通りに割れている**。ハードコード禁止               |

## 3. スライスの順序 — **News を先行させる**

| #     | 内容                                                                                                       | 完了条件                                                                                                                             |
| ----- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **1** | **`article-list`**（`ArticleListSection` + `ArticleCard` + フィルタ + ページネーション）。`kind` 両対応  | `defineLandingPage({ pattern: 'article-list' })` が News/ブログ両方で組め、ページ単位ストーリー（日英）と VRT 基準が入っている       |
| **2** | **`article-detail`**（`ArticleBodySection` + `ArticleAuthor` + `ArticleToc` + `ShareButtons`）。`kind` 両対応 | 同上。`kind: 'news'` で著者・目次のフィールドが**型として存在しない**ことがテストで固定されている                                    |

**スライス内でも News を先に通すこと。** `kind: 'blog'` 側（著者・目次・監修者・更新日）は
News が緑になってから足す。理由は事業側の要請（Polastack のプレスリリース面）と、
**ブログ側だけが §4 のゲート待ちである**ため。

News だけなら先行して出せる:

- ブログの読み幅ゲート（§4-1）は **News には掛からない**。News の本文は中央値 約2,200字で、
  事例記事（約3,400字）より短く、`46.5rem` の流用が実測レンジ内に収まる
- 著者・目次・更新日・監修者は `kind: 'news'` に存在しないため、実装しなくても News は完結する

## 4. 実装開始前の必須ゲート

**この2点を通すまで `kind: 'blog'` の実装に着手しないこと。**
News 側（Slice 1・2 の `kind: 'news'` 部分）はゲート対象外で先行できる。

### 4-1. ブログ読み幅の実ブラウザ再計測

`[NB]` は `WebFetch` ベースで **CSS の実値を1つも持っていない**（`composition-redesign.md`
冒頭の出典表記・未決着 #7）。一方でブログ記事の本文は**事例記事の約2倍**（中央値 約7,000字、
最大 18,000字）ある。`case-study-detail` の実装値 `max-width: 46.5rem`（= 744px）を
そのまま流用してよいかは検証されていない。

- 対象: SmartHR Mag. / HR大学 / 現場と人 / お役立ちコラム / Bizpedia の記事（各2〜3本）
- 測るもの: 本文段落の**実効幅**（宣言 `max-width` ではない）・`font-size` ・`line-height`。
  手順は `research-case-study-detail.md` §1-1 に従う
- 判定: 中央値が `46.5rem` から大きく外れる場合、**ブログ本文だけ別の読み幅を持つ**。
  外れない場合は流用を確定し、その旨を本書 §7 に記録する

**「事例記事と同じでいいだろう」で進めないこと。** それは推測であり、
このリポジトリの鉄則（実測なしに構成を推測しない）に反する。

### 4-2. `[NB]` の分母の偏りを埋める

未決着 #8。実ブラウザ計測が可能になるなら、同じ機会に以下を再取得する。

| 対象                     | 前回の失敗理由                                        |
| ------------------------ | ----------------------------------------------------- |
| サイボウズ / kintone     | 日本語ブログを1ページも特定できず（取れたのは英語の技術ブログのみ） |
| Chatwork（kubell）の News | `Socket is closed` で2回とも切断                      |
| Sansan の News 記事      | 一覧が「該当の記事がありません」を返した（JS描画待ちの限界） |

現状 **News 記事12本のうち5本が2社（SmartHR 3・ANDPAD 2）に偏っている。**
埋まれば §2 の決定事項（とくに「末尾 CTA を必須にしない」「著者 0/12」）の
根拠が強くなる。**逆に覆る可能性もあるので、実装を進める前に確認する価値がある。**

## 5. 作る部品

| 部品                 | 内容                                     | スライス | `kind` |
| -------------------- | ---------------------------------------- | -------- | ------ |
| `ArticleListSection` | フィルタ + カードグリッド + ページネーション | 1        | 両方   |
| `ArticleCard`        | サムネ + カテゴリ + タイトル + 日付      | 1        | 両方   |
| `ArticleBodySection` | タイトル + メタ + 著者 + 目次 + 本文の章 | 2        | 両方   |
| `ShareButtons`       | X / Facebook / はてブ / LINE / Pocket    | 2        | 両方   |
| `ArticleAuthor`      | 氏名 + 肩書き + 顔写真 + プロフィール文  | 2        | blog   |
| `ArticleToc`         | 章見出しからの目次（`h2` のみ / `h2+h3`） | 2        | blog   |

既存で足りるもの: `Section` / `Container` / `Text` / `Heading` / `Link(arrow)` /
`CTASection` / `Page` / `SectionHeader(as="h1")`。

**`ArticleBodySection` は分割しないこと。** 実測が「構成は固定」と言っている以上、
細かく分けても組み合わせの自由度は要らない。分けるとかえって順序を間違える余地が生まれる
（`CaseStudyArticleSection` と同じ判断）。

## 6. やらないこと（実測を根拠に）

| 作らないもの                       | 実測                                            |
| ---------------------------------- | ----------------------------------------------- |
| 冒頭の数値タイル / メトリクス行    | **0/54**（事例 0/27 + News 0/12 + ブログ 0/15） |
| News の著者・目次・更新日          | **0/12**（型に含めない。optional にもしない）   |
| 無限スクロール                     | **0/14 ページ**                                 |
| 並べ替え UI                        | 1/14（LayerX のみ）                             |
| 一覧の検索ボックス                 | 2/14                                            |
| 記事内サイドバー（人気記事・フィルタ） | ブログ 3/7・News 0/7。一覧の仕事                |
| 関連記事の複数セクション分割       | 6/15。1セクションで足りる                       |
| 連載 / 4コマ専用のレイアウト       | 1/15                                            |
| 章あたりの写真枚数の制限           | 実測 0〜14枚で章数と相関が無く、決められない    |
| 章ごとの面の交替                   | 記事本文は単一の面（`case-study-detail` と同じ）|

## 7. 併せて必ず行うこと

| 項目                                                       | 理由                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `DEFAULT_TONES` に `article-list` / `article-detail` を追加 | `Record<LandingPagePattern, …>` が型で網羅を保証しているため、書き忘れるとコンパイルが落ちる |
| `LANDING_PAGE_PATTERNS` の網羅テスト更新                   | `src/test/guidelines-sync.test.ts`。規範ファイル（AGENTS.md / GUIDELINES.md）との突き合わせ |
| ページ単位 VRT の基準追加（desktop / mobile）              | `pnpm vrt:update` で撮り、**`git status -- vrt/` で意図したページだけの差分か確認**してからコミット |
| Storybook ストーリーは**日英両方**                         | ラベル（「関連記事」「目次」「一覧に戻る」）は Props で注入し、ハードコードしない        |
| axe-core a11y テスト                                       | とくに目次のアンカーと `ShareButtons` のアクセシブル名                                   |
| changeset（`@siracusahq/gtm-design-system` minor）         | 新規パターンの追加は利用者から見える変更。無いと CI が落ちる                             |
| `pnpm size` の上限確認                                     | 部品が6つ増える。バレル import だけでなく**単体 import の枠**を見ること                  |
| Netlify デプロイプレビューでの目視                         | 新しいページ型のレイアウトを人が一度見る（CLAUDE.md 既定）                               |

**カラー規約の確認**（`packages/ui-web/CLAUDE.md`）: カテゴリのチップ・タグ・
目次のアンカー・シェアボタンはいずれも**明背景に置かれる**。
`text-brand-*` と `bg-brand-500` 以上は使用禁止で、操作用は `primary`（`#008575`）を使うこと。
`src/tokens/tokens.test.ts` が CI で検出して落とす。
