設計の正本は [composition-redesign.md](./composition-redesign.md) §3-1（2026-08-14 の**追記②**）。
実測の正本は [docs/research/research-resources-seminar.md](../../../docs/research/research-resources-seminar.md)（`[RS]`）。
運用は Stage 2〜5 と同じ（縦切りスライス・PR ごとにユーザー承認でマージ・プレビュー目視）。

**記事系ページ（`article-list` / `article-detail`）は

本書はその第2弾にあたり、**Slice 0 で両者の共有語彙を確定させてから**部品実装に入る。

## 0. スコープ

**対象**: 資料ライブラリ一覧とセミナーの一覧・詳細
（`resources-library` / `seminar-list` / `seminar-detail`）。
`composition-redesign.md` §3-1 のページ型を 8 種 → **11 種**にする。

**対象外**:

| 除外するもの                       | 理由                                                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **資料の個票ページ型**             | **新設しない。** 既存 `lead-gen` が実測 10 項目中 9 項目で合致（`[RS]` §3-2）。`LeadGenInput` に `header?` を足す緩和だけ行う |
| セミナーの「満席」状態             | 実測 **0/29 ページ**（未決着 #13）。非破壊で後から足せる                                                                     |
| セミナーの「常設」状態             | 実測 **1/21**（未決着 #14）。`[NB]` が連載 1/15 で専用型を作らなかったのと同じ判断                                           |
| 見逃し配信の集約ページ             | 実測 2/9（HRBrain）。`seminar-detail` でも `seminar-list` でもない中間物（`[RS]` §8-12）                                     |
| フォーム部品そのもの               | `form: React.ReactElement` で外に出す。入力項目は実測できていない（`[RS]` §1-3f）                                            |
| CMS 連携・データ取得               | このシステムは表示層のみを配る                                                                                               |

**「資料の個票も型を作ろう」という誘惑に乗らないこと。**
実測との差分は **`header` を剥がすかどうかの1点だけ**である。
`case-study-detail` が「実測に無いものは作らない」で得た規律を、
ここでは**「実測に有るものも、既存で足りるなら作らない」**に拡張して適用する。

## 1. 狙い

**これは LP の CTA が指す先そのものである。**
`[LP]` の実測で FV の2オファー（§4-3）の「重い方」の実体は資料DLとセミナー申込だった。
記事系（信頼形成）よりコンバージョンへの距離が近く、
**GTM の観点では `article-*` より優先度が高いと判断する余地すらある。**

実測上の裏付け:

- 獲得系は記事系の中核（章 `h2`・公開日・著者・目次・SNS シェア・末尾 CTA）を **0/27** で持たない。
  既存型の拡張では届かないことが確定している
- 逆に**個票は既存 `lead-gen` でほぼ足りる**（10 項目中 9 項目が合致）。
  新設は一覧側に集中させられる

### 3-0. Slice 0: 共有語彙の確定（**CEO からの明示指示**）

**部品を1つも作らないスライス。** 型と判断だけを確定させる。

**理由**: `[RS]` は独立に `ContentTaxonomy` / `ContentImage` / `ContentPagination` を定義したが、
**`[NB]` の `ArticleTaxonomy` / `ArticleImage` / `ArticlePagination` と構造が完全に同じ**である。
さらに ContentHub（LP 末尾の回遊セクション・別トラックで先行実装中）も
独自のカード語彙を持っている。**このまま各スライスで individually 決めると、
同じ概念に4つの型が生まれる。**

**一度だけ、まとめて決める。** 判断は以下の表を埋めることで行う。

| 判断項目                       | 突き合わせる相手                                                                        | 決めること                                                                                       |
| ------------------------------ | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **タクソノミー型**             | `ArticleTaxonomy`（`[NB]`）/ `ContentTaxonomy`（`[RS]`）/ ContentHub のカテゴリ表現       | 1つに統合するか、別に保つか。**構造は同じだが意味する軸が違う**（記事は年別 6/7、獲得系は年別 0/15） |
| **画像型**                     | `CasePhoto` / `ArticleImage`（`[NB]`）/ `ContentImage`（`[RS]`）                          | `alt` 必須の契約は3者共通。**統合の第一候補**                                                     |
| **ページネーション型**         | `ArticlePagination`（`[NB]`）/ `ContentPagination`（`[RS]`）                              | **完全に同一形。統合しない理由が現時点で無い**                                                   |
| **カード4種**                  | `CaseCard` / `ArticleCard`（`[NB]`）/ `ResourceCard` / `SeminarCard`（`[RS]`）           | 4部品に割るか、1つの `ContentCard` に slot を切るか（`[RS]` §8-15）                              |
| **ContentHub のカード語彙**    | `[LP]` の回遊セクション記録（9/12 ページ）+ ContentHub の実装中コード                    | **ContentHub が4系統すべてのカードを1箇所で扱う**以上、ここが統合の可否を決める                  |
| **登壇者型**                   | `CaseSpeakerList`（最大4名）/ `SeminarSpeaker`（`[RS]` 実測最大3名）                     | 共有できるか（未決着 #18）                                                                       |

**進め方**:

1. `[LP]` のコンテンツ回遊セクションの記録（`docs/research/research-lp-anatomy.md`）から、
   **ContentHub のカードが実際に何を表示していたか**を洗い出す
2. ContentHub の実装中コード（別トラック）の現在のカード Props を読む
3. 上表を埋め、**`composition-redesign.md` に「共有語彙の決定」として1節を追加する**
4. その結論に沿って Slice 1〜3 の型名を確定させる

**この順序を守ること。** `article-pages-workorder.md` §2 は
「ContentHub のカード語彙を `ArticleListItem` に合わせる（逆ではない）」と決めているが、
**獲得系のカードは日付を持たない**（実測 0/7）ため、
`ArticleListItem` に寄せると資料カードが破綻する。**この矛盾を Slice 0 で解く。**

**Slice 0 の成果物にコードは含まれない。** ドキュメントの更新と型名の確定だけである。

（実装時に追記する。**この節がこのスライスの経緯の正本**。

### 9-1. ゲート 4-3 — 「Bill One 型」は実在した（2026-08-15）

**結論: フォーム直行型は実在する。`[RS]` の「7/7 が詳細ページ経由・フォーム直行 0/7」は
到達できなかった2社を分母に含めていなかったための結論だった。**

実ブラウザ（Playwright / headless Chromium）で資料一覧のカードのリンク先を全件辿った。

| サイト   | 一覧                                | カードの遷移先                                                        |
| -------- | ----------------------------------- | --------------------------------------------------------------------- |
| Sansan   | `jp.sansan.com/resources/service/`  | **全件が `/form/download_*`**。遷移先は `form` 1個・入力欄 11 のフォームページ |
| Bill One | `bill-one.com/resources/`           | **全件が `/form/download_*`**。同じく `form` 1個・入力欄 13           |

遷移先ページには記事的な本文構造が無く（`h1` は資料名そのもの）、**カードから
1クリックでフォームに着く**。詳細ページを挟まない。

**型への影響**: `ResourceListItem.href` は**「詳細ページ」とも「フォーム」とも決めない**。
単なる遷移先として扱う。実測に両方が存在する以上、どちらかに固定すると片方が組めない。
そのかわり、資料個票（`lead-gen`）を**必ず経由する前提を置かない**。
