# Web/LP デザインシステム 再設計方針

`@polastack/gtm-design-system` を「コンポーネントの詰め合わせ」から
**「AIエージェントが高品質なLPを高速に生成できる装置」** に作り替えるための設計文書。

## なぜやるか

現状のパッケージは、業務システムUI（`@polastack/design-system`）のスタックを
ほぼそのまま複製している。目的が違うのに構造が同じであることが、
以下の3つの問題を同時に生んでいる。

### 問題1: 配布物が完成品になっていない

Tailwind CSS v4 は**利用者のソースを走査**してCSSを生成する。`node_modules` は既定で
走査対象外であり、配布CSSにも README にも `@source` の記述がない。

最小の消費側アプリで実測した結果:

| 消費側の設定                                            | 出力CSS | 生成ユーティリティ |
| ------------------------------------------------------- | ------- | ------------------ |
| `@import '@polastack/gtm-design-system/theme.css'` のみ | 9.15 kB | **0件**            |
| 上記 + `@source '.../dist'`                             | 67.8 kB | 全件               |

つまり**公開中の 0.2.0 は、素直に導入すると無スタイルでレンダリングされる。**

同じ構造の問題がフォントにもある。`--font-sans: 'Inter', 'Noto Sans JP'` は宣言
されているが、実際に読み込んでいるのは `.storybook/preview-head.html` だけで、
これは配布物に含まれない。

どちらも **Storybook では完璧に見え、CI（Build / Typecheck / Test / Size）でも
検出されない。** `pnpm size` は JS しか測っていない。

### 問題2: APIが統一感を生まず、ばらつきを生んでいる

18セクションすべてが `background`（4通り）と `spacing`（5通り）を独立に受け取る。
10セクションのLPを組むと、背景と余白の組み合わせだけで **20^10 ≈ 10兆通り**。
このうち成立するのは十数通りしかない。

AIエージェントは props を見つければ使い、しかもLPごとに違う選び方をする。
**セクションが自分の見た目を決める権限を持っていること**が、統一感が出ない原因。

さらに、使われていない選択肢が大量に残っている（ストーリー内の使用回数）:

| prop             | 選択肢数           | 使用回数                      |
| ---------------- | ------------------ | ----------------------------- |
| `eyebrowStyle`   | 6（×15セクション） | **0**                         |
| `cardStyle`      | 2                  | **0**                         |
| `backgroundMesh` | bool               | **0**                         |
| `animated`       | bool               | **0**                         |
| `scrolling`      | bool               | **0**                         |
| `logoStrip`      | node               | **0**                         |
| `titleGradient`  | string             | **0**（かつ実装が破綻。後述） |

### 問題3: 意匠が業務システム由来のまま

- `radii` は共通トークンで最大 1.5rem。実使用は `rounded-full` 15回 / `rounded-2xl` 9回と
  **スケールの上端に張り付いている**
- `shadows` はUI操作用の小さい影のみ。LPの「浮いたカード」に使える語彙がない
- `duration` は最大500ms、`easing` は Material 由来のみ。結果 `AnimateOnScroll` が
  `duration = 600` / `ease-out` を**ハードコードしてトークンを迂回している**
- `tracking-[-0.04em]` / line-height 1.11 は欧文ディスプレイ前提。和文では詰まりすぎる

## 方針

6つの層に分けて対応する。層0は他と独立に着手でき、層1〜3は依存関係がある。

| 層  | 内容                                               | 効く問題    |
| --- | -------------------------------------------------- | ----------- |
| 層0 | 意匠の決定（radii / shadow / motion / 和文タイポ） | 問題3       |
| 層1 | セクションから「見た目を決める権限」を剥がす       | 問題2       |
| 層2 | リズム（背景・余白・CTA）をページが自動で与える    | 問題2       |
| 層3 | 「ページ」を配布単位にする                         | 問題2・速度 |
| 層4 | 配布形態を CSS Modules に変え、完成CSSを配る       | 問題1       |
| 層5 | ページ単位のビジュアルリグレッションと dev 警告    | 全部        |

層4（案C）は層1〜3を**「守られるルール」にするための土台**である。
Tailwind クラスを配布したままだと、`className="bg-neutral-900 py-40"` で
すべての規約が迂回でき、しかもそれは静かに起きる。

---

## 層0: 意匠の決定

トークンの共通化の境界線を引き直す。現在 `@polastack/tokens` にあるもののうち、
**ブランドとして本当に共通なのは色相とフォントファミリだけ**。

```
tokens（共通のまま）     color scale / fontFamily / fontWeight / spacing 4pxグリッド
ui-app 固有             radii(小) / shadow(UI) / motion(100–300ms)
ui-web 固有（新設）      radii(大・pill寄り) / shadow(soft-large) / motion(400–900ms)
                        和文向け tracking・line-height スケール
```

`radii` / `shadows` / `duration` / `easing` は「そのデザインシステムの性格」そのもので、
業務UIとLPで違って当然。共通トークンから各パッケージへ降ろす。

**注意**: 二重管理の検出（`tokens.test.ts`）は無効化しない。正本の置き場所が
変わるだけで、CSS変数との突き合わせは維持する。層4でトークンを codegen 化すれば、
このテストが守っている事故そのものが構造的に消える。

## 層1: props の棚卸し

### A. 全セクション共通で削除する

| prop           | 選択肢 | 使用回数 | 判断                             |
| -------------- | ------ | -------- | -------------------------------- |
| `background`   | 4      | 35       | **削除** — ページが決める（層2） |
| `spacing`      | 5      | 7        | **削除** — ページが決める（層2） |
| `eyebrowStyle` | 6      | 0        | **削除** — トーンが決める（層2） |

`background` が35回使われているのは「必要だから」ではなく、
**セクションが決めるべきでないことを毎回決めさせられている**証拠。

`eyebrowStyle` の削除に伴い、`Text` の `size` にある overline 系7バリアント
（`overline` / `overline-pill` / `overline-border` / `overline-text` / `overline-dot` /
`overline-gradient` / `overline-icon-pill`）も整理し、独立した `Eyebrow`
コンポーネントに切り出してトーン連動にする。

### B. 個別に削除する

| コンポーネント                                            | prop                       | 理由                                                                                                              |
| --------------------------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `HeroSection`                                             | `titleGradient`            | 未使用。かつ**実装が破綻している**（`title` を素で1回、`GradientText` でもう1回、`<br/>` を挟んで二重に描画する） |
| `HeroSection`                                             | `backgroundPattern`（5）   | トーンが決める                                                                                                    |
| `HeroSection`                                             | `layout`（3）              | `image` の有無 + `imagePlacement: 'side' \| 'below'` に統合                                                       |
| `CTASection`                                              | `backgroundMesh`           | トーンが決める                                                                                                    |
| `CTASection`                                              | `logoStrip`                | 未使用。`LogoCloud` と役割が重複                                                                                  |
| `FeatureGrid`                                             | `cardStyle`                | 未使用。見た目のみの差                                                                                            |
| `CodeBlock`                                               | `alignment`                | 見た目のみの差                                                                                                    |
| `CodeBlock`                                               | `layout`                   | `description` の有無から導出できる                                                                                |
| `StatsSection`                                            | `animated`                 | 常時ON + `prefers-reduced-motion` を尊重                                                                          |
| `LogoCloud`                                               | `scrolling`                | ロゴ件数から導出（8件以上でスクロール）                                                                           |
| `FeatureGrid` / `CaseStudySection` / `TestimonialSection` | `columns`                  | 件数から導出                                                                                                      |
| `BentoGrid`                                               | `BentoItem.variant`（3択） | アイテム単位の見た目指定。AIが1件ずつ指定するとまだら模様になる。**位置で自動決定する**（1件目のみ強調）          |
| `HeroSection` / `CTASection` / `PricingCard`              | `actions[].variant`        | 1つ目を primary、以降を secondary に自動割当                                                                      |

`columns` の自動導出ルール:

| 件数 | 列数     |
| ---- | -------- |
| 2    | 2        |
| 3    | 3        |
| 4    | 2（2×2） |
| 5–6  | 3        |
| 7+   | 3        |

これにより「4件の機能を4列に潰して1件あたりが細くなる」事故が構造的に消える。

### C. 残すもの

`eyebrow` / `title` / `subtitle` / 各セクションのデータ配列（`features` / `plans` /
`testimonials` など）/ `CodeBlock` の `language`・`filename`・`showLineNumbers`・
`highlightLines` / `CTASection` の `note`・`socialProof` / `HeroSection` の
`badge`・`actions`・`image`。

判断基準は **「意味が違うか、見た目が違うだけか」**。後者は消す。

### 削減の効果

10セクションのLPで表現しうる見た目の組み合わせ:

```
現状:  20^10 ≈ 10兆通り（うち成立するのは十数通り）
再設計後: トーン3通り × コンテンツ
```

## 層2: リズムをページが与える

背景と余白はセクション単体では決められない。**前後関係で決まる**。
ページコンテナがルールで割り当てる。

### 背景

- ヒーローと最終CTAのみ強調面
- 本文セクションは default ↔ muted を交互に
- 暗い面の連続を禁止（3連続で dev 警告）
- 「強調面」の実体はトーンによって変わる

### 余白

- 単一のリズムスケールを使う
- 関連するセクション間は詰め、話題が変わるところで開く（章立て）

### CTA

- 1ビューポート内のプライマリCTAは1つまで
- ページ全体でプライマリCTAはヒーローと最終CTAの2箇所まで
- それを超えたものはコンテナが自動でセカンダリに降格

### トーン

変化は「自由度」ではなく「名前付きの選択肢」として渡す。締めすぎると全ページが
同じ顔になり、マーケティングとしては失敗するため。

| トーン     | 用途                                     | 性格                                                          |
| ---------- | ---------------------------------------- | ------------------------------------------------------------- |
| `trust`    | コーポレートサイト、エンタープライズ向け | 明るい、余白広め、装飾最小、`primary` のみ                    |
| `product`  | サービスサイト                           | 明るい + アクセント、スクリーンショット主役、技術的           |
| `campaign` | 獲得LP、広告着地                         | コントラスト強め、ヒーロー濃色、CTA強調、`brand` の装飾を許可 |

`MarketingButton` の `gradient` バリアントは `campaign` トーンでのみ有効とする。

## 層3: ページを配布単位にする

AIの品質事故はコンポーネント単体ではなく**構成**で起きる。
セクションの順序、CTAの数、証拠の出し方。ならば構成そのものを配る。

用途が2つあるので、APIも2つ用意する。

### (a) LP量産 — データ駆動

```tsx
<LandingPage {...defineLandingPage({
  pattern: 'lead-gen',        // 型を選ぶ = セクション順序が確定する
  hero:    { title, subtitle, cta },
  proof:   { logos },
  features:[...],
  cases:   [...],
  closing: { form },
})} />
```

AIの仕事が「デザインする」から**「フォームを埋める」**に変わる。構成の判断が
発生しないので速く、間違えようがない。必須項目の欠落は**型エラーで落ちる**。

用意するパターン: `lead-gen`（資料DL）/ `product`（製品LP）/ `case-study` /
`corporate-top`。

### (b) コーポレート・サービスサイト — コンポジション

1ページずつ違うので、セクションを自由に並べられる形を残す。
層1・層2が効いているため、並べ方だけ自由でリズムは自動。

```tsx
<Page tone="trust">
  <Hero ... />
  <ModuleOverview ... />
  <SecurityBadges ... />
</Page>
```

Astro でコーポレートサイトとサービスサイトを作り、LPを量産するという計画に
この2本立てが対応する。

## 層4: CSS Modules への移行

### なぜ Tailwind の配布をやめるか

利用者は Astro を前提としており、Tailwind を持っているとは限らない。
また Tailwind クラスを配布したままだと以下が起きる。

- **`@theme` 変数がグローバルを汚す**。`--color-primary-*`・`--font-sans`・`--radius-*`
  を宣言するため、利用者が自分の Tailwind テーマを持っていると読み込み順で
  一方が勝つ。preflight は利用者のページ全体をリセットする
- **`className` が静かに効かない**。AIは高確率で `<HeroSection className="mt-24">` と
  書く。利用者に Tailwind がなければ何も起きず、あってバージョンが違えば微妙にずれる。
  どちらもエラーにならず Storybook でも再現しない
- prefix による名前空間分離は**設定1行では済まない**。`prefix(ps)` を付けると
  利用者が書くクラス名が `ps:flex` になるため、全コンポーネントのクラス文字列を
  書き換える必要がある（実測: prefix 適用時の生成ユーティリティは0件）

### なぜ vanilla-extract ではなく CSS Modules か

どちらを選んでも**利用者には見えない**（コンパイル済みCSSを配るため）。
したがってこれは純粋に自社内の実装体験の選択であり、以下2点で CSS Modules を採る。

1. **AIの実装精度**。35コンポーネントを書き、その後も保守するのは主にAI。
   素のCSSでの精度は明確に高い。vanilla-extract は `.css.ts` がビルド時実行である
   ことを理解できず、runtime値を参照して壊す失敗を繰り返す
2. **既存のビルド構成を壊さない**。esbuild 0.25 は CSS Modules をネイティブに処理する
   ことを検証済み。tsup 設定を変更せずに動き、コンポーネント単位エントリのおかげで
   **CSSも自動的にコンポーネント単位で分割される**

移行方向の非対称性も理由になる。CSS Modules → vanilla-extract は容易
（トークンはCSS変数として存在し、cva → recipe は構造が同じ）だが、逆は型情報を捨てる作業。

### 必須の3点セット

CSS Modules は既定では「静かに壊れる」。CSSの `.gradient` をリネームすると
`s.gradient` が `undefined` になり `class="base undefined"` が出力される。
以下を必ず併せて導入する。

1. **トークン → CSS変数の生成**。`@polastack/tokens` から `theme.css` を codegen し、
   値の二重管理を構造的に消す
2. **`*.module.css.d.ts` の生成**。typecheck に含め、クラス名のリネーム・typo を
   型エラーにする。**これを省略するなら CSS Modules は vanilla-extract より劣る**
3. **stylelint で `var()` を既知トークンに制限**。存在しない変数参照を落とす

### 配布物

- コンパイル済みCSS（Tailwind は不要）
- Web フォントを `@font-face` として同梱（現在の未配信問題を同時に解決）
- `pnpm size` に**CSSサイズの枠を追加**する。現状JSしか測っておらず、
  CSSが肥大しても誰も気づかない

## 層5: うるさく壊す

### ページ単位のビジュアルリグレッション

Playwright のスクリーンショット比較をCIで回す（Chromatic は有料のため自前で十分）。
**検証単位はコンポーネントではなくページ。** 統一感はページを並べて初めて判定でき、
コンポーネント単位の Storybook では見えない。

### 日本語の最悪ケースを固定する

実務上いちばん効く。AIが書く日本語コピーは長さが暴れるため、見出しが3行に
折り返してヒーローが崩れる、カードの高さが揃わない、といった事故が最も多い。

「異常に長い和文」「異常に短い和文」「英語」の3パターンをページ単位のストーリーとして
持ち、VRTで固定する。

### dev ビルドでの警告

- `h1` が2つ以上ある
- 1ビューポート内にプライマリCTAが2つ以上
- `LogoCloud` のロゴが6社未満（少ないと逆効果）
- 暗いセクションが3連続

### 消費側からの結合テスト

最小の Astro アプリをCIでビルドし、生成物に期待するCSSが載っているかを検証する。
Storybook では絶対に見えない配布の事故を止める唯一の手段。

## 層6: AI向け規範ファイルの同梱

配布物（`files`）に機械可読のルールファイルを含める。CLAUDE.md はこのリポジトリの
中でしか効かず、`@polastack/gtm-design-system` を入れた先のAIエージェントには届かない。

層1〜3が完了していれば、書くことは劇的に減る。

```
使えるトーンは3つ。ページの型は4つ。あとは埋めるだけ。
import '@polastack/gtm-design-system/styles.css' を1行書く。
```

**APIで表現できるルールを文章で書くのは負け筋。** 現状のまま規範ファイルを書くと、
10兆通りの組み合わせのうち何が正しいかを文章で説明する羽目になり、守られない。

## 実施順序

1. 暫定対応 — 公開中 0.2.0 の `@source` 問題を README に明記
2. 層0 — 意匠の決定（層4と独立に着手可能）
3. 層1・層2 — props の削除とリズム規則の実装
4. 層4 — CSS Modules 移行 + 3点セット
5. 層3 — ページAPI（データ駆動 + コンポジション）
6. 層5 — VRT / dev警告 / 和文最悪ケース / 消費側結合テスト
7. 層6 — AI向け規範ファイルの同梱
