# Web/LP デザインシステム 再設計方針

`@siracusahq/gtm-design-system` を「コンポーネントの詰め合わせ」から
**「AIエージェントが高品質なLPを高速に生成できる装置」** に作り替えるための設計文書。

## 実測の出典表記

本文中の数値には出典を短く添える。いずれも 2026-08-02 の一次調査。

| 記号   | 調査                         | 内容                                                                          |
| ------ | ---------------------------- | ----------------------------------------------------------------------------- |
| `[LP]` | LP アナトミー調査            | 国内BtoB 19ページのセクション順・CTA・ロゴ・数値訴求・フォーム・追従CTAの実測 |
| `[MB]` | マルチブランド調査           | 国内コンパウンド6社のCSS実測 + L\*C\*h 計算                                   |
| `[VL]` | ビジュアル言語・和文組版調査 | 8社の生CSS実測 + KV画像の目視確認 + デジタル庁DADS                            |
| `[NB]` | News / ブログ調査             | 国内BtoB 9社の一覧16ページ + 記事27本の構成実測（2026-08-14）                 |

**`[NB]` だけ手法が違う。CSS実値（余白・フォントサイズ・読み幅・色）を含まない。**
環境の制約により実ブラウザ計測ができず、`WebFetch` による構造の読み取りで代替したため、
主張できるのは構成・情報設計だけである。書式が要る箇所は `case-study-detail` の実装値を流用すること。

出典のない数値は本リポジトリ内の実測(ストーリー内の prop 使用回数、消費側の再現環境など)。
調査記録の全文はリポジトリの `docs/research/` に収録している。

## なぜやるか

現状のパッケージは、業務システムUI（`@siracusahq/design-system`）のスタックを
ほぼそのまま複製している。目的が違うのに構造が同じであることが、
以下の問題を同時に生んでいる。

### 問題1: 配布物が完成品になっていない

Tailwind CSS v4 は**利用者のソースを走査**してCSSを生成する。`node_modules` は既定で
走査対象外であり、配布CSSにも README にも `@source` の記述がない。

最小の消費側アプリで実測した結果:

| 消費側の設定                                            | 出力CSS | 生成ユーティリティ |
| ------------------------------------------------------- | ------- | ------------------ |
| `@import '@polastack/gtm-design-system/theme.css'` のみ | 9.15 kB | **0件**            |
| 上記 + `@source '.../dist'`                             | 67.8 kB | 全件               |

つまり**当時公開されていた 0.2.0（旧 `@polastack` スコープ）は、素直に導入すると無スタイルでレンダリングされる状態だった**
（README への手順明記は Phase 10 で対応済み。恒久対応が Stage 2 の CSS Modules 化）。

同じ構造の問題がフォントにもある。`--font-sans: 'Inter', 'Noto Sans JP'` は宣言
されているが、実際に読み込んでいるのは `.storybook/preview-head.html` だけで、
これは配布物に含まれない。

どちらも **Storybook では完璧に見え、CI（Build / Typecheck / Test / Size）でも
検出されない。** `pnpm size` は JS しか測っていない。

### 問題2: APIが統一感を生まず、ばらつきを生んでいる

18セクションすべてが `background`（4通り）と `spacing`（5通り）を独立に受け取る。
10セクションのLPを組むと、背景と余白の組み合わせだけで **20^10 ≈ 10兆通り**。
このうち成立するのは十数通りしかない。

AIエージェントは props を見つければ使い、しかもLPごとに違う選び方をする。
**セクションが自分の見た目を決める権限を持っていること**が、統一感が出ない原因。

さらに、使われていない選択肢が大量に残っている（ストーリー内の使用回数）:

| prop             | 選択肢数           | 使用回数                      |
| ---------------- | ------------------ | ----------------------------- |
| `eyebrowStyle`   | 6（×15セクション） | **0**                         |
| `cardStyle`      | 2                  | **0**                         |
| `backgroundMesh` | bool               | **0**                         |
| `animated`       | bool               | **0**                         |
| `scrolling`      | bool               | **0**                         |
| `logoStrip`      | node               | **0**                         |
| `titleGradient`  | string             | **0**（かつ実装が破綻。後述） |

### 問題3: 意匠が業務システム由来のまま

- `radii` は共通トークンで最大 1.5rem。実使用は `rounded-full` 15回 / `rounded-2xl` 9回と
  **スケールの上端に張り付いている**
- `shadows` はUI操作用の小さい影のみ。LPの「浮いたカード」に使える語彙がない
- `duration` は最大500ms、`easing` は Material 由来のみ。結果 `AnimateOnScroll` が
  `duration = 600` / `ease-out` を**ハードコードしてトークンを迂回している**
- `tracking-[-0.04em]` / line-height 1.11 は欧文ディスプレイ前提。
  **和文で負の字送りを使っている国内BtoB企業は8社中0社**（`[VL]`）。詰めは `letter-spacing`
  ではなく `palt` で行うのが共通の作法であり、現行実装はこの作法に反している

### 問題4: ブランドが3つに増えるのに、色が1系統しかない

このシステムは今後、**コーポレート / Polastack / ピアデスクシリーズ**の3ブランドを支える。
ピアデスクシリーズは配下に複数製品が将来増える。

現状のトークンは単一ブランド前提で、`primary` と `brand` の2色が hex 直値で固定されている。
ブランドを増やすたびにトークンを増やす作りでは、**バクラクが実際に踏んだ破れ方**
（プロダクト別CSSでの生hex直書き、他プロダクトのランプを参照したコピペ残り、
primary のランプ位置が `-60` と `-70` で混在）を確実に再現する（`[MB]`）。

### 問題5: ビジュアル資産の語彙がゼロ

18セクションのうち画像を扱う口は `HeroSection.image` と `FeatureShowcase.image` の
2つだけで、いずれも `React.ReactNode` の素通し。実装コードに `<img>` は0件、
`aspect-*` も0件。**画像の縦横比・枠・影・傾き・プレースホルダについて、
このシステムは何のルールも持っていない。**

一方、調査した8社のヒーローは**全社が何らかの主役ビジュアルを持ち、
その処理手法（枠の有無・正対か傾きか・読ませるか沈めるか）がブランドの識別子になっている**（`[VL]`）。
ここが空白のままでは、AIが生成したLPは「文字だけのページ」か
「毎回違う扱いの画像が並ぶページ」のどちらかにしかならない。

## 方針 — 6つの Stage

| Stage | 内容                                                                  | 効く問題     |
| ----- | --------------------------------------------------------------------- | ------------ |
| 1     | テーマ契約とトークン（マルチブランド / 和文タイポ / 意匠）            | 問題3・問題4 |
| 2     | 全コンポーネント1周（ビジュアル資産 + props削除 + CSS Modules）       | 問題1・2・5  |
| 3     | ページ層（`<Page brand tone>` / `defineLandingPage()` / ページ型5種） | 問題2・速度  |
| 4     | リード獲得（計測 / 追従CTA / 2オファー / フォーム摩擦）               | 事業成果     |
| 5     | 守り（ページ単位VRT / 和文最悪ケース / dev警告 / 結合テスト）         | 全部         |
| 6     | AI向け規範ファイルの同梱                                              | 速度・再現性 |

Stage 2 で CSS Modules へ移行する（後述の案C）ことが、Stage 1・3 を
**「守られるルール」にするための土台**である。
Tailwind クラスを配布したままだと、`className="bg-neutral-900 py-40"` で
すべての規約が迂回でき、しかもそれは静かに起きる。

Stage 2 を「props削除」「CSS Modules 移行」「ビジュアル資産」の3周に分けない理由は、
**同じファイルを3回書き換えることになるから**。1コンポーネントにつき1回だけ触る。

## Stage 1: テーマ契約とトークン

### 1-1. マルチブランド体系

支える単位は3階層。

| 階層               | 単位                                         | 買い手                       | アクセント色相                     |
| ------------------ | -------------------------------------------- | ---------------------------- | ---------------------------------- |
| コーポレート       | 運営会社（Siracusa）のコーポレートサイト     | 投資家・採用候補・パートナー | **ティール（`#008575` アンカー）** |
| プロダクトブランド | Polastack（Enterprise Agent Stack）          | **技術者**                   | **未定**                           |
| シリーズブランド   | ピアデスクシリーズ（配下に製品が将来増える） | **非技術者**                 | **未定**                           |

ピアデスクの英字表記は **`peerdesk`** で確定（2026-08-03 ブランド側決定）。
npm スコープは `@polastack/*` から **`@siracusahq/*`** へ変更することが同日決定した（npm 上で `siracusa` スコープは取得不可だったため `siracusahq` を確保）
（別PRで実施。移行手順は [theme-contract-spec.md](../../../docs/theme-contract-spec.md) §10 と併せて計画する）。

**採る構造: バクラクの3層テーマ契約**（`[MB]`。国内で唯一、この設計思想を実装している実例）。

```
層1 骨格トークン    ニュートラル / タイポ / 余白リズム / 形状 / モーション
                    → 全ブランド共通。ブランドによって変わらない
層2 ブランドランプ  ブランドごとの色相を、全ブランドで同一の刻みを持つ段階スケールに展開
                    → 段の数と刻みは共通。色相だけが違う
層3 抽象スロット    --color-brand-surface / --color-brand-ink / --color-cta-bg …
                    → 「いま表示しているブランド」を指す役割名。コンポーネントはこれしか参照しない
```

切替は **`data-brand` 属性**で行う。`<Page brand="peerdesk">` が `data-brand="peerdesk"` を出し、
CSSがスロットの向き先を差し替える。バクラクはプロダクトLPごとに 800バイト程度のCSS 1枚を
追加読み込みする方式だったが、こちらは配布物が1枚のCSSなので属性セレクタで足りる。

**シリーズ既定 + 製品上書き**を許す。ピアデスクシリーズの既定ランプをシリーズが持ち、
配下の個別製品が必要なときだけ自分のランプへスロットを向け替える。
バクラクが `base.css` の既定をシリーズ色（bakuraku）に向けていたのと同じ形（`[MB]`）。

**契約の詳細仕様は別文書 [theme-contract-spec.md](../../../docs/theme-contract-spec.md) に委譲する。**
スロット名の一覧、ランプの段数と刻み、`data-brand` の適用範囲、
ダークモードとの掛け合わせ、codegen の入出力形式はそちらで確定させる。
本文書では「3層である」「切替は `data-brand`」「シリーズ既定+製品上書き」の3点のみを決める。

#### 注意: 色相を振ることは主流ではない

`[MB]` の実測では、**6社中4社（freee / マネーフォワード / SmartHR / Sansanの一部）は
プロダクト間でアクセントを変えていない。** 色相を振っているのはバクラクとラクスの2社だけで、
**どちらも10製品以上を1シリーズに束ねているケース**である。

したがって「3ブランドだから色相を3つ」という導出は他社実態からは出てこない。
それでも契約を先に作るのは、**ピアデスクシリーズの配下に製品が増えることが確定しているから**であり、
契約が無い状態で製品が増えると生hex直書きが始まるから。
**契約は作るが、色相を実際に何本振るかはブランド判断であって、この文書では決めない。**

#### 破れ方への備え

バクラクは契約を持っていてもなお破れている（`[MB]`）。

| 破れ方                                 | 実例                                                                               | 対策                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------- |
| トークンを経由せず生hex直書き          | `clm.css` が `#A35EA1` 等を直書き                                                  | stylelint で hex リテラルを禁止（Stage 2）               |
| 他ブランドのランプを参照するコピペ残り | `attendance.css` / `ar-management.css` に `--color-product-10: var(--docissue-10)` | ランプ名とブランド名の一致をテストで検証                 |
| ランプ位置の混在                       | primary が `-60` と `-70` に分裂し L\* が 38.5〜57.0 にばらける                    | 「操作色はランプの固定段から採る」をテストで縛る（次項） |

### 1-2. 操作色と装飾色 — 同一ランプの2つの段

現行の `primary`（操作用）/ `brand`（装飾用）の2階層は、**ブランドを増やしても成立するように
「別々の色」ではなく「同一ランプの2つの段」として一般化する。**

| 役割                                | ランプの段               | 保証                         | 禁止                                       |
| ----------------------------------- | ------------------------ | ---------------------------- | ------------------------------------------ |
| **操作色** `--color-brand-action-*` | OKLCH **L ≈ 0.553** の段 | 白文字 4.5:1 以上（WCAG AA） | —                                          |
| **装飾色** `--color-brand-decor-*`  | OKLCH **L ≈ 0.73** の段  | —                            | **明背景のテキスト・ボタン背景に使用禁止** |

現行の値はすでにこの構造になっている（計算値）:

| 現行トークン  | hex       | OKLCH L    | 白背景コントラスト |
| ------------- | --------- | ---------- | ------------------ |
| `primary-500` | `#008575` | **0.5527** | 4.55:1             |
| `brand-500`   | `#13c3a0` | **0.7299** | 2.25:1             |

つまり**新しい制約を導入するのではなく、いま現行値が満たしている L の関係に名前を付けて他ブランドへ展開する。**

ただし厳密には、現行2色は同一色相ではない（`primary` H≈180.4 / `brand` H≈173.4 と **7°ずれている**。
ルート CLAUDE.md の「両方 H≈173」は不正確）。契約の不変量は**各段の L / C** であって
「ランプ内の色相が単一であること」ではない。単一色相から生成するのは新ブランド用の既定パスであり、
**コーポレート（ティール）は現行 hex を一切変更せず explicit 登録とする。**

段を揃えるだけでは不十分である点も明記する。
バクラクは `-60` を採る7プロダクトの L\* を 49.5〜57.0（幅7.5）に収めることに成功しているが、
**その7色の白背景コントラストは 3.50:1〜4.57:1 で、4色が WCAG AA 未満**（`[MB]`）。
**ランプ段の統一と AA 適合は別の話**であり、操作段は色相ごとに実測してAAを確認する。
`packages/tokens/src/tokens.test.ts` がすでにコントラスト比を実計算しているので、
新ブランドのランプを足すときは同時に期待値を追加する。

### 1-3. 第3の役割 — CTA専用アクセント（オプション）

`--color-cta-bg` / `--color-cta-ink` を**オプションのスロット**として用意する。
未指定なら操作色にフォールバックする。

根拠はカミナシの実測（`[LP]`）。ブランドの主色は `#0360e5`（青）だが、
固定ヘッダー内のプライマリCTAの塗りは **`#ffdb22`（黄）でブランド色と別**。
freee の下部固定バー部品も `#2864f0` とブランド色を使っており、社によって判断が分かれる。

**「CTAはブランド色である」を構造に焼き込まない。**
振り分けの判断はブランド側に残し、システムはスロットだけ持つ。

### 1-4. 色のガバナンス

**デザインシステムが持つのは、ルール・生成器・検証・レジストリの4つだけ。**
**色相の値そのものはブランドの判断であり、この文書でも `packages/tokens` でも先に決めない。**

| DSが持つもの | 内容                                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------- |
| ルール       | ランプの段数と刻み。操作段 L≈0.553 / 装飾段 L≈0.73。ニュートラルは共通で固定                                      |
| 生成器       | 色相を1つ与えるとランプ全段を生成する関数（OKLCH の L と C を固定して H だけ回す）                                |
| 検証         | 操作段の白文字コントラスト、装飾段の誤用、ランプ位置の統一、hexリテラルの混入                                     |
| レジストリ   | ブランド名 → 色相 の対応表を1箇所に持つ。ラクスがコーポレートCSS1枚に10製品色を登録していたのと同じ発想（`[MB]`） |

ニュートラルを共通で固定することは実態に裏付けがある。
**色を振っている2社（ラクス10製品色 / バクラク13プロダクト色）は、どちらもニュートラルを
全サイトで完全共有している**（`[MB]`）。「アクセントを振るなら、ニュートラルは絶対に固定する」。

### 1-5. 和文タイポグラフィ

`[VL]` の8社実測とデジタル庁DADSから、**候補レンジではなく確定値**として置く。

| 項目                | 確定値                                   | 根拠                                                                                                                                  |
| ------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 見出しの行間        | **1.3〜1.4**                             | 値が取れた6社すべてが主要見出しでこの帯。デジタル庁 Display の 140% とも一致（`[VL]`）                                                |
| 本文の行間          | **1.6〜1.75**                            | デジタル庁「一般的な本文」160%〜「心理的負荷の軽減」175% と実サイト中央値が重なる帯。LayerX の 1.9 は最外れ値として採らない（`[VL]`） |
| 負の字送り          | **禁止**                                 | 8社中**0社**。和文の詰めは `palt` で行い `letter-spacing` はアキ方向にしか使わないのが共通の作法（`[VL]`）                            |
| 見出しの字送り      | **0 〜 +.05em**                          | Sansan +.03 / LayerX +.04 / バクラク +.05 / ナレッジワーク +.03〜.08（`[VL]`）                                                        |
| ウェイト補正        | **Regular +.04em / Bold +.03em**         | ナレッジワークが全段で貫いている唯一の体系的先行例。太字は字面が膨らむぶんアキが広く見えるのを打ち消す（`[VL]`）                      |
| `palt`              | **見出しとラベルのみ。本文には付けない** | ナレッジワーク方式。LayerX の全面適用と2択で、本文に効かせないのは意図的な判断（`[VL]`）                                              |
| `line-break`        | **`strict`**                             | SmartHR のみの先行例。禁則を厳格にする（`[VL]`）                                                                                      |
| `text-spacing-trim` | **`space-all`**                          | SmartHR のみの先行例。`palt` に依存せず約物アキを詰める（`[VL]`）                                                                     |
| 本文の下限          | **14px未満を禁止**                       | デジタル庁が「原則として許容されない」と明記。14px 自体も付随情報に限る（`[VL]`）                                                     |
| `text-wrap`         | **`balance` を見出しに採用**             | **国内BtoB 8社中0社。先行例ゼロの領域**（`[VL]`）                                                                                     |

#### `text-wrap: balance` を先行例ゼロでも採る理由

`[VL]` の実測では、和文の改行制御は `text-wrap` ではなく
**`<br>` の手動挿入・画像化・`white-space: nowrap`** で行われている。
バクラク・SmartHR・カミナシのヒーロー見出しはいずれも `<br>` か画像で改行位置を固定している。

**手動の `<br>` は、コピーを人が書く前提の解法である。**
本システムはAIが日本語コピーを量産する前提であり、AIに `<br>` の適切な位置を判断させると
必ず暴れる（「見出しが3行に折り返してヒーローが崩れる」は既知の最頻事故）。
`text-wrap: balance` は**この手動作業の自動化**として採る。

先行例が無いことのリスクは、Stage 5 の和文最悪ケース VRT で吸収する。
`balance` が効かないブラウザではただ折り返すだけなので、劣化は緩やかである。

### 1-6. 既存バグの修正

`packages/ui-web/src/styles/theme.css` に2件。

**(a) `:lang(ja)` の `font-feature-settings` が body の指定を丸ごと上書きしている**

```css
body {
  font-feature-settings: 'cv01', 'cv03', 'cv04', 'tnum';
}
:lang(ja) h1,
:lang(ja) h2,
:lang(ja) h3 {
  font-feature-settings: 'palt';
}
```

`font-feature-settings` は加算されない。和文ページの h1〜h3 では `tnum`（等幅数字）が失われ、
**数値訴求の桁がガタつく。** 数値訴求は 19/19 ページが持つ必須要素（`[LP]`）であり、
見出しに数字が入るケースは頻出する。全機能を明示的に並べて書く。

**(b) `.lang-ja` / `.lang-en` がデッドコード**

どちらのクラスもコンポーネント側で一度も付与されていない（使用0件）。
和文の行間はこの2クラスではなく、1-5 のタイポスケールが担う。削除する。

### 1-7. radii / shadow / motion

トークンの共通化の境界線を引き直す。現在 `@siracusahq/tokens` にあるもののうち、
**ブランドとして本当に共通なのはニュートラル・フォントファミリ・余白リズムだけ**。

```
tokens（共通のまま）     neutral scale / fontFamily / fontWeight / spacing 4pxグリッド
ui-app 固有             radii(小) / shadow(UI) / motion(100–300ms)
ui-web 固有（新設）      radii(役割名) / shadow(2層) / motion(二系統)
                        和文タイポスケール
```

- **`radii` は役割名にする。** 現状 `rounded-full` 15回 / `rounded-2xl` 9回とスケール上端に
  張り付いているのは、px値で選ばせているから。`--radius-card` / `--radius-pill` /
  `--radius-media` / `--radius-section` のように、**どこに使うかで名前を付ける**。
  バクラクが `--radius_section: 20px` / `--radius_section-inner-md: 10px` という
  役割名トークンを持っているのと同じ形（`[MB]`）
- **`shadow` は2層にする。** UI操作用の小さい影と、LPの「浮いたカード」用の
  大きく柔らかい影は別物。1つのスケールに混ぜない
- **`motion` は二系統にする。** UI応答（100〜300ms、`ease-out`）と
  演出（400〜900ms、expo系）を分ける。`AnimateOnScroll` のハードコード
  （600ms / ease-out）は演出系トークンへ戻す

**注意**: 二重管理の検出（`tokens.test.ts`）は無効化しない。正本の置き場所が
変わるだけで、CSS変数との突き合わせは維持する。Stage 2 でトークンを codegen 化すれば、
このテストが守っている事故そのものが構造的に消える。

### 2-C. CSS Modules への移行（案C）

#### なぜ Tailwind の配布をやめるか

利用者は Astro を前提としており、Tailwind を持っているとは限らない。
また Tailwind クラスを配布したままだと以下が起きる。

- **`@theme` 変数がグローバルを汚す**。`--color-primary-*`・`--font-sans`・`--radius-*`
  を宣言するため、利用者が自分の Tailwind テーマを持っていると読み込み順で
  一方が勝つ。preflight は利用者のページ全体をリセットする
- **`className` が静かに効かない**。AIは高確率で `<HeroSection className="mt-24">` と
  書く。利用者に Tailwind がなければ何も起きず、あってバージョンが違えば微妙にずれる。
  どちらもエラーにならず Storybook でも再現しない
- prefix による名前空間分離は**設定1行では済まない**。`prefix(ps)` を付けると
  利用者が書くクラス名が `ps:flex` になるため、全コンポーネントのクラス文字列を
  書き換える必要がある（実測: prefix 適用時の生成ユーティリティは0件）

#### なぜ vanilla-extract ではなく CSS Modules か

どちらを選んでも**利用者には見えない**（コンパイル済みCSSを配るため）。
したがってこれは純粋に自社内の実装体験の選択であり、以下2点で CSS Modules を採る。

1. **AIの実装精度**。35コンポーネントを書き、その後も保守するのは主にAI。
   素のCSSでの精度は明確に高い。vanilla-extract は `.css.ts` がビルド時実行である
   ことを理解できず、runtime値を参照して壊す失敗を繰り返す
2. **既存のビルド構成を壊さない**。esbuild 0.25 は CSS Modules をネイティブに処理する
   ことを検証済み。tsup 設定を変更せずに動き、コンポーネント単位エントリのおかげで
   **CSSも自動的にコンポーネント単位で分割される**

移行方向の非対称性も理由になる。CSS Modules → vanilla-extract は容易
（トークンはCSS変数として存在し、cva → recipe は構造が同じ）だが、逆は型情報を捨てる作業。

#### 必須の3点セット

CSS Modules は既定では「静かに壊れる」。CSSの `.gradient` をリネームすると
`s.gradient` が `undefined` になり `class="base undefined"` が出力される。
以下を必ず併せて導入する。

1. **トークン → CSS変数の生成**。`@siracusahq/tokens` から `theme.css` を codegen し、
   値の二重管理を構造的に消す。**ブランドランプの生成もここに乗せる**
   （色相を1つ与えるとランプ全段が出る。1-4 の「生成器」の実体）
2. **`*.module.css.d.ts` の生成**。typecheck に含め、クラス名のリネーム・typo を
   型エラーにする。**これを省略するなら CSS Modules は vanilla-extract より劣る**
3. **stylelint で `var()` を既知トークンに制限**。存在しない変数参照を落とす。
   **併せて hex リテラルの直書きを禁止する**（バクラクの `clm.css` と同じ破れ方を止める）

#### 配布物

- コンパイル済みCSS（Tailwind は不要）
- Web フォントを `@font-face` として同梱（現在の未配信問題を同時に解決）
- `pnpm size` に**CSSサイズの枠を追加**する。現状JSしか測っておらず、
  CSSが肥大しても誰も気づかない

#### 2段階CTAは「2オファー」として設計する

現行の想定は「軽（資料DL）+ 重（問い合わせ）」の軽重2段階だったが、

| 軽 + 重                   | 7                                     |

「＼詳しい料金がわかる／ 料金表をもらう」という**2本とも軽いCTA**を並べている。
これは軽重の2段階ではなく、**「何の資料が欲しいか」の分岐**であり質的に別の設計。

またセルフサーブ型（freee / MF / chatwork）では重いCTAが「問い合わせ」ではなく
「無料で始める」になり、重さの性質が営業接触ではなくアカウント作成に変わる。

→ **`primary` / `secondary` に軽重を焼き込まない。** `offers: [Offer, Offer]` として、
各オファーが自分のラベル・kicker・遷移先・計測IDを持つ形にする。

#### `FormSection` に `onSubmit` の口を開ける

現行は **Formspree 固定**（`formspreeId` prop を受けて `https://formspree.io/f/{id}` に
直接 fetch する）。npm パッケージとして配る以上、利用者の送信先を決め打ちしてはならない。

`onSubmit(values) => Promise<void>` を第一級にし、Formspree は
「`formspreeId` を渡したときに使われる既定の実装」に降格する。

実測では **15/19 ページがフォームを別ページに置いている**（`[LP]`）ため、
埋め込みフォームは lead-gen 型の主役であって、product 型の必須部品ではない。

#### 全CTA・フォームに計測フック

`data-cta` 属性と `onCTAClick` コールバックを、CTAを出しうる全コンポーネントに通す。
LPは成果を測れなければ改善できないが、**現状はクリックを捕捉する口が1つも無い。**
Stage 4 でページ層から一括で受け取れるようにする。

### 3-2. 既定セクション順序

製品系12ページの最大公約数（`[LP]`）:

```
Hero
 → 社会的証明帯（ロゴ帯 or 数値バッジ）        9/12 がヒーロー直下
 → 価値・課題提起
 → 機能／サービス
 → 料金
 → 選ばれる理由                                7/12
 → 導入事例
 → サポート／導入の流れ                        5/12
 → FAQ（任意）                                 5/12 — 必須ではない
 → コンテンツ回遊（資料・セミナー・コラム）    9/12
 → 最終CTA面                                   10/12

```

**料金 → 事例の順序に変更する。** 当初の想定は「事例 → 料金」だったが、
両方を持つページでは **料金 → 事例が4件、事例 → 料金が1件**（`[LP]`）。

**FAQ は任意にする。** 12ページ中5ページ（42%）にしかない。必須セクションではない。

#### 記事系ページの順序（`[NB]`）

上記はLP（製品系12ページ）の順序である。記事ページはこれとは別の順序を持つ。

**News 記事**（実測 12 本）:

```
パンくず（11/12）
 → 記事タイトル h1（12/12）
 → 公開日（12/12。更新日は 0/12）
 → [カテゴリ / タグ]（8/12）
 → [SNS シェア]（8/12）
 → リード文（10/12）
 → 本文の章 ×4（12/12。h3 は 3/12）
 → [会社概要・問い合わせ先の定型章]（6/12）
 → [末尾 CTA]（7/12）
 → 関連記事 3 件（10/12）
 → 一覧へ戻る（10/12）
```

**ブログ記事**（実測 15 本）:

```
パンくず（14/15）
 → 記事タイトル h1（15/15）
 → 公開日（15/15） + [更新日]（5/15）

```

**News とブログの分岐点は「著者・目次・更新日・SNS シェア」の 4 つ。**
本文量も違う（News 中央値 約2,200字 / ブログ 約7,000字 / 事例記事 約3,400字）。

**末尾 CTA を必須にしないこと。** 事例記事は 27/27 が持っていたが、
記事系は News 7/12・ブログ 11/15 で、SmartHR ニュースのように
末尾 CTA を一切持たない運用が実在する。

### 3-3. リズム

背景と余白はセクション単体では決められない。**前後関係で決まる。**
ページコンテナがルールで割り当てる。

#### 背景 — 未検証であることを明記する

当初の「本文セクションは default ↔ muted を交互に」という規則は、
**`[LP]` では検証できていない。** ブラウザレンダリングもスクリーンショット取得も
行っていないため、実サイトの背景の明暗リズムは**一切分かっていない**。

「ヒーローと最終CTAのみ強調面」も同様に未検証で、**むしろ反証の気配がある**。
カミナシは本文中に「導入までの流れ」「セミナー」など多数の面を持ち、
freee会計・バクラクは本文中にセキュリティ専用セクションを持ち、
Bill One は「Bill One Bank」の独立ブロックを持つ。強調面が2枚に収まる構造には見えない（`[LP]` の推測）。

→ **交互リズムは「他社がそうしているから」ではなく「自分たちがそう決めたから」として実装する。**
**基準は Stage 5 のページ単位VRTで自分たちで作る。** 最初のスナップショットが基準になる。

確定で置ける規則は1つだけ。**暗い面の連続を禁止する**（3連続で dev 警告）。
これは可読性の問題であって、他社実態の問題ではない。

#### 余白

- 単一のリズムスケールを使う
- 関連するセクション間は詰め、話題が変わるところで開く（章立て）

#### CTA — 「2箇所まで」を撤回する

当初の規則「1ビューポート1つ・ページ全体で2箇所まで」は**明確に反証された**（`[LP]`）。

| 観測                            | 値                                                                    |
| ------------------------------- | --------------------------------------------------------------------- |
| 総CTA数の中央値                 | **15〜16本**                                                          |
| 「2本まで」に該当するページ     | **0件**                                                               |
| プライマリCTAの**ラベル種類**数 | **2種が最頻**（9ページ中8ページ）                                     |
| 反復回数                        | バクラク経費精算 = 「メールで資料を受け取る」×5 +「料金表をもらう」×5 |

→ **新しい規則: プライマリCTAの「ラベル」は2種類まで。反復は自由**（目安4〜6回）。

ページコンテナはラベルの種類数を数え、3種類目が現れたら dev 警告を出す。
**回数は数えない。** 同じ2種をセクション区切りごとに繰り返し置くのが実態の標準形。

これは実装にも影響する。`CTABand` のような**繰り返し置ける部品**が必要で、
「ページに2つしか置けない特別なコンポーネント」ではない。

### 3-4. トーンとブランドの直交

変化は「自由度」ではなく「名前付きの選択肢」として渡す。締めすぎると全ページが
同じ顔になり、マーケティングとしては失敗するため。

| トーン     | 用途                                     | 性格                                                  |
| ---------- | ---------------------------------------- | ----------------------------------------------------- |
| `trust`    | コーポレートサイト、エンタープライズ向け | 明るい、余白広め、装飾最小、操作色のみ                |
| `product`  | サービスサイト                           | 明るい + アクセント、プロダクト画面主役、技術的       |
| `campaign` | 獲得LP、広告着地                         | コントラスト強め、ヒーロー濃色、CTA強調、装飾色を許可 |

**ブランド軸とトーン軸は直交する。**

- **ブランド**（`brand`）= 誰の顔か。色相・視覚デバイス・ロゴを決める
- **トーン**（`tone`）= 何を狙うページか。装飾量・コントラスト・余白量を決める

`<Page brand="peerdesk" tone="campaign">` は成立するし、
`<Page brand="corporate" tone="trust">` も成立する。
**組み合わせを禁止しない。** 一方が他方を上書きする関係にもしない。

`MarketingButton` の `gradient` バリアントは `campaign` トーンでのみ有効とする。

### 3-5. API 2本立て

用途が2つあるので、APIも2つ用意する。

#### (a) LP量産 — データ駆動

```tsx
<LandingPage {...defineLandingPage({
  pattern: 'product-portfolio-top',
  brand:   'peerdesk',
  tone:    'product',
  hero:    { title, subtitle, offers: [docOffer, priceOffer] },
  proof:   { logos } /* または { stats } */,
  products:[...],
  cases:   [...],
  closing: { form },
})} />
```

AIの仕事が「デザインする」から**「フォームを埋める」**に変わる。構成の判断が
発生しないので速く、間違えようがない。必須項目の欠落は**型エラーで落ちる**。

#### (b) コーポレート・サービスサイト — コンポジション

1ページずつ違うので、セクションを自由に並べられる形を残す。
Stage 1・2 が効いているため、並べ方だけ自由でリズムは自動。

```tsx
<Page brand="corporate" tone="trust">
  <Hero ... />
  <ModuleOverview ... />
  <SecurityBadges ... />
</Page>
```

Astro でコーポレートサイトとサービスサイトを作り、LPを量産するという計画に
この2本立てが対応する。

## Stage 4: リード獲得

Stage 3 までは「崩れないページが速く出る」までしか担保しない。
LPは**成果を測って改善する装置**であり、そのための口が現状ゼロ。

### 4-1. 計測

- 全CTAに `data-cta="<id>"` を出す
- `<Page onCTAClick={handler}>` でページ単位に一括で受け取る
- フォームの `onSubmit` / 送信成功 / 送信失敗をイベントとして出す
- **計測タグそのものは同梱しない。** GA4 も GTM も利用者の選択であり、
  DSがベンダーを決めてはならない。フックまでを提供する

### 4-2. 追従CTA — 2部品

当初の「モバイルは画面下固定バー」を**撤回する**。

| 観測                                               | 値                                   |
| -------------------------------------------------- | ------------------------------------ |
| 全幅の下部固定モバイルCTAバーを確認できたページ    | **0 / 19**（`[LP]`）                 |
| 固定ヘッダー内にCTA2本                             | 1件確認（カミナシ）                  |
| 右下フローティングカード                           | 1件確認（カミナシ）                  |
| 下部固定バーを「部品としては持つが当該LPで未使用」 | 1件（freee `.ncms-mod-sticky-bar2`） |

**ただしこれは「無い」ことの証明ではない。** SmartHR / Bill One / Sansan は
クライアントレンダリングで、JS実行後に挿入される可能性を排除できていない（`[LP]`）。
それでも**実装の根拠として使えるのは、実際に確認できた2形態だけ**である。

用意する部品は2つ。

| 部品                    | 実測値（カミナシ、`[LP]`）                                                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`StickyHeaderCTA`**   | 固定ヘッダー内にCTAを2本内包。`position: fixed; top: 0; width: 100%; z-index: 2`。**モバイルでは2本が各 `45vw` / 高さ40px で横並び**、ハンバーガー40px、ヘッダー行 60px  |
| **`FloatingCornerCTA`** | 右下カード。`position: fixed; bottom: 30px; right: 30px; width: 380px; height: 240px; z-index: 5`。中身は2CTA。**閉じるボタン必須**。モバイルでは内部ボタン `width: 90%` |

`FloatingCornerCTA` の**dismiss（×）は任意ではなく必須にする。**
カミナシの実装が持っており、閉じられない追従要素はモバイルで本文を覆う。

全幅下部バーは実測が0件なので**作らない。** 必要になったら、そのとき根拠と一緒に足す。

### 4-3. 2オファー

Stage 2-D で定義した `offers: [Offer, Offer]` を、ページ型ごとの既定値として持つ。

| ページ型                            | 既定のオファー構成                              |
| ----------------------------------- | ----------------------------------------------- |
| `product` / `product-portfolio-top` | 軽（サービス資料）+ 軽（料金表） または 軽 + 重 |
| `lead-gen`                          | 単一オファー（そのページの資料）                |
| `corporate-top`                     | オファーなし                                    |

**FVのCTAは2本が圧倒的**（13/17 ≒ 76%、`[LP]`）。3本以上は dev 警告の対象にする。

### 4-4. フォームの摩擦

`[LP]` で項目数が実測できたのは freee会計のヒーロー内フォームのみで、
**メール1項目 + Google / Microsoft SSO の2ボタン**だった。他社は全て取得不可。

データが1件しかないので**項目数の上限を規則にはしない。** 代わりに構造で支える。

- `FormSection` は必須項目と任意項目を型で分ける
- 送信ボタンのラベルをオファー名と一致させる（「送信」ではなく「資料を受け取る」）
- 問い合わせ・見積もり・トライアルは**フォームを分ける**のが実態
  （SmartHR = 3本、Bill One = 2本、freee人事労務 = 3本。`[LP]`）。
  1つのフォームに用途セレクタを付ける設計は採らない

## Stage 5: 守り

### ページ単位のビジュアルリグレッション

Playwright のスクリーンショット比較をCIで回す（Chromatic は有料のため自前で十分）。
**検証単位はコンポーネントではなくページ。** 統一感はページを並べて初めて判定でき、
コンポーネント単位の Storybook では見えない。

**背景リズムの基準はここで作る。** 3-3 のとおり他社実態は未検証なので、
最初に自分たちが良いと判断したスナップショットが基準になる。
以降はそこからのズレを検出する。

### 日本語の最悪ケースを固定する

実務上いちばん効く。AIが書く日本語コピーは長さが暴れるため、見出しが3行に
折り返してヒーローが崩れる、カードの高さが揃わない、といった事故が最も多い。

「異常に長い和文」「異常に短い和文」「英語」の3パターンをページ単位のストーリーとして
持ち、VRTで固定する。**`text-wrap: balance`（Stage 1）の効果もここで確認する。**

### dev ビルドでの警告

| 警告                                     | 根拠                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------- |
| `h1` が2つ以上ある                       | 構造の問題                                                            |
| プライマリCTAの**ラベル種類**が3種類以上 | `[LP]`。**回数は数えない**（当初の「1ビューポート2つ以上」は撤回）    |
| FVのCTAが3本以上                         | FV 2本が13/17（`[LP]`）                                               |
| 暗いセクションが3連続                    | 可読性                                                                |
| `StatBadge` に `asOf` が無い             | 景品表示法                                                            |
| 社会的証明スロットが空                   | ロゴ帯と数値バッジのどちらも無い状態。19/19が数値訴求を持つ（`[LP]`） |
| ロゴが1〜5社                             | 下記                                                                  |

**「ロゴ6社未満」の警告は撤回し、切替ガイドに置き換える。**

`[LP]` の実測では、**ロゴ帯と数値バッジは代替関係**にある。

| 選択                                          | ページ数          |
| --------------------------------------------- | ----------------- |
| **0社（ロゴ帯を置かず数値バッジに振り切る）** | **6 / 19（32%）** |
| 6〜8社（事例セクション内に少数）              | 2                 |
| 14社以上（カルーセル）                        | 5                 |

freee は「有料課金ユーザー企業数62万」「シェアNo.1 56.3%」の数値の圧倒性でロゴを不要にしており、
**0社は劣った選択ではない。** 「6社未満は逆効果」という因果は、CVRデータが非公開である以上
検証不能でもある。

→ **規則:**

1. 社会的証明スロットには「ロゴカルーセル」と「数値バッジ」の2実装があり、**どちらかを必ず置く**
2. ロゴを載せるなら**中央値は約20社**。14社以上でカルーセルにする
3. **1〜5社の中途半端なロゴ帯は日本語ページに実例が0件**。少数しか出せない場合は
   ロゴ帯ではなく**事例カードに紐付ける**（SmartHR 6社 / Bill One 8社の方式）

### 消費側からの結合テスト

最小の Astro アプリをCIでビルドし、生成物に期待するCSSが載っているかを検証する。
Storybook では絶対に見えない配布の事故を止める唯一の手段。

### CSSサイズの枠

`pnpm size` に CSS の枠を追加する。**ブランドを増やすとランプが増える**ため、
ブランド追加のたびにCSSが線形に膨らむ。ここに枠が無いと気づけない。

## Stage 6: AI向け規範ファイルの同梱

配布物（`files`）に機械可読のルールファイルを含める。CLAUDE.md はこのリポジトリの
中でしか効かず、`@siracusahq/gtm-design-system` を入れた先のAIエージェントには届かない。

Stage 1〜4 が完了していれば、書くことは劇的に減る。

```
ブランドは3つ。トーンは3つ。ページの型は5つ。あとは埋めるだけ。
import '@siracusahq/gtm-design-system/styles.css' を1行書く。
```

**APIで表現できるルールを文章で書くのは負け筋。** 現状のまま規範ファイルを書くと、
10兆通りの組み合わせのうち何が正しいかを文章で説明する羽目になり、守られない。
