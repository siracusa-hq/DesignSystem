# お知らせ / ブログ系ページ型 実測調査 — 国内BtoB SaaS の「量産される記事」の第2の型

対象: 日本のBtoB SaaS の **Web / LP 面のみ**（`@siracusahq/gtm-design-system` 側）。
母集団は [LP アナトミー調査](./research-lp-anatomy.md) /
[事例記事調査](./research-case-study-detail.md) と同じ核（同じ 10 社を候補にした）。

調査日: 2026-08-14
調査手法: **`WebFetch` による HTML / テキスト取得と構造の読み取り**（実ブラウザ計測ではない。§1-1）
出典記号: **`[NB]`**（News / Blog 調査。`composition-redesign.md` 冒頭の「実測の出典表記」表に倣う）

## 0. 調査の動機

`case-study-detail` の実測で、次のことが分かっている。

> 事例記事は**構成と書式がサイト内で固定されており**、記事ごとに変わるのは
> 章数・文字数・写真枚数という「量」だけである（一致率 97.6%）。
> これはデザインシステムがパターンとして配るのに最も適した性質である。

事例記事が「フォーマットに則って量産されるコンテンツ」なら、
**お知らせ（News / プレスリリース）とブログ（コラム / オウンドメディア）も同じはず**である。
むしろ本数は事例記事より多い。SmartHR Mag. も HR大学 も記事数は数百〜数千本の規模にある。

一方で `composition-redesign.md` §3-1 のページ型は現在 6 種
（`lead-gen` / `product` / `product-portfolio-top` / `corporate-top` /
`case-study-list` / `case-study-detail`）で、**News とブログの受け皿が無い**。
LP 末尾のコンテンツ回遊セクション（`[LP]` 9/12）が指す遷移先の半分が、
このシステムでは表現できない状態にある。

本調査の問いは 2 つ。

1. News / ブログの一覧・詳細は、事例記事と同じくらいフォーマット化されているか
2. **`case-study-list` / `case-study-detail` の拡張で済むのか、新しいページ型が要るのか**

このリポジトリの鉄則は「実測なしに構成を推測しない」。
`case-study-detail` が一度「データが無いから作らない」と保留され、
実地調査を経て解除された前例に従う。

## 1. 手法と限界（先に読むこと）

### 1-1. 元調査（`[LP]` / `case-study-detail`）との手法の違い

**本調査は実ブラウザ計測ではない。** 環境の制約により Playwright 等の
ブラウザ自動化を使えないため、`WebFetch`（URL 取得 → Markdown 変換 → 構造の読み取り）で代替した。

| 項目                                                | `case-study-detail` 調査 | 本調査 `[NB]`                 |
| --------------------------------------------------- | ------------------------ | ----------------------------- |
| 取得手段                                            | ヘッドレス Chromium      | `WebFetch`（HTML → Markdown） |
| `getComputedStyle` の実値（font-size / 読み幅 ほか） | **取得した**             | **取得していない**            |
| 要素のページ絶対座標（y 座標）                      | **取得した**             | **取得していない**            |
| スクリーンショットによる目視確認                    | 29 ページ                | **0 ページ**                  |
| JS 描画後の DOM                                     | 反映される               | **反映されない場合がある**    |
| セクション順序・見出し階層                          | 取得した                 | 取得した                      |
| メタデータ項目・著者・目次・関連記事                | 取得した                 | 取得した                      |

**したがって本調査が主張できるのは「構成・情報設計」だけである。**
余白 px・フォントサイズ・読み幅・色は 1 つも測っていない。
実装時にタイポグラフィの値が要る場合は、`case-study-detail` 調査の
中央値（本文 16px / 行間 1.80 / 読み幅 742px）を流用するか、
実ブラウザ計測が可能になった時点で測り直すこと。

### 1-2. 事実として記録したもの

- **一覧ページ**: `h1` の文言と型 / フィルタ・タブの軸と選択肢 / カード型か 1 行リストか /
  アイテムのメタ情報 / ページネーション形式 / ピックアップ枠 / 検索ボックス / 末尾導線
- **詳細ページ**: パンくず / `h1` / 公開日・更新日 / カテゴリ・タグ / 著者表示 /
  目次 / `h2`・`h3` の個数 / SNS シェア / 本文中 CTA / 末尾 CTA / 関連記事 /
  一覧への戻り / 画像枚数 / リード文 / 本文の概算文字数

### 1-3. 取得できなかったもの・失敗の記録（**必ず読むこと**）

取得できないこと自体が実測結果である。以下は隠さず全部残す。

**a) URL の推定が 3 回外れた。**
一覧ページから抽出した記事 URL が相対パス断片のまま返ってきた結果、
組み立てた URL が 404 になったケースが 4 件ある。

| 試した URL                                              | 結果                                     | 正しい URL                       |
| ------------------------------------------------------- | ---------------------------------------- | -------------------------------- |
| `smarthr.jp/mag/`                                       | **404**                                  | `mag.smarthr.jp/`（別サブドメイン） |
| `smarthr.jp/hr/labor/heatstroke-measures/` ほか 2 件    | **404**                                  | `mag.smarthr.jp/hr/labor/...`    |
| `kaminashi.jp/blog`                                     | **404**                                  | `kaminashi.jp/media`             |
| `andpad.jp/news/15972/` / `andpad.jp/news/12736/`       | **404**（コーポレート側の記事 ID を混同） | `andpad.jp/news/20260616`（日付） |

**ANDPAD は News の URL 体系が 2 系統ある。**
`andpad.co.jp/news/{数値ID}/`（コーポレート）と `andpad.jp/news/{YYYYMMDD}`（サービス）が並存し、
一覧も `andpad.co.jp/news/` と `andpad.jp/posts/news` の 2 つある。本調査は後者（サービス側）を採った。

**b) `blog.kaminashi.jp` は `kaminashi.jp/media` へ 301 されていた。**
検索結果に残っている旧ドメインは現存しない。**「現場と人」というメディア名にリブランドされている。**

**c) Chatwork のコラム 1 本が別ホストへ 302 していた。**
`go.chatwork.com/ja/column/finance_accounting/dx.html` → `go.taxita.com/column/accounting068`。
**Chatwork（kubell）は経理系コラムを別サービス（taxita）へ移管している。**
別ホストの記事は本調査の分母に入れていない。

**d) kubell（Chatwork の運営会社）のコーポレート News は 2 回とも取得に失敗した。**
`corp.kubell.com/news/` と `corp.kubell.com/news` の両方が `Socket is closed` で切断された。
403 でも 404 でもないため、ネットワーク層かサイト側のいずれの問題かは切り分けられていない。
**Chatwork は「ブログのみ取得成功、News は 0」で記録する。**

**e) Sansan のニュース一覧は「該当の記事がありません」を返した。**
`jp.corp-sansan.com/news/` はフィルタ UI（カテゴリ 8 / 年 / キーワード）と
`load more` ボタンは取得できたが、**記事が 1 件も描画されていない**。
JS でのフェッチ後に描画する実装で、`WebFetch` では中身に到達できなかったと考えられる（§1-1 の限界）。
**一覧の骨格だけ採用し、Sansan の News 記事は 0 本とする。**

**f) HRBrain のお知らせ一覧は途中で切れた。**
`hrbrain.jp/news` はフィルタ軸（すべて / ニュース / 機能追加・更新 / 導入リリース / 導入インタビュー）
までは取得できたが、以降が `[Content truncated due to length...]` で欠落。
**記事 URL が採れず、HRBrain の News 記事も 0 本。**

**g) バクラク（LayerX）のブログは特定できなかった。**
`bakuraku.jp/media/` は **404**。LayerX は技術記事を note・はてなに出しており、
自社ドメイン上のオウンドメディアが存在しない可能性がある（未確認）。
**LayerX は「News のみ」で記録する。**

**h) サイボウズ / kintone の日本語ブログを特定できなかった。**
取得できたのは `blog.kintone.io`（**英語の技術ブログ**。Hatena Blog 基盤、
カテゴリ 13・著者は Twitter ハンドル・1 行リスト型）のみで、
これは日本の B2B SaaS マーケティング面の記事ではない。**集計の分母から外す。**

**i) 文字数・画像枚数は概算である。**
`WebFetch` が返した Markdown 上での見積もりで、レンダリング後の実測ではない。
とくに画像は SVG プレースホルダやデータ URI を含む数え方になっており、
カミナシの「14 枚」等は上振れしている可能性がある。

**j) 1 サイト 2〜3 記事は、そのサイトの全記事を代表しない。**
`case-study-detail` 調査と同じ制約。記事は一覧の 1 ページ目付近から採った。

**k) PC / SP の区別が無い。** レスポンシブの検証は一切していない。

**l) 「その構成が良いか」は測っていない。** 測ったのは
「何が、どの順で、どれだけ使われているか」だけである。

## 2. サイトごとの記録

### 2-1. SmartHR — News とブログを**別ドメイン・別ブランド**で運営する

| 面     | URL                   | 名前          |
| ------ | --------------------- | ------------- |
| News   | `smarthr.co.jp/news/` | 「ニュース」  |
| ブログ | `mag.smarthr.jp/`     | 「SmartHR Mag.」 |

**News 一覧**: `h1「ニュース」`（短いページタイトル型）。フィルタは **3 軸**
（カテゴリ: プレスリリース / お知らせ、テーマ: コーポレート / サービス、年: 2015〜2026 の 12 年）。
サムネイル付きカード型。日付 `2026.07.07`。先頭に「トピックス」というピックアップ枠がある。
検索ボックス無し。ページネーションは JS 読み込み型で形式を確定できなかった（§1-1）。

**News 記事 3 本**（`/news/press/20260707/` `/20260428/` `/20260415_wellworkingstory/`）は
**構成が完全に一致**している。

```
パンくず（トップ > ニュース > 記事タイトル）
 → h1（プレスリリース見出し）
 → 公開日 2026.07.07（更新日は無い）
 → カテゴリ「プレスリリース」+ テーマ「コーポレート」/「サービス」
 → SNS シェア（Twitter / Facebook。上下 2 箇所）
 → リード文
 → 本文 h2 ×3（h3 は 1 本だけ 6 個）
 → 関連ニュース 10 件
 → 「ニューストップへ戻る」
```

**著者 0/3・目次 0/3・末尾 CTA 0/3。** 本文は 1,200〜3,800 字、画像 1〜4 枚。

**ブログ（SmartHR Mag.）一覧**: `h1「SmartHR Mag. - 働く明日が、もっとよくなる」`
= **ブランド名 + タグライン型**。カテゴリは 4 大分類（人事・労務 / 経営・組織 / 働き方 / ケーススタディ）
× 小分類、加えて「話題のキーワード」タグが 20 個以上。カード型でサムネイル必須、
**著者名がカードに出る**。ピックアップ記事 6 件。**検索ボックスあり**（本調査で唯一）。

**ブログ記事 3 本**も構成が一致する。

```
パンくず（SmartHR Mag. > 人事・労務 > 労務管理 > 記事タイトル）
 → h1
 → 公開日 2026.08.03（更新日は無い）
 → 著者（氏名 + 顔写真 + 肩書き + プロフィール文。社労士・精神保健福祉士など有資格者、
        または「SmartHR Mag. 編集メンバー」）
 → リード文（「この記事でわかること」の箇条書き形式が 2/3）
 → 目次（5〜6 項目 = h2 のみ）
 → 本文 h2 ×5 + h3 ×12〜14
 → 本文中に「あわせて読みたい」リンクと資料DLバナー
 → SNS シェア（Facebook / Twitter / LINE / はてなブックマーク）
 → 記事末尾に本文末タグ（法改正・健康経営 など）
 → 末尾 CTA（お役立ち資料 1 本）
 → 関連記事（「あわせて読みたい」「人気の記事」「最新記事」「おすすめ記事」に分割）
```

本文 6,500〜10,000 字、画像 4〜14 枚。**News の 3 倍前後の分量がある。**

### 2-2. カミナシ — News とブログを同一ドメインの `/news` と `/media` に置く

**News 一覧**（`kaminashi.jp/news`）: `h1「お知らせ一覧」`。フィルタは **1 軸のみ**
（ALL / メディア掲載 / プレスリリース / お知らせ）で、**年別アーカイブを持たない唯一のサイト**。
サムネイル + 抜粋文付きカード型。日付 `2026.08.04`。「もっとみる」ボタン。
「最新のお知らせ」「人気の資料」枠あり。

**News 記事 2 本**（`/news/detail/pr_20260804` `/pr_20260701`）:
パンくず（TOP > お知らせ > タイトル）→ h1 → 公開日 → カテゴリタグ → リード文 →
h2 ×3〜4（h3 は 0）→ 画像 3 枚 → 「最新のお知らせ」3 件 → 「お知らせ一覧に戻る」。
**SNS シェア無し・著者無し・目次無し・末尾 CTA 無し**（本調査の News で最もそぎ落とされている）。
本文 1,200〜2,200 字。

**ブログ（現場と人）一覧**（`kaminashi.jp/media`）:
`h1「現場で働く人の発見、気づき、助けとなる。現場と人」` = **タグライン + ブランド名型**。
フィルタが **2 軸**あるのが特徴で、**業界**（食品製造 / 機械製造 / 運輸・物流 / 宿泊・ホテル /
飲食 / サービス）と**人気カテゴリー**（業務効率化 / 品質管理 / 衛生管理 / 設備保全 /
マニュアル / HACCP / ISO / IATF / 現場DXアワード / 動画）。
**カードに公開日と更新日の両方が出る**（本調査で唯一）。人気記事枠あり。

**ブログ記事 3 本**（`/media/electronic-checklist` `/on-site-digital-transformation`
`/gemba-dx-award-2025-yamaichisangyo`）:

- **3 本すべてが「公開日 2025.02.02 / 更新日 2026.05.22」の 2 日付を出す**
- 著者は氏名のみ（「むつごろー」「鎌田 大輝」「現場と人 編集部」）で、肩書き・顔写真・プロフィール文は無い
- 目次は解説記事 2 本にあり（13 項目 / 15 項目 = h2 + h3 の全展開）、
  **インタビュー型の 1 本（現場DXアワード）には無い**
- h2 6〜8 / h3 12〜17。本文 6,500〜13,000 字
- 本文中に同一の CTA バナーが 3 箇所繰り返される（解説記事）
- 関連記事「関連する記事」3 件 + 「人気の記事」
- 「TOPへ」で一覧に戻る

### 2-3. マネーフォワード — News は最小構成、ブログは連載を含む

**News 一覧**（`corp.moneyforward.com/news/`）: `h1「Press Release / プレスリリース」`（日英併記）。
**サムネイル無しの 1 行リスト型**。フィルタ 2 軸（年 2012〜2026 の 16 択、カテゴリ: サービス / コーポレート）。
**番号ページャ**（1 2 3 4 5 »）。ピックアップ枠・検索ボックス無し。

**News 記事 2 本**: パンくず（HOME > プレスリリース > タイトル）→ h1 → 公開日 `2026-08-14` →
**カテゴリ表示は記事側に無い**（一覧にはあるのに落ちる）→ リード文 → h2 ×2〜4（`■` 記号付き。h3 は 0）
→ SNS シェア（ツイート / シェア / ブックマーク）→ 末尾に広報の問い合わせ先。
**関連記事 0 件**（本調査の News で唯一）。本文 1,300〜2,800 字。

**ブログ（Bizpedia）一覧**（`biz.moneyforward.com/blog/`）: `h1` を特定できず。
**1 行リスト型**（左にカテゴリラベル、タイトル、日付 `2026.8.10`、抜粋）。
カテゴリは「経理に役立つ」「猫経理」「DX」の 3 つ。

**ブログ記事 2 本**が**同一メディア内で大きく違う**。

| 記事                        | 目次    | h2/h3 | 著者                                   | 画像 | 文字数    |
| --------------------------- | ------- | ----- | -------------------------------------- | ---- | --------- |
| 骨太の方針2026（解説記事）  | 6 項目  | 3 / 6 | 合江 篤・ERPドメインリサーチャー・経歴文 | 1    | 約 6,500 |
| 猫経理66（4 コマ連載）      | **無し** | 1 / 0 | 前田 康二郎・経歴文                     | 2    | **約 100** |

**同じメディアでも「解説記事」と「連載」でテンプレートが違う。** これは重要な発見で、
`case-study-detail` の「サイト内は完全に固定」という性質が、
ブログでは**「記事の種類ごとに固定」**へ弱まることを示している（§3-4）。

### 2-4. freee — News は自社フォーマット、ブログは別ブランド（経営ハッカー）

**News 一覧**（`corp.freee.co.jp/news/`）: `h1「NEWS」+ 説明文`。
フィルタが**本調査で最も細かい 3 軸**（年 2012〜2026 / 月 全 + 1〜12 / タグ 14 種
= 製品名 `freee会計` `freee人事労務` … と種別 `プレスリリース` `業務提携` の混在）。

| 揺れ                                  | 中身                                                                         |

| Bizpedia の目次・末尾CTA・文字数      | **解説記事 6,500 字 / 4 コマ連載 100 字**。同じメディアに別テンプレートが同居 |

> 事例記事は「サイト単位」でフォーマットが固定されていた。
> **News / ブログは「メディア単位 × 記事の種類単位」で固定されている。**
> 同じ会社でも News とブログはまったく別のテンプレートであり（§3-5）、
> 同じブログの中でも「解説記事 / インタビュー / 連載」でテンプレートが分かれる。

逆に「解説記事 / インタビュー / 連載」の分岐までは作らなくてよい
（連載は実測 1/15 で、それ専用のページ型を配る根拠が無い）。

## 4. 設計提案

### 4-1. 方針

`case-study-detail` §4-1 の方針をそのまま継承する。

- **記事ごとの構成の選択肢は作らない。** 順序はパターンが決める。呼び出し側が渡すのは内容だけ
- **実測に無いものは作らない。** 冒頭の数値タイル（**0/54**）・
  News の著者（0/12）・News の目次（0/12）・無限スクロール（0/14）は**作らない**
- **一覧と記事で語彙を共有する。** カテゴリ・タグ・公開日は両方で同じ型を使う

そのうえで本調査に固有の判断を 1 つ足す。

- **News とブログを 1 つの入力型に押し込まない。** 判別ユニオンで分ける（§3-5）。
  両方のフィールドを optional にして 1 型にすると、
  **「著者と目次を持つ News」という実測に存在しない構成が型で許される**。
  `case-study-detail` が「選択肢はパターンのレベルで固定し、記事ごとには選ばせない」で
  得た性質を、ここで手放してはいけない

### 4-2. 何を新設するか

**新ページ型は 2 つ**（`article-list` / `article-detail`）を推奨する。
それぞれ内部に `kind: 'news' | 'blog'` の判別ユニオンを持たせる。

| 案                                              | 型の数 | 評価                                                                                                       |
| ----------------------------------------------- | -----: | ---------------------------------------------------------------------------------------------------------- |
| `case-study-list/detail` を拡張                 |     +0 | **不可**。`profile` / `summary` / `speakers` が 0/27 で流用できず、必須フィールドを optional に緩める破壊的変更になる |
| `news-list` `news-detail` `blog-list` `blog-detail` |    +4 | 実測には最も忠実だが、一覧の差分（`h1` の型・ピックアップ枠・年別）は**中身の差**であってページ型の差ではない |
| **`article-list` + `article-detail`（判別ユニオン）** | **+2** | **推奨。** `kind` で許容フィールドが変わるため実測の縛りを型で表現でき、共通の骨格は 1 つで済む            |
| `article-detail` 1 つ（全部 optional）          |     +1 | **不可**。実測に無い組み合わせを型が許してしまう（§4-1）                                                  |

### 4-3. 作らないもの（実測を根拠に）

| 作らないもの                                    | 根拠                                                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------------- |
| **冒頭の数値タイル**                            | 事例 0/27 + News 0/12 + ブログ 0/15 = **0/54**                                |
| **News の著者・目次**                           | **0/12**。型に含めない（`kind: 'news'` では存在しないフィールドにする）       |
| **無限スクロール**                              | **0/14 ページ**。番号ページャか「もっと見る」の二択                          |
| **記事ごとの目次の深さの選択**                  | 目次は `h2`（5/12）と `h2+h3`（7/12）で割れるが、**メディア単位で固定**。パターンが決める |
| **関連記事の複数セクション分割**                | 6/15。1 セクションで十分（`case-study-detail` の `related` と同じ扱い）        |
| **連載 / 4 コマ専用のレイアウト**               | 1/15（Bizpedia 猫経理）。専用の型を配る根拠が無い                             |
| **記事内サイドバー（人気記事・フィルタ）**      | ブログ 3/7・News 0/7。一覧の仕事                                              |
| **並べ替え UI**                                 | 1/14（LayerX のみ）                                                           |
| **検索ボックス**                                | 一覧 2/14。当面は作らない                                                     |

### 4-4. 既存の決定との整合

| 既存の決定                                                | この提案での扱い                                                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **写真規範（`alt` 必須）**                                | ブログのサムネイル・本文画像も `alt` 必須。`CasePhoto` と同じ契約の型を使い回す（新しい写真型を増やさない）                          |
| **`asOf`（時点表記が無いと dev 警告）**                   | 記事に数値タイルが無い（0/54）ため出番は無い。ただし**ブログの `updatedAt` は実測 5/15 で存在する**ので任意フィールドとして持たせる（警告は出さない） |
| **CTA ラベル2種ルール（3種目で dev 警告）**               | 末尾 CTA は 1〜2 本。**バクラクの 3 本併置は 2/12 の例外**で、既存の警告を緩める根拠にはしない                                       |
| **`Container` の既定は `xl`（1280px）**                   | 記事本文は `case-study-detail` の実装値（`max-width: 46.5rem`）を流用する。本調査では読み幅を測っていない（§1-1）ので新しい値は提案しない |
| **`SectionHeader` の `as` プロップ**                      | 一覧・記事ともヒーローを持たないので `h1`。同じ仕組みを使う                                                                          |
| **`CaseCard` / `CaseStudyMeta`**                          | 記事カードは別語彙（会社名・数値バッジを持たない）。**`ArticleCard` を新設**し、`CaseCard` は変更しない                              |
| **バイリンガル対応（テキストは Props で注入）**           | 「関連記事」「目次」「一覧に戻る」「公開日」「更新日」はすべてラベルオブジェクトへ。実測の見出し文言が 12 通りに割れている（§3-3）ことが根拠 |
| **`Page` の面リズム**                                     | 記事本体は単一の面に置く（`case-study-detail` と同じ）。目次を本文と別の面にしない                                                   |

### 4-5. 必要な新部品（見積もり）

| 部品                     | 内容                                                       | 判断                                                            |
| ------------------------ | ---------------------------------------------------------- | --------------------------------------------------------------- |
| `ArticleListSection`     | フィルタ + カードグリッド + ページネーション               | 新規 1。`kind` でカード型 / 1 行リスト型とピックアップ枠を切替  |
| `ArticleCard`            | サムネ + カテゴリ + タイトル + 日付                        | 新規 1。`CaseCard` とは語彙が違うので分ける                     |
| `ArticleBodySection`     | タイトル + メタ + 著者 + 目次 + 本文の章                   | 新規 1。分割しない（`CaseStudyArticleSection` と同じ理由）      |
| `ArticleAuthor`          | 氏名 + 肩書き + 顔写真 + プロフィール文 + 監修者           | 新規 1（`kind: 'blog'` でのみ使う）                             |
| `ArticleToc`             | 章見出しからの目次                                         | 新規 1（`kind: 'blog'` でのみ使う）。`h2` のみ / `h2+h3` を選ぶ |
| `ShareButtons`           | X / Facebook / はてブ / LINE / Pocket                      | 新規 1。ブログ 15/15 が持つ                                     |

既存で足りるもの: `Section` / `Container` / `Text` / `Heading` / `Link(arrow)` /
`CTASection` / `Page` / `SectionHeader(as="h1")`。

**スライスは 2 つに割るのが妥当**（一覧 = `article-list` + `ArticleCard`、
詳細 = `article-detail` + `ArticleBodySection` + 付随部品）。

### 4-6. 推奨

**`article-list` / `article-detail` を 7・8 番目のページ型として作ることを推奨する。**

根拠は 3 つ。

1. **フォーマット化の度合いが事例記事と同水準（一致率 95.0%、§3-4）。**
   しかも本数は事例記事より 1 桁多い。SmartHR Mag.・HR大学 の規模を考えると、
   **パターンとして配る効果は `case-study-detail` を上回る可能性が高い**
2. **既存型の拡張では済まないことが実測で確定した（§3-5）。**
   事例記事の中核 3 要素は News / ブログに 0/27、ブログの中核 4 要素は事例記事に 0/27。
   `CaseStudyDetailInput` の必須フィールドを optional に緩める破壊的変更を避けられる
3. **LP 末尾のコンテンツ回遊（`[LP]` 9/12）の遷移先が、現在このシステムに存在しない。**
   ContentHub（別トラック）が指す先を用意しないと、回遊セクションが宙に浮く

**ただし実装前に 1 つ埋めるべき穴がある。** 本調査は CSS の実測値を 1 つも持っていない（§1-1）。
`case-study-detail` の実装（`max-width: 46.5rem` / `h1` 32px / 章 `h2` 26px）を
そのまま流用する前提で進めるか、実ブラウザ計測が可能になった時点で
**ブログ記事の読み幅だけは測り直す**こと。ブログは本文が事例記事の 2 倍あり、
読み幅の影響が大きい。

```markdown
> - **年別アーカイブは News 6/7 / ブログ 0/7**、**ピックアップ枠は News 2/7 / ブログ 6/7** と
>   一覧のフィルタ軸も逆を向いている
> - **事例記事の中核（会社プロフィール・課題/決め手/効果サマリー・話者）は News / ブログに 0/27。**
>   逆にブログの中核（著者・目次・更新日・SNS シェア）は事例記事に 0/27。
>   **`case-study-*` の拡張では済まない**ことが実測で確定した
> - **作らないもの**も再確認された: 冒頭の数値タイルは
>   事例 0/27 + News 0/12 + ブログ 0/15 = **0/54**、無限スクロール **0/14 ページ**、
>   並べ替え UI 1/14、記事内サイドバー（ブログ 3/7・News 0/7）
> - サイト内一貫性は **95.0%**（事例記事の 97.6% とほぼ同水準）。
>   揺れたのは 3 箇所すべてが「解説記事 / インタビュー / 連載」という**記事の種類の差**であり、
>   同一テンプレート内の揺れではない
>
> **`[NB]` は CSS の実値（余白・フォントサイズ・読み幅）を含まない。**
> 環境の制約により実ブラウザ計測ができず、`WebFetch` による構造の読み取りで代替したため。
> 書式は `case-study-detail` の実装値を流用する前提で進める。
```

## 6. 新ページ型 型定義ドラフト

> **本セクションは提案であり、`packages/ui-web/src/` 配下は一切変更していない。**
> `CaseStudyListInput` / `CaseStudyDetailInput`（`src/patterns/define-landing-page.ts`）を手本に、
> 同じ流儀で各フィールドに実測根拠のコメントを付けた。
> **実測で確認できなかった項目は型に含めていない**（0 件だったことも根拠として明記する）。

```ts
/* ============================================================================
 * 共有の語彙（一覧カードと記事ヘッダの両方が参照する）
 * 実測 [NB]: 一覧 16 ページ / 記事 27 本。docs/research/research-news-blog.md
 * ========================================================================== */

/**
 * 記事の種類。一覧・詳細ともにこの判別子でパターンの振る舞いが変わる。
 *
 * 実測が示したのは「News とブログは同じ会社の中でも別テンプレート」という性質である。
 * 著者は News 0/12 / ブログ 14/15、目次は News 0/12 / ブログ 12/15、
 * 更新日は News 0/12 / ブログ 5/15。両方 optional の 1 型にすると
 * 「著者と目次を持つ News」という実測に存在しない構成が型で許されるため、
 * kind による判別ユニオンで分ける（case-study-detail の
 * 「選択肢はパターンのレベルで固定し、記事ごとには選ばせない」と同じ考え方）。
 */
export type ArticleKind = 'news' | 'blog';

/**
 * 記事のカテゴリ / タグ。一覧のフィルタ軸と記事のメタ表示で同じものを指す。
 *
 * 実測: ブログ記事 15/15・News 記事 8/12 がカテゴリを表示する。
 * 値を一覧のフィルタ URL へリンクさせる作りが多数（CaseStudyMeta と同じ性質）。
 */
export interface ArticleTaxonomy {
  label: string;
  /** 一覧のフィルタへのリンク。実測では値がリンクになっているサイトが多数 */
  href?: string;
}

/**
 * 記事の日付。
 *
 * 実測: 公開日は News 12/12・ブログ 15/15 で**必須**（事例記事は 6/27 だった。逆転している）。
 * 更新日はブログ 5/15（現場と人 3/3・お役立ちコラム 2/2）で、News は 0/12。
 * 書式は 4 通りに割れている（2026.07.07 / 2026-08-14 / 2025/12/19 / 2026年07月14日）ため、
 * **表示書式はシステム側が決めてよい領域**と判断する。値は ISO 文字列で受け取る。
 */
export interface ArticleDates {
  /** 公開日（実測 27/27。必須） */
  publishedAt: string;
  /** 更新日（実測 ブログ 5/15。News では型に存在しない） */
  updatedAt?: string;
}

/**
 * 記事のサムネイル / 本文画像。
 * alt は必須（CasePhoto / CaseStudyListItem.photo と同じ契約を守る）。
 *
 * 実測: 一覧のサムネイルは News 3/6・ブログ 5/7。
 * 本文画像は News 中央値 2.5 枚・ブログ 中央値 4 枚。
 */
export interface ArticleImage {
  src: string;
  alt: string;
}

/* ============================================================================
 * 一覧ページ（article-list）
 * ========================================================================== */

/**
 * 一覧のカード 1 件。
 *
 * 実測で 3 者（News / ブログ / 事例）のカードの語彙が違うことが確認された。
 * 事例カード（CaseStudyListItem）は会社名・数値バッジを持つが、記事カードは持たない。
 * そのため CaseCard を流用せず別の型にする。
 */
export interface ArticleListItem {
  /** 記事タイトル（実測: 全カードが持つ） */
  title: string;
  href: string;
  /** 日付（実測: 全カードが持つ。更新日を出すのは 1/14 = 現場と人のみ） */
  dates: ArticleDates;
  /** カテゴリ（実測: News 一覧 7/7・ブログ一覧 6/7 が軸として持つ） */
  category?: ArticleTaxonomy;
  /** サムネイル（実測: News 3/6・ブログ 5/7。無いサイトは 1 行リスト型になる） */
  thumbnail?: ArticleImage;
  /** 抜粋文（実測 3/14: カミナシ・Bizpedia・現場と人） */
  excerpt?: string;
  /**
   * 著者名（実測 1/14: SmartHR Mag. のみがカードに著者を出す）。
   * 少数派だが「カードに出す / 出さない」はメディア単位で固定されているため任意で持たせる。
   */
  authorName?: string;
}

/**
 * 一覧のフィルタ軸。
 *
 * 実測の軸の数: News 一覧 2〜3 軸 / ブログ一覧 1〜2 軸
 * （事例一覧 CaseStudyListInput の 4 軸より少ない）。
 * 軸の中身は News が「カテゴリ 7/7・年 6/7・製品/事業 5/7」、
 * ブログが「カテゴリ 6/7・業界/読者属性 2/7・年 0/7」で逆を向いている。
 * そのため軸の**名前は固定せず**、呼び出し側が渡す形にする。
 */
export interface ArticleFilterAxis {
  /** 軸の名前（例: 「カテゴリ」「年」「事業」「業界」） */
  label: string;
  options: ArticleTaxonomy[];
}

/**
 * ページネーション。
 *
 * 実測: 番号ページャ 4/14・「もっと見る」5/14・年タブのみ 1/14。
 * **無限スクロールは 0/14 なので型に含めない。**
 * 並べ替え UI は 1/14（LayerX のみ）なので含めない。
 * 検索ボックスは 2/14 なので含めない。
 */
export type ArticlePagination =
  | { type: 'pages'; current: number; total: number; hrefFor: (page: number) => string }
  | { type: 'load-more'; onLoadMore: () => void; hasMore: boolean };

/**
 * お知らせ / ブログの一覧ページ（実測 [NB] 16 ページ）。
 *
 * この型もヒーローを持たない（case-study-list / case-study-detail と同じ）。
 * キャッチコピー型ヒーローは News 0/7・ブログ 0/7 で 1 件も存在しない。
 *
 * `kind` により、パターンが決める見た目が変わる:
 * - `news`: 短いページタイトル型の見出し（実測 7/7）。ピックアップ枠は既定で出さない（2/7）
 * - `blog`: ブランド名 + タグライン型の見出し（実測 5/7）。ピックアップ枠を既定で出す（6/7）
 */
export interface ArticleListInput extends LandingPageCommon {
  pattern: 'article-list';
  kind: ArticleKind;
  /**
   * ページの見出し。
   * News は `title` に「ニュース」「お知らせ」等の短いラベル（実測 7/7）。
   * ブログは `title` にメディア名、`description` にタグライン（実測 5/7 がこの形）。
   */
  page: { eyebrow?: string; title: React.ReactNode; description?: string };
  /** フィルタ（実測: News 2〜3 軸 / ブログ 1〜2 軸）。軸ごと省略可 */
  filters?: ArticleFilterAxis[];
  /** 一覧本体。1 件以上 */
  items: [ArticleListItem, ...ArticleListItem[]];
  /**
   * ピックアップ / 人気記事枠（実測: News 2/7・ブログ 6/7）。
   * ブログでは事実上の必須だが、News では少数派のため任意にする。
   */
  featured?: ArticleListItem[];
  /** ページネーション（実測 9/14 が持つ。持たないサイトは全件表示） */
  pagination?: ArticlePagination;
  /** UI 語彙。既定は日本語 */
  labels?: ArticleListLabels;
  /**
   * 一覧末尾の導線（任意）。
   * hero が無く再利用できるオファーが存在しないため、actions は必須
   * （case-study-list と同じ扱い）。
   */
  closing?: Slot<CTASectionProps>;
}

/* ============================================================================
 * 記事ページ（article-detail）
 * ========================================================================== */

/**
 * 本文の章。実測: News 中央値 4 章・ブログ 中央値 6 章。
 *
 * 事例記事の CaseChapter と違い「章 1 つに写真 1 枚」の制約は置かない。
 * 実測でブログは画像 0〜14 枚と章数との相関が無く、
 * HR大学 のように 13 章で画像 4 枚という記事がある。
 */
export interface ArticleChapter {
  heading: string;
  /** 小見出し（実測: News 3/12・ブログ 13/15）。中央値はブログで 12 個 */
  subsections?: { heading: string; paragraphs: string[] }[];
  paragraphs?: string[];
  /** 章内の画像（枚数の上限は設けない。実測が 0〜14 で定まらないため） */
  images?: ArticleImage[];
}

/**
 * 著者。**ブログにのみ存在する**（実測: ブログ 14/15・News 0/12）。
 *
 * 顔写真は 3/15（SmartHR Mag. のみ）、
 * 「編集部」名義は 5/15、氏名 + 肩書き + プロフィール文は 8/15。
 */
export interface ArticleAuthor {
  /** 氏名または「◯◯編集部」（実測 14/15） */
  name: string;
  /** 肩書き（実測 8/15。「社会保険労務士」「ERPドメインリサーチャー」等） */
  title?: string;
  /** 顔写真（実測 3/15 = SmartHR Mag. のみ）。alt は必須 */
  photo?: ArticleImage;
  /** プロフィール文（実測 8/15） */
  bio?: string;
  href?: string;
}

/**
 * 監修者。**HR大学 のみが持つ**（実測 3/15、サイト単位では 1/7）。
 *
 * 少数派だが、専門領域の記事（人事・労務・会計）では
 * 有資格者による監修の明示が信頼性の要素になっており、
 * Polastack の想定領域でも同じ需要が出ると判断して型に含める。
 * **実測が 1 サイトのみである点は明記しておく。**
 */
export interface ArticleSupervisor {
  name: string;
  title?: string;
  bio?: string;
  href?: string;
}

/**
 * SNS シェア。**ブログ 15/15・News 8/12**。
 *
 * 実測の内訳: X/Twitter 15・Facebook 14・はてなブックマーク 9・LINE 3・Pocket 3・URLコピー 1。
 * 実測に無いもの（LinkedIn 単独・Instagram・メール共有）は含めない。
 */
export type ArticleShareTarget = 'x' | 'facebook' | 'hatena' | 'line' | 'pocket' | 'copy-link';

/**
 * 目次。**ブログにのみ存在する**（実測: ブログ 12/15・News 0/12）。
 *
 * 目次を持たない 3 本はすべてインタビュー / 連載型で、解説記事は 12/12 が持つ。
 * 深さは h2 のみ（5/12）と h2+h3（7/12）に割れるが、**メディア単位で固定**されている。
 * 記事ごとに選ばせないため、`depth` は article-detail のトップレベルに置く。
 */
export type ArticleTocDepth = 2 | 3;

/**
 * News 記事（実測 12 本）。
 *
 * 著者・目次・更新日を**型として持たない**。実測 0/12 であり、
 * optional にすると実測に存在しない構成が許されるため（§4-1）。
 */
interface NewsArticleBody {
  kind: 'news';
  /** 公開日のみ。更新日は実測 0/12 のため ArticleDates ではなく直に持つ */
  publishedAt: string;
  /** カテゴリ（実測 8/12） */
  category?: ArticleTaxonomy;
  /**
   * SNS シェア（実測 8/12）。省略すると出さない。
   * カミナシ 0/2・ANDPAD 0/2 のように持たないサイトが実在する。
   */
  share?: ArticleShareTarget[];
}

/**
 * ブログ記事（実測 15 本）。
 */
interface BlogArticleBody {
  kind: 'blog';
  /** 公開日 + 任意の更新日（実測: 公開日 15/15・更新日 5/15） */
  dates: ArticleDates;
  /** カテゴリ（実測 15/15。必須） */
  category: ArticleTaxonomy;
  /** カテゴリとは別のタグ（実測 8/15） */
  tags?: ArticleTaxonomy[];
  /** 著者（実測 14/15）。mimi のみ持たないため必須にはしない */
  author?: ArticleAuthor;
  /** 監修者（実測 3/15 = HR大学 のみ） */
  supervisor?: ArticleSupervisor;
  /**
   * 目次の深さ（実測 12/15 が目次を持つ。h2 のみ 5 / h2+h3 7）。
   * 省略すると目次を出さない（インタビュー / 連載型の 3/15 がこれ）。
   */
  tocDepth?: ArticleTocDepth;
  /** SNS シェア（実測 15/15。必須に近いが、既定値をパターンが持つ形にする） */
  share?: ArticleShareTarget[];
}

/**
 * お知らせ / ブログの記事ページ（実測 [NB] News 12 本 + ブログ 15 本 = 27 本。
 * docs/research/research-news-blog.md）。
 *
 * `article-list` の遷移先で、この型もヒーローを持たない。
 * パンくず → タイトル → 日付・カテゴリ → [著者] → [目次] → 章 → 関連記事 → 一覧へ戻る、
 * という順序はパターンが決める。
 *
 * 実測が示したのは「メディア単位 × 記事の種類単位で構成が固定（一致率 95.0%）、
 * News とブログのあいだでは共通点が骨格しか無い」という性質である。
 * そのため kind による判別ユニオンにし、**記事ごとに構成を選ばせない**。
 */
export type ArticleDetailInput = LandingPageCommon & {
  pattern: 'article-detail';
  article: {
    /** 記事タイトル（実測 27/27。必須） */
    title: string;
    /** 一覧への戻り導線（実測 News 10/12・ブログ 11/15）。事例記事と違い必須にしない */
    backTo?: { label: string; href: string };
    /** リード文（実測 News 10/12・ブログ 13/15） */
    lead?: string;
    /** アイキャッチ画像（実測: 一覧のサムネイルと同一のことが多い） */
    hero?: ArticleImage;
  };
  /** 本文。最低 1 章（実測の最小が 1 章 = Bizpedia 猫経理）。中央値 News 4 / ブログ 6 */
  chapters: [ArticleChapter, ...ArticleChapter[]];
  /**
   * 関連記事（実測 News 10/12・ブログ 14/15。3 件が最頻）。
   * 一覧のカードをそのまま使う。複数セクションへの分割（6/15）は作らない（§4-3）。
   */
  related?: ArticleListItem[];
  /**
   * 末尾 CTA（実測 News 7/12・ブログ 11/15）。
   * **事例記事（27/27）と違い必須にできない。**
   * SmartHR ニュース 0/3 のように末尾 CTA を持たない運用が実在する。
   */
  closing?: Slot<CTASectionProps>;
  /** UI 語彙（パンくず・目次・著者・関連記事の見出しほか）。既定は日本語 */
  labels?: ArticleDetailLabels;
} & (NewsArticleBody | BlogArticleBody);

/* ============================================================================
 * ラベル（バイリンガル対応。CaseStudyArticleLabels と同じ流儀）
 * ========================================================================== */

/**
 * 一覧の UI 語彙。
 * 実測で「もっと見る」「もっとみる」「load more」「新着記事一覧を見る」と
 * 同じ機能に 4 通りの文言があり、正規化できない。すべて Props で注入する。
 */
export interface ArticleListLabels {
  /** 既定「もっと見る」 */
  loadMore?: string;
  /** 既定「ピックアップ」。実測: 「トピックス」「PICK UP」「人気記事」「人気の記事」 */
  featured?: string;
  /** 既定「すべて」。実測: 「ALL」「すべて」「全て」 */
  filterAll?: string;
  /** 既定「前へ」/「次へ」 */
  prevPage?: string;
  nextPage?: string;
}

/**
 * 記事の UI 語彙。
 *
 * 関連記事の見出しは実測で 12 通りに割れている
 * （「あわせて読みたい」「おすすめ記事」「最新記事」「人気記事」「関連する記事」
 *  「関連ニュース」「最新のお知らせ」「OTHER INFORMATION その他のお知らせ」ほか）。
 * **ハードコードできない典型例。**
 */
export interface ArticleDetailLabels {
  /** 既定「目次」（blog のみ） */
  toc?: string;
  /** 既定「公開日」 */
  publishedAt?: string;
  /** 既定「更新日」（blog のみ） */
  updatedAt?: string;
  /** 既定「執筆者」（blog のみ）。実測: 「執筆者」「著者」表記なしの 3 通り */
  author?: string;
  /** 既定「監修者」（blog のみ） */
  supervisor?: string;
  /** 既定「この記事をシェア」 */
  share?: string;
  /** 既定「関連記事」。実測 12 通り（上記） */
  related?: string;
  /** 既定「一覧に戻る」。実測: 「ニューストップへ戻る」「お知らせ一覧に戻る」「VIEW ALL」「TOPへ」 */
  backToList?: string;
}
```

### 6-1. `DEFAULT_TONES` への追加
