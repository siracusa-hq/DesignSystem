# Eyebrow（セクション見出し上の小ラベル）実態調査 — 国内BtoB SaaS の「セクションの区切り方」

対象: 日本のBtoB SaaS の **Web / LP 面のみ**（`@siracusahq/gtm-design-system` 側）。
母集団は [LP アナトミー調査](./research-lp-anatomy.md) / [中間CTA帯調査](./research-cta-band.md) と同じ核。

調査日: 2026-08-10
調査手法: **ヘッドレス Chromium（Playwright）による実レンダリング**での DOM + `getComputedStyle` 実測。
curl による生 HTML / CSS 取得を補助に使用。

## 0. 調査の動機

`SectionHeader` は Eyebrow（見出し上の小ラベル）を持てる。現行実装は

```css
/* packages/ui-web/src/components/primitives/eyebrow/eyebrow.module.css */
.eyebrow {
  display: inline-flex;
  border-radius: var(--radius-pill); /* 9999px = 完全なピル */
  padding: var(--spacing-1) var(--spacing-3); /* 4px 12px */
  font-size: var(--text-body-sm); /* 0.875rem = 14px */
  font-weight: 500;
  letter-spacing: 0.04em;
  color: var(--color-text-brand); /* corporate-500 #008575 */
  background: color-mix(in srgb, var(--color-text-brand) 10%, transparent);
}
```

```css
/* section-header.module.css */
.header {
  margin-bottom: var(--spacing-12);
  text-align: center;
} /* 48px・常に中央 */
.eyebrowRow {
  display: flex;
  justify-content: center;
  margin-bottom: var(--spacing-4);
} /* 16px */
```

ストーリーの実例は `FEATURES` / `PRICING` / `CASE STUDIES` / `MODULES` / `BY THE NUMBERS` など
**英語ラベルをほぼ全セクションに**置く構成になっている
（`src/stories/` での `eyebrow=` 指定 44 箇所・ラベル文字列は 40 種類超。
`src/components/sections/` の 17 部品が `eyebrow` プロップを透過している）。

ブランドオーナーからの問いは2つ。

1. セクション区切りで eyebrow を使う構成は、一般的な BtoB サイト・LP で本当に一般的なのか
2. eyebrow 以外に、セクション見出しの区切り方としてどのような手法が有効か

## 1. 手法と限界（先に読むこと）

### 1-1. 前2回の調査からの手法の変更点

`research-lp-anatomy.md` / `research-cta-band.md` は「**ブラウザレンダリングはしていない**」を最大の限界として明記していた。
今回は**その制約を外している**。リポジトリの VRT 用に導入済みの Playwright + Chromium
（`node_modules/.pnpm/@playwright+test@1.62.1`、`~/.cache/ms-playwright/chromium-1234`）が
外部ネットワークに到達できることを確認したため、実ブラウザで各ページを開いて計測した。

これにより、前回まで判定不能だったものが取れている。

- **CSS カスケードの最終的な勝敗**（メディアクエリ・詳細度を含めた実効値）。1440×1000 の PC ビューポートでの確定値
- **疑似要素（`::before` / `::after`）の実寸とレイアウト上の位置**。飾り線の検出はこれが無いとできない
- **要素の実際の座標・寸法**。「見出しの真上に何があるか」を DOM 構造ではなく**幾何学的に**判定できる
- **Cloudflare 配下のマネーフォワード**。前2回は curl 403 で構造しか取れなかったが、今回は実ブラウザで完全取得できた
- **スクリーンショット**。4サイトについて見出し周辺を切り出して目視確認した

### 1-2. 事実として記録したもの

- 各ページを 1440×1000 で開き、`networkidle` 待機 → **ページ全体を 600px 刻みでスクロール**（IntersectionObserver 起点の
  フェードイン演出で `opacity: 0` のままになる要素を可視化するため）→ 先頭に戻して計測
- 見出しとその周辺要素の `getComputedStyle` 実値（`font-size` / `font-weight` / `letter-spacing` /
  `text-transform` / `color` / `background-color` / `border-radius` / `padding` / `display` ほか）
- 疑似要素の `content` / `width` / `height` / `background-color` / `position` / `margin`
- 要素の `getBoundingClientRect()` によるページ絶対座標
- コントラスト比は WCAG 相対輝度式で実際に計算した

### 1-3. セクションの数え方（この調査の定義）

「セクション単位で数える」ためには、まずセクションを機械的に定義する必要がある。次の手順を全ページに同一に適用した。

1. `body` 配下の全要素から、**幅 ≧ ビューポート幅の 88%** かつ **高さ 150px 以上** かつ
   **高さ ≦ ページ全高の 85%** を満たすものを集める（= ページ幅いっぱいの大ブロック）。
   `header` / `footer` / `nav` / 対応する ARIA ロールの配下は除外する
2. その集合の要素を最も多く直接の子に持つ要素を**セクションコンテナ**とし、その直接の子で 1 の条件を満たすものを
   **セクション**とする
3. 各セクション内で最初に現れる可視の `h1` / `h2` / `h3` を、そのセクションの**セクション見出し**とする
4. 見出しを1つも含まないセクション（FV のビジュアルのみ、CTA帯、ロゴ帯など）は eyebrow の分母から外す
5. **ヒーロー（ページ先頭の、`h1` を含むセクション）も分母から外す**。
   ヒーロー内のバッジは役割が違うため §3-6 で別に集計する

この手順が破綻したのは 2 ページ（後述の freee人事労務・HRBrain）で、そこだけ
セクションのセレクタを手で指定して再計測した。**手で指定した事実はサイト記録に明記している。**

### 1-4. eyebrow の判定方法

セクション見出しに対して、次の2系統で候補を拾い、両方を記録した。

- **見出しの内側（inner）**: 見出しの子孫のうち、最大フォントサイズの子孫（= 実際のタイトル行）の
  **0.75 倍以下**のフォントサイズで、タイトル行より上に描画され、40 文字以下のもの
  （例: ANDPAD・freee人事労務・Chatwork のヒーローがこの形）
- **見出しの上（above）**: 同一セクション内で、タイトル行の上端から **140px 以内**に下端があり、
  水平方向に重なりがあり、40 文字以下で、テキストを持つ子要素を持たない要素。
  テキストが無くても「高さ 10px 以下・幅 360px 以下」なら**飾り線**、
  `img` / `svg` で 96px 以下なら**アイコン**として拾う

拾った候補のうち「セクションの内容を指す短いラベル」に当たるものを eyebrow と判定した。
**この最終判定だけは筆者の解釈である。** 判定が割れうるもの（freee会計の説明文型など）は
§3-3 で形を分けて記録し、集計でも分けている。

### 1-5. 推測・未検証として区別したもの

- 計測は **PC 1440px 幅の1ブレークポイントのみ**。SP でラベルが消える／出る可能性は検証していない
- ページ内の位置（%）は**レンダリング後の Y 座標**の百分率。前2回の「HTML ソースのバイト位置」より正確だが、
  スクロールで遅延挿入される要素の影響は残る
- 「eyebrow が無い」は**この1回のレンダリング結果に無い**という意味。A/B テスト・出し分けは排除できていない
  （freee会計には `ab-accounting-top__select test-a` というクラスが実際に残っている）
- ダークモードは調査対象外。国内BtoB LP はいずれもライト固定で、`prefers-color-scheme` 対応を確認できていない
- **「その形が良いか」は測っていない。** 測ったのは「何が、どれだけ、どういう値で使われているか」だけ

#### 3-4-1. コントラストの実測（この節は設計上の欠陥の指摘）

`background: color-mix(in srgb, #008575 10%, transparent)` は、白面の上で **`#e6f3f1`** に解決される。

| 組み合わせ                                                 | コントラスト比 | WCAG AA（14px / 500 = 通常テキスト、4.5:1 必要） |
| ---------------------------------------------------------- | -------------: | ------------------------------------------------ |
| チップの面 `#e6f3f1` vs 白面                               |     **1.14:1** | （面としてほぼ見えない）                         |
| **ラベル文字 `#008575` on `#e6f3f1`**                      |     **4.00:1** | **不適合**                                       |
| ラベル文字 `#008575` on 白（チップ無しの場合）             |         4.55:1 | 適合                                             |
| チップの面 `#e1eeed` vs `--color-surface-sunken` `#fafafa` |         1.14:1 | （沈んだ面でも同じく見えない）                   |
| **ラベル文字 `#008575` on `#e1eeed`（沈んだ面の上）**      |     **3.83:1** | **不適合**                                       |

**10% のティントは、チップとしては見えない（1.14:1）のに、文字のコントラストだけは 4.55 → 4.00 に削っている。**
`#008575` が「500 単独で白文字 4.55:1 を満たし WCAG AA 適合」（`CLAUDE.md`）であることを前提に選ばれた色なのに、
自分で敷いた背景でその前提を壊している。

`CLAUDE.md` が警告しているとおり、**jsdom 上の axe-core は色計算ができないためこれを検出できない。**
`eyebrow.test.tsx` の `axe` は通っているが、それは根拠にならない。

eyebrow を 1 つも使わない 7 サイトについて、**何で区切っているか**を並べる。

我々の現行構成（36px 見出し・96px 余白・1.044:1 の面交替）に最も近い。

### 案A: 現行維持 + 書式だけ実測に寄せる（最小差分）

Eyebrow を全セクションに置く運用は変えず、形と書式だけ直す。

```css
.eyebrow {
  display: inline-flex;
  align-items: center;
  gap: var(--spacing-2);
  /* border-radius / background / padding を削除 */
  font-size: var(--text-body-lg); /* 14px → 18px（実測中央値） */
  font-weight: 700; /* 500 → 700（実測中央値） */
  letter-spacing: 0.01em; /* 0.04em → 0.01em（実測中央値） */
  color: var(--color-text-brand); /* 白面で 4.55:1 = AA 適合 */
}
```

**対応する実測**: freee人事労務（7/7・20px/700/ブランド色/背景なし）、
Bill One（20px/700/ブランド色）、kintone（18px/700/背景なし）。
= §3-3 の「素テキストのみ」11 + 「素テキスト+図形」5 = **16 / 31（52%）が背景を持たない形**。

**トレードオフ**

- ✅ 変更範囲が最小。`eyebrow.module.css` の 5 行と、ストーリーのラベル文言だけ
- ✅ コントラスト不適合（4.00 → 4.55:1）が即座に解消する
- ✅ ピル型という「CTA 肩コピーの記号」との衝突が消える
- ❌ **設問1に答えていない。** 「全セクションに置く」構成は実測 23% のままで、
  ブランドオーナーの問い（本当に一般的なのか）に対する回答が「一般的ではないが続ける」になる
- ❌ 英語ラベル運用の是非（`FEATURES` を日本語にするか）を先送りする
- ❌ 飾り線という語彙が引き続き無い

### 案B: eyebrow を縮小し、飾り線（Rule）を既定の区切りにする — **推奨**

`SectionHeader` の既定を「見出し + 余白 + 短い飾り線」に変え、**eyebrow は明示的に指定したときだけ出す**。

```css
/* section-header.module.css — 既定で見出しの上に短い棒を置く */
.rule {
  width: 4.5rem; /* 72px。実測 56〜100px の中央 */
  height: 0.3125rem; /* 5px。実測 4〜7px の中央 */
  border-radius: var(--radius-pill);
  background: var(--color-text-brand); /* ブランド色。文字ではないのでコントラスト要件の対象外 */
  margin-bottom: var(--spacing-6); /* 24px。Chatwork 30px / MF は下置き */
  margin-inline: auto; /* 中央寄せ時。左寄せ時は 0 */
}
```

```css
/* eyebrow.module.css — 案A と同じ素テキスト化 */
.eyebrow {
  font-size: var(--text-body-lg); /* 18px */
  font-weight: 700;
  letter-spacing: 0.01em;
  color: var(--color-text-brand);
}
```

運用ルール（ストーリーとドキュメントに書く）:

1. **既定は飾り線のみ。** eyebrow は置かない
2. eyebrow を置くのは「セクション名が見出しから読み取れない」場合だけ（実測の freee会計型 = 訴求の山のみ）
3. eyebrow を置くなら**日本語**。英語ページ（`English/Product` トーン）でのみ英語 Title Case
4. **`FEATURES` のような全部大文字は使わない**（実測 0 件）
5. CTA セクション・暗面セクションには eyebrow を置かない（実測の除外規則と一致）

**対応する実測**

- 飾り線: Chatwork（6/6）、Bill One（6/6）、MF（4/4）、ANDPAD（7/7 縦罫）= **4 / 13 サイト、適用率はいずれも 100%**
- eyebrow なしでの成立: SmartHR / カミナシ / ANDPAD / Chatwork / MF / HRBrain / LayerX = **7 / 13（54%）**
- 素テキスト eyebrow: 16 / 31
- **飾り線 + eyebrow なし + 中央寄せ + ブランド色の棒** の組み合わせは、マネーフォワードがそのまま実施している
  （32px 中央見出し・100×4px `#0054ac` の下棒・80px 余白・面の交替 `#f2f5ff`）

**トレードオフ**

- ✅ **設問1・2の両方に答える。** 「一律 eyebrow は少数派（23%）」という実測に運用を合わせ、
  空いた席に実測 100% 適用の手法（飾り線）を入れる
- ✅ 飾り線は**文字を持たないので翻訳・語彙統一の運用コストがゼロ**。
  現状 65 箇所ある `eyebrow=` のラベル文言（`Features` / `機能詳細` / `MODULES` が混在）を管理し続けなくてよい
- ✅ ブランド色を「文字色」ではなく「図形の塗り」として使うため、コントラスト要件から外れる。
  `#008575` を彩度そのままで使える
- ✅ 中央寄せ・左寄せの両方に同じ部品で対応できる（`margin-inline: auto` / `0`）
- ✅ VRT の検知力が上がる。棒は面より輪郭が明確で、ピクセル差分に出やすい
- ❌ **飾り線を採用している国内サイトは 4 / 13（31%）で、eyebrow（46%）より少ない。**
  「より一般的な手法に乗り換える」わけではない。乗り換える理由は頻度ではなく
  「適用率が 100% で運用がぶれない」「文字を持たない」という性質のほう
- ❌ SectionHeader に「棒を出す / 出さない」の分岐が増える。形の選択肢を持たない（`Eyebrow` の docstring）
  という現行の設計思想と、部分的に衝突する
- ❌ **VRT 基準の更新が必要。** `packages/ui-web/vrt/__screenshots__/{desktop,mobile}/` の

- ❌ ダークモードでの棒の色（`--color-text-brand-on-dark` = corporate-300）を別途決める必要がある

### 推奨: **案B（eyebrow を縮小し、飾り線を既定の区切りにする）**

#### 根拠1: 設問1への答えが運用に反映される

- eyebrow をセクション区切りに一律で使う構成は、**国内 13 ページで 3 ページ（23%）**。
  セクション単位では 31 / 86（36%）。**「一般的」とは言えない**
- 現行のストーリー構成（ほぼ全セクションに英語ラベル）は、実測の少数派 23% を、
  さらに**実測 0 件の形（ピル + ブランド色ティント）と実測 0 件の書式（全部大文字）**で実装したもの
- 案A（書式だけ直す）は形の問題を解くが、**構成の問題を解かない**。
  案C（廃止）は構成の問題を解くが、**逃げ道を残さない**

#### 根拠2: 飾り線を選ぶ理由は「頻度」ではなく「性質」

飾り線・縦罫の採用は 4 / 13（31%）で、eyebrow（46%）より少ない。**頻度では劣る。**
それでも推す理由は 3 つ、いずれも実測から出ている。

1. **適用率がほぼ 100%。** 飾り線を採用した 4 サイトは、Bill One 6/6・MF 4/4・ANDPAD 7/7・Chatwork 6/7 と、
   ほぼ例外なく置いている。一方 eyebrow は kintone 5/7・freee会計 3/6 のように**揺れる**。
   デザインシステムの部品としては、揺れない語彙のほうが扱いやすい
2. **文字を持たない。** 現状 44 箇所の `eyebrow=` には
   `FEATURES` / `機能詳細` / `MODULES` / `モジュール` / `BY THE NUMBERS` / `実績` /
   `DEVELOPER EXPERIENCE` / `デベロッパーエクスペリエンス` / `デベロッパー体験` が混在している
   （同じ概念に対して英日 2 通り、さらに日本語だけで 2 通りの訳がある）。
   これは「英語か日本語か」「Feature か Function か」を毎回決める運用コストで、
   実測でも Stripe が日本語版で eyebrow を翻訳し直しているとおり、多言語では二重に効いてくる。棒にはこれが無い
3. **ブランド色を安全に使える。** ブランド色を文字色として小さな面の上に置くと 4.00:1 で AA を割るが、
   図形の塗りとして使えばコントラスト要件の対象外になる。
   実測の 3 サイト（Chatwork `#f03748` / Bill One `#0075b5` / MF `#0054ac`）はいずれも棒にブランド色を使っている

#### 根拠3: 実装済みの部分は触らなくてよいことが確認できた

- **セクション余白**: `--spacing-section-md: 6rem = 96px` は実測中央値 96〜104px に一致。**変更不要**
- **見出し→リードの距離**: `margin-top: 16px` は実測 12〜32px の範囲内。**変更不要**
- **中央寄せ**: 国内 61% が中央寄せ。既定として妥当。**変更不要**（ただし左寄せの選択肢は将来課題）

#### 実装時に必ず併せて行うこと

| 項目                                                                                          | 理由                                                                                         |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `border-radius: 9999px` + `background: color-mix(...)` の削除                                 | ピル型 eyebrow の実測 0 / 41。かつ文字コントラストを 4.55 → 4.00:1 に削っている              |

## 7. 判断できなかったこと・残課題

1. **「その形が良いか」は測っていない。**
   本調査が答えたのは「何が、どれだけ、どういう値で使われているか」だけ。
   飾り線が eyebrow より**良い**という証拠は無い。あるのは「適用率が安定していて、文字を持たない」という性質だけ。
   案B を採る場合、Netlify のデプロイプレビューでの目視が必須。

2. **PC 1440px の 1 ブレークポイントしか測っていない。**
   SP で eyebrow が消える／小さくなる、飾り線の寸法が変わる、といった分岐は未検証。
   バクラクの `tab:` プレフィックス、freee の `-md` サフィックスから、
   少なくとも 2 段階のブレークポイントを持つことは判っているが、値は追っていない。

3. **セクションの数え方は 1 つの定義に過ぎない。**
   §1-3 のアルゴリズム（幅 88% 以上・高さ 150px 以上のブロック）は、
   ラッパーの入れ子が深いサイト（freee人事労務・HRBrain）で失敗し、手で補正した。
   別の定義を採れば分母は前後する。**比率の小数点以下は信用しないこと。**
   ただし「一律 eyebrow は 3 / 13 サイト」という**サイト単位の結論は定義に依存しない。**

4. **eyebrow か否かの最終判定は筆者の解釈。**
   特に freee会計の「他社にはないfreeeの強み」は、カテゴリラベルではなく説明文であり、
   「eyebrow」と呼ぶかは判断が割れる。§3-3 で形を分けて記録してあるので、
   別の判定を採る場合は 3 件を差し引いて読み直せる。

5. **A/B テスト・出し分けを排除できていない。**
   freee会計には `ab-accounting-top__select test-a` というクラスが実際に残っている。
   1 回のレンダリング結果しか見ていないため、別のバリアントで eyebrow の有無が変わる可能性がある。

6. **ダークモードは対象外。**
   国内 BtoB LP はいずれもライト固定。我々の `.dark .eyebrow` は
   `--color-text-brand-on-dark`（corporate-300）の 10% ティントを敷いており、
   **暗面でのコントラストは今回計算していない。** 案を実装する際に別途計算すること。

7. **事例詳細ページ（case-detail）・獲得LP（lead-gen）は未調査。**
   今回は product / product-portfolio-top / corporate のみ。
   ページ型によって eyebrow の必要性が違う可能性がある（`case-study-list` は §2 の母集団に無い）。

8. **飾り線の「上に置くか下に置くか」の判断材料が薄い。**
   実測は上 1（Chatwork）/ 下 2（Bill One・MF）/ 左 1（ANDPAD）で、母数が小さすぎて傾向と呼べない。
   案B では「上・24px」を提案したが、これは Chatwork の 30px に寄せた仮の値である。
