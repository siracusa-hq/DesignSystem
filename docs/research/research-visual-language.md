# 国内BtoB企業 Web/LP ビジュアル言語・和文組版 調査

調査日: 2026-08-02 / 対象: Web・LP・マーケティングコミュニケーション

## 0. 調査方法と、事実／推測の区別について

**一次情報の取り方**

- 各社のサイトの**生HTMLとCSSを curl で実際にダウンロードし**、`font-family` / `line-height` / `letter-spacing` / `font-feature-settings` / `text-wrap` を機械的に抽出した。この方法で得た数値は**実測値**であり、以下では出典URLを併記する。
- ヒーローのビジュアルは、**画像ファイルを実際にダウンロードして目視確認**した。SVGは `magick` でラスタライズして確認した。以下「目視確認」と書いたものはこれを指す。
- STUDIO製のサイト（HQ・ナレッジワーク・カミナシ）は、Nuxt のペイロード JSON に**名前付きテキストスタイル定義がそのまま埋まっていた**ため、社内デザイントークンに相当するものを完全な形で取得できた。これは実測値というより**制作者が定義した設計値そのもの**であり、本調査で最も価値の高いデータである。
- 公開デザインシステム文書は**補助情報**として扱う。各知見に `[ブランド/マーケ由来]` `[プロダクトUI由来]` のラベルを付け、後者は結論から除外する。

**限界（重要）**

- CSS の静的解析であるため、**「その値が実際にヒーローの見出しに効いているか」までは断定できない**場合がある。出現回数を併記して支配的な値を示すにとどめた箇所は、その旨を明記した。
- **ブラウザを起動してのレンダリング確認はしていない。** 影・角丸・傾きなどの処理は、ダウンロードした画像そのものの観察に基づく。
- 取得に失敗したものは第7章に列挙した。**捏造はしていない。**

**スクリーンショットの処理手法（3タイプに分かれる）**

1. **読ませる／デバイスに入れる** — カミナシ、freee。実機ベゼルあり、ブラウザ枠なし、正対（傾きなし）、影は控えめ。
2. **読ませない／解体してテクスチャにする** — バクラク。UIを断片化して半透明パネルにし、地の色に沈める。
3. **ヒーローには出さない** — SmartHR（下部バナーへ）、LayerX、ナレッジワーク、HQ、Sansan。

**今回の8社で「傾き・パース付きのスクリーンショット」を使っていた社はゼロ。** 全て正対か、解体か、不使用だった。

## 4. (C) 「アーキテクチャ図・コードを主役にする」という仮方針の位置づけ

**結論: 今回調べた8社の中に、アーキテクチャ図やコードをヒーローの主役に据えている社は1社も無かった。空白地帯である。ただし、その空白には理由がある可能性が高く、無条件に「先行者利益がある」とは言えない。**

### 4-1. 事実: 図解はどこに置かれているか

**図解（ダイアグラム）自体は複数社が使っているが、例外なくヒーローの下に置かれている。**

- **SmartHR**: 機能連携の図解を `img_a-1_007_pc.webp`（2048×460）・`img_a-1_008_pc.webp`（2240×992）として持っている。`alt` に「SmartHRは、労務管理、給与計算、勤怠管理、タレントマネジメント、情シスソリューションなどの機能が、従業員ポータルと従業員データベースに連携。…」と図解の内容が全文書かれており、**明確に構造説明の図**である。だがこれは**ヒーローではなく下部セクション**にあり、しかも**画像化**されている。
- **freee**: `motif01_accounting.svg` 〜 `motif08_launch.svg` の**モチーフSVG体系**を持つ。全て viewBox 180×180 統一・2色・プリミティブ図形のみ。ただしこれは**サービス領域を表す抽象記号**であって、要素間の関係を示すアーキテクチャ図ではない。
- **Sansan**: KVのイラスト内に、名刺・データベース・グラフ・人物の関係が**線画のなかに溶かし込まれている**。図解に近いが、図解の体裁（矢印・ラベル・ボックス）は取らず、イラストとして描かれている。
- **HQ**: アイソメトリック図は福利厚生カテゴリの**列挙**であって、構造の説明ではない。

### 4-2. 事実: 「主役ビジュアルとしてのUI」に最も近い実例

**バクラクの現行KV（2026-08-02 時点）が、依頼元の仮方針に最も近い。**

濃紺のベタ地に、申請フォーム・入金テーブル・請求一覧・グラフ・承認者カードといった**プロダクトUIの断片を半透明のガラス状パネルとして散りばめ、文字が読めない密度まで沈めてテクスチャ化している**。これは「スクリーンショットを見せる」でも「イラストを描く」でもなく、**システムの構成要素そのものを画面全体の地紋にする**というアプローチであり、「アーキテクチャ図・コードを主役にする」と発想の系統が同じである。

**参考価値が高いのは、その処理の作法**:

- UIを**読ませないところまで低コントラストに落としている**（可読性を捨てて、密度と構造感だけを残す）
- **地の色を1色の濃い面に統一**し、UI断片はその上の明度差だけで表現
- 中央に**1つだけ強い焦点**（発光するアプリアイコン）を置いて視線を止める
- 左半分に**写実的な紙の帳票**を配置し、「紙 → デジタル」の対比を作る＝抽象UIだけでは意味が伝わらないため、**具象物とペアにしている**

### 4-3. 空白である理由の整理（事実と推測を区別）

**事実として観察されたこと**

1. 今回の8社は**すべて非エンジニア向けの水平SaaS**（経理・人事・労務・営業・現場）である。買い手が技術者ではない。
2. **写真派とイラスト派の判断根拠を明文化している2社（freee・バクラク）は、いずれも「わかりやすさ／自分ごと化」を理由に挙げている。**
   - freee: 「スモールビジネスが主なユーザーであるため、サービスの分かりやすさや親しみやすさは重要」（Takram）
   - バクラク: 人物ありの写真は「自分ごと化しやすくなる」（note、PJ③）
3. **一貫性の担保を語った一次情報も、いずれも「誰でも作れること」を軸にしている。**
   - freee: 「誰でも新規にイラストを作成できるよう構造がシステム化」／判断軸は「だれでも使えるのか」
   - バクラク: 「背景と服の色を統一し、各サービスの違いを出しながら一貫性を出す」
4. **図解は存在するが、必ずヒーローより下にある**（4-1）。

**ここから言えること（推測であることを明記）**

- ヒーローに求められる機能が「**構造の説明**」ではなく「**自分ごと化と情緒的な接続**」であるために、図解が下位に置かれている、と解釈できる。**これは推測である。** 各社が「図解をヒーローに置かない」と明示的に述べた一次情報は見つかっていない。
- したがって「アーキテクチャ図・コードを主役にする」方針は、**買い手が技術者である（あるいは技術的な構造の理解が購買判断に直結する）場合には有効な差別化になりうるが、非技術者向けの水平SaaSでは、各社が意図的に避けている可能性がある**。**これも推測である。**
- なお、今回の調査対象には**開発者向けインフラ／API系の企業が1社も含まれていない**。この領域では図解・コードをヒーローに置く例が国内外に存在する可能性が高いが、**本調査では確認していない。**「空白地帯」という判定は、**あくまで今回調べた非エンジニア向けBtoB SaaS 8社の範囲での話**である。

### 4-4. 仮方針を採る場合に、実例から借りられる作法

観察された事実から、直接転用できる具体策は以下。

1. **図解を主役にするなら、必ず具象物とペアにする。** バクラクは抽象UI断片に写実的な紙帳票を組み合わせ、freee は申告フォームのスクショに3D風の風船・マスコットを添えている。**抽象だけで押し切っている社は無い。**
2. **主役デバイスは1種類に絞ったほうが強い。** ナレッジワーク（タイポのみ）、HQ（アイソメのみ）、カミナシ（デバイスモックアップのみ）は明確に1種類。4種混在の freee は、その代わり**モチーフSVGだけは viewBox 180×180 統一・2色・幾何形状のみ**という強い規律を敷いて破綻を防いでいる。**混在させるなら、少なくとも1系統には数値レベルの規律を持たせる。**
3. **図解を画像化するか、CSS/SVGで実装するかを先に決める。** SmartHR は図解を画像化し、`alt` に全文テキストを入れることでアクセシビリティを担保している（`alt` が数百字ある）。**図解を主役にするならこのコストを織り込む必要がある。**
4. **傾き・パースは使わない。** 今回の8社で傾けたスクリーンショットはゼロ。カミナシ・freee とも正対。
5. **見出しの組版は 1.3〜1.4 / 字送りは 0 か正の値。** 図解が主役でも、隣に置く見出しはこの範囲に収まる。負の字送りは1社も使っていない。

## 5. 依頼元のデザインシステムへの含意（数値の候補レンジ）

事実の整理から直接導ける範囲のみ記す。判断は依頼元に委ねる。

- **見出しの行間**: 1.3〜1.4。実サイト6社が収束しており、デジタル庁の Display 規定（140%）とも一致する。
- **本文の行間**: 1.6〜1.75。デジタル庁の「一般的なウェブサイトの本文」（160%）〜「心理的負荷の軽減」（170〜175%）と、実サイトの中央値（Sansan 1.6〜1.8、バクラク 1.75）が重なる帯。LayerX の 1.9 は最外れ値。
- **字送り**: 見出し 0 〜 +.05em、本文 0 〜 +.02em。**負の値は使わない**（8社中0社）。**ウェイトで補正するなら、ナレッジワークの「Regular +.04em / Bold +.03em」が唯一の体系的な先行例。**
- **`palt`**: 全面適用（LayerX）と見出しのみ（ナレッジワーク）の2択。**本文にまで効かせるかを明示的に決める必要がある。** ナレッジワークが本文に付けない選択をしているのは意図的。
- **`text-wrap`**: 先行例なし。8社中0社。採用するなら国内BtoBでは先行事例のない領域になる。
- **`text-spacing-trim: space-all` / `line-break: strict`**: SmartHR のみ。`palt` に依存しない和文組版の作り込みとして、唯一の先行例。
- **本文14px未満**: デジタル庁が「原則として許容されない」と明記。freee a11y ガイドラインのコントラスト規定（24px以上または19px以上の太字は3:1、それ以外は4.5:1）と併せて、下限の根拠として使える。
