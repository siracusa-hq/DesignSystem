# 事例記事（case-study-detail）フォーマット実測調査 — 国内BtoB SaaS の「量産される記事」の型

対象: 日本のBtoB SaaS の **Web / LP 面のみ**（`@siracusahq/gtm-design-system` 側）。
母集団は [LP アナトミー調査](./research-lp-anatomy.md) / [中間CTA帯調査](./research-cta-band.md) /
[Eyebrow 調査](./research-eyebrow.md) と同じ核。

調査日: 2026-08-13
調査手法: **ヘッドレス Chromium（Playwright）による実レンダリング**での DOM + `getComputedStyle` 実測。

## 0. 調査の動機

`composition-redesign.md` §3-1 は、ページ型5種を定めたうえでこう書いて保留している。

> **個別事例記事（`case-study-detail`）は今回作らない。** `[LP]` で1本も取得できておらず、
> 構成のデータが無い。推測で型を作ると、根拠のない構成を配ることになる。

同ドキュメント末尾の未決着リスト #5 も「`case-study-detail`（個別事例記事）の構成 — 1本も取得できていない」。
保留の理由は**手法の限界**であって、作らないという設計判断ではなかった。
`research-eyebrow.md` §1-1 で実ブラウザ計測が確立し、その制約は外れている。

ブランドオーナーからの仮説はひとつ。

> **事例記事こそフォーマットが決まっていて、それに則って量産されるコンテンツではないか。**

本調査はこの仮説の検証と、パターン化に必要な実測の取得を目的とする。
そのため**1サイト3記事**を採取した。1記事では「フォーマットが固定か」を検証できず、
同一サイト内の複数記事の一致率こそが仮説の検証になるからである。

## 1. 手法と限界（先に読むこと）

### 1-1. 計測の手順

- 各記事を **1440×1000** の PC ビューポートで開き、`domcontentloaded` + 3 秒待機
- **ページ全体を 600px 刻みでスクロール**（IntersectionObserver 起点のフェードイン演出で
  `opacity: 0` のままになる要素を可視化するため）→ 先頭に戻して 1.2 秒待機 → 計測
- 記事本文の根（article root）は**機械的に決めた**: 25 文字以上の `<p>` を集め、
  祖先を 12 階層まで遡って文字数を加算し、最大値の 70% 以上を保持する要素のうち**最も深いもの**
- 本文段落（40 文字以上の `<p>`）の `getBoundingClientRect().width` の中央値を「読み幅」とした。
  宣言値の `max-width` ではなく**実効幅**である（サイドバー併置時にこれが効く）
- 見出し・写真・表・チップ・話者名は `getComputedStyle` の実値と `getBoundingClientRect()` の
  ページ絶対座標で記録した
- スクリーンショット（1440×1000 の先頭 1 画面）を全 29 ページで取得し、うち 6 ページを目視確認した
- 環境の制約により**ブラウザは常に 1 インスタンスのみ**を起動し、記事ごとに落とした

### 1-2. 事実として記録したもの

- DOM 構造（見出し階層・表 / 定義リスト・`figure` / `figcaption`・`blockquote`）
- `font-size` / `font-weight` / `line-height` / `letter-spacing` / `color` / `background-color` /
  `border-radius` の実値
- 写真の実寸・アスペクト比・`object-fit`・`alt` の有無と内容・キャプションの有無
- ページ全高（スクロール量の代理指標）と本文の文字数
- メタ情報（業種・規模など）のリンク先 URL（= 一覧のフィルタ軸との対応）

### 1-3. 取得できなかったもの・計測が壊れた箇所（**必ず読むこと**）

**a) Bill One には Web 記事としての事例が存在しない。**
`https://bill-one.com/case/` / `https://bill-one.com/ap/case/` のカードは
**すべて `\/ap\/form\/download_case_*\/` の資料ダウンロードフォームへ遷移する**（15 件すべて）。
2 ページ計測したが、中身は `h1「資料ダウンロード」` + `h2 事例タイトル` + サムネイル +
「この資料を読んでわかること」+ フォーム（会社名 / 氏名 / メール / 電話）で、本文段落は **0**。
つまり Bill One の事例は **PDF + lead-gen ページ**であって、事例記事ではない。
**これは失敗ではなく、そういう運営をしているという実測結果**として記録する。

**b) kintone は本体ドメインに事例を持たない。**
`https://kintone.cybozu.co.jp/cases/` `.../case/` はいずれも **404**。
トップページのリンクを辿ると事例は
**`https://kintone-sol.cybozu.co.jp/cases/*.html`（別ドメイン）**にあった。そちらを採取した。

**c) ANDPAD の記事ヘッダを1度取り逃し、再計測した。**
初回の抽出はサイト共通ヘッダ / フッタを除くために
`closest('header,footer,nav,[role=...]')` を除外条件にしていたが、
ANDPAD は**記事タイトル部を `<header class="l-article-header">` で囲んでいる**ため、
`h1`（36px/700）・会社プロフィール表・「課題 / 効果」ブロックが**まるごと落ちていた**。
`.l-article-header` を直接指定して再計測し、本文の記録を差し替えている。
**この取り逃しがあった事実をここに残す。** 同種の入れ子 `header` を持つサイトが
他にもあれば、同じ穴が空いている可能性がある（他 8 サイトでは `h1` が取れているので、
少なくともタイトルの取り逃しは無い）。

**d) カミナシの写真は `<img>` ではない。**
STUDIO 製で、`<div class="box image">` に CSS カスタムプロパティ（`--img-origin` など）で
画像 URL を持たせ、`aria-hidden` の子 `span` が描画する。
`<img>` を数える方式ではヒーロー写真が 0 枚に見えるため、
`.box.image` を含めて数え直した。**この形式の写真は `alt` を持ち得ない。**

**e) モーダル・追従バナーが計測を汚した箇所がある。**
Chatwork は初回訪問時に資料DLモーダルが全面に出る（ヒーロー写真の判定がモーダル画像を掴んだ）。
カミナシも同種のモーダル画像を持つ。ヒーロー写真の寸法はスクリーンショットで補正した。

**f) 「サイトごとに 3 記事」は、そのサイトの全記事を代表しない。**
記事は一覧ページの1ページ目（= 新着順の先頭付近）から採った。
古い記事は別テンプレートの可能性がある。実際 kintone は本文構成が記事ごとにかなり違い、
ANDPAD も 3 記事のうち 1 記事（energio）だけ章数が 2 と極端に少ない。

**g) PC 1440px の1ブレークポイントのみ。** SP でのレイアウト（サイドバーの回り込み、
写真比率の変化、目次の開閉）は検証していない。

**h) 「その構成が良いか」は測っていない。** 測ったのは
「何が、どの順で、どれだけ、どういう値で使われているか」だけである。

## 4. 設計提案 — `case-study-detail` パターン

### 4-1. 方針

実測が示したのは「サイト内では完全に固定、サイト間では割れる」という性質である。したがって、

- **記事ごとの構成の選択肢は作らない。** 章の順序・プロフィールの位置・写真の比率・末尾の並びは
  パターンが決める。呼び出し側が渡すのは**内容だけ**
- **実測に無いものは作らない。** 冒頭の数値タイル（0/27）・引用の飾り枠（0/27）・
  目次（2/9）は**作らない**
- **一覧（`case-study-list`）と語彙を共有する。** メタ情報の軸は実測で完全に一致している
  （業種 / 従業員規模 / サービス / 課題）。同じ 1 件のデータから一覧カードと記事ヘッダの
  両方を作れることが、この設計の最大の価値

### 4-2. 入力型（既存の作法に合わせた案）

```ts
/**
 * 一覧カードと記事ヘッダで共有するメタ情報。
 * 軸は case-study-list のフィルタ軸（CASE_STUDY_FILTER_AXES）と同一。
 * 実測: 9/9 サイトが同じ語彙を使い、4/9 は値を一覧のフィルタ URL へリンクさせている。
 */
export interface CaseStudyMeta {
  companyName: string;
  /** LogoMark の要素のみ受け付ける（既存 CaseStudy / CaseStudyListItem と同じ制約） */
  companyLogo?: React.ReactElement<LogoMarkProps>;
  service?: string;
  industry?: string;
  employeeRange?: string;
  challenges?: string[];
}

/**
 * 写真。alt は必須（既存 CaseStudy.photo / CaseStudyListItem.photo と同じ契約）。
 * 実測では意味のある alt を書いているのは 9 サイト中 1 サイトだけだが、
 * これは我々の既存決定を曲げる理由にならない（写真は実在性の証拠であって装飾ではない）。
 */
export interface CasePhoto {
  src: string;
  alt: string;
  /** 話者名と肩書き。実測 2/9 が figcaption をこの用途に使う */
  caption?: string;
}

/** 話者。実測: 明示ブロックを持つのは 3/9、最大 4 名（MF） */
export interface CaseSpeaker {
  name: string;
  /** 会社名 + 部署 + 役職（実測は1行で書かれる） */
  title: string;
}
/** 4名まで（実測の最大が 4。5人目は型エラーで落とす） */
export type CaseSpeakerList =
  | [CaseSpeaker]
  | [CaseSpeaker, CaseSpeaker]
  | [CaseSpeaker, CaseSpeaker, CaseSpeaker]
  | [CaseSpeaker, CaseSpeaker, CaseSpeaker, CaseSpeaker];

/** 問答（実測 4/9。h3 = 質問、段落 = 回答） */
export interface CaseQA {
  question: string;
  answer: string[];
}

/**
 * 章の中身。地の文か問答かはページ全体で1つに決める（実測: 記事ごとに混在するサイトは無い）。
 * LandingProof と同じ「どちらか一方」のユニオン。
 */
export type CaseChapterBody = { paragraphs: string[] } | { qa: CaseQA[] };

/** 章 = 見出し + 本文 + 写真1枚まで（実測: 章数 ≒ 写真枚数） */
export type CaseChapter = {
  heading: string;
  photo?: CasePhoto;
} & CaseChapterBody;

/**
 * 冒頭サマリー（実測 5/9）。
 * 課題と効果は必ず対で現れ（片方だけの例は 0/27）、決め手は任意（2/9 は持たない）。
 */
export interface CaseSummary {
  challenge: string[];
  /** 「導入の決め手」「解決策」。実測 3/9 */
  reason?: string[];
  effect: string[];
}

/**
 * 事例記事（実測 9 サイト × 3 記事 = 27 記事。research-case-study-detail.md）。
 *
 * この型もヒーローを持たない（case-study-list と同じ）。
 * 記事タイトル → 会社プロフィール → 写真 → サマリー → 章 → 関連事例 → 締め、
 * という順序はパターンが決める（実測 9/9 で一致）。
 */
export interface CaseStudyDetailInput extends LandingPageCommon {
  pattern: 'case-study-detail';
  article: {
    /** 成果か課題を含む1文（実測 8/9 がこの型。会社名だけのタイトルは採らない） */
    title: string;
    /** 一覧への戻り導線。実測 9/9 が持つため必須 */
    backTo: { label: string; href: string };
    /** 冒頭写真。実測 8/9 */
    photo?: CasePhoto;
    /** 本文前のリード段落（実測 6/9） */
    lead?: string;
    /** 公開日・取材時点（実測 2/9。§4-4 の asOf の議論） */
    publishedAt?: string;
  };
  /** 会社プロフィール。実測 9/9 が持つため必須 */
  profile: CaseStudyMeta;
  /** 話者（実測 3/9 が明示ブロック、3/9 が写真キャプション） */
  speakers?: CaseSpeakerList;
  /** 冒頭サマリー（実測 5/9） */
  summary?: CaseSummary;
  /** 本文。最低2章（実測の最小が 2 章）。中央値 5 章 */
  chapters: [CaseChapter, CaseChapter, ...CaseChapter[]];
  /** 関連事例（実測 9/9・3 件が最頻）。一覧のカードをそのまま使う */
  related: [CaseStudyListItem, CaseStudyListItem, ...CaseStudyListItem[]];
  /**
   * 末尾 CTA（実測 9/9）。hero が無く再利用できるオファーが存在しないため、
   * actions は必須（case-study-list と同じ扱い）。
   */
  closing: Slot<CTASectionProps>;
}
```

`DEFAULT_TONES` に `'case-study-detail': 'product'` を追加する
（`case-study-list` と同じ。記事は製品面の続きであり、campaign でも trust でもない）。

| **引用ブロック（`blockquote` の飾り枠）** | 実測 **0/27**。話者は写真キャプションか話者ブロックで示す                                |

### 4-5. 必要な新部品

| 部品                          | 内容                                                                                             | 判断                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`CaseStudyArticleSection`** | 記事本体（タイトル + プロフィール + 写真 + サマリー + 章 + 話者）を1つの部品として持つ           | **新規1つ。分割しない。** 実測が「構成は固定」と言っている以上、細かく分けても組み合わせの自由度は要らない。分けるとかえって順序を間違える余地が生まれる |
| **`CaseCard` の共有化**       | `case-study-list.tsx` 内のローカル関数 `CaseCard` を切り出し、記事末尾の「関連事例」で再利用する | **新規部品ではなくリファクタ。** 既存 `CaseStudySection` は `quote` が必須で、関連事例カード（タイトル + 会社名 + メタ）とは語彙が違う                   |
| `CaseStudyMeta` 型            | 一覧と記事で共有するメタ情報の型                                                                 | 型のみ。`CaseStudyListItem` が `extends` する形に変える（破壊的ではない）                                                                                |

`Link(arrow)` / `LogoMark` / `SectionHeader(as="h1")` / `CTASection` / `Page`。

**`Page` の面リズムとの衝突に注意。** 本文は 9/9 が単一面である。
記事本体を 1 セクションとして扱い、`default → muted` の交替が章のあいだに入らないようにすること
（`pageSurface` の割り当てで、記事本体・関連事例・締めの 3 スロットだけがリズムの対象になる）。

### 4-6. 推奨

**`case-study-detail` を作ることを推奨する。** 保留の理由（データが無い）は解消した。

根拠は 3 つ。

1. **仮説が実測で支持された（§3-3）。** 一致率 97.6%。事例記事は
   「スロットの決まったフォームに文章を流し込むコンテンツ」であり、
   **パターンとして配ることの効果が、LP のどのページ型よりも高い**。
   記事は 1 サイトに数十〜数百本ある。1 本ごとにレイアウトを判断させてはいけない
2. **一覧とデータを共有できる（§4-1）。** `case-study-list` は Stage 3 Slice 3 で実装済みで、
   記事はその遷移先である。メタ情報の軸が実測で完全に一致しているため、
   **1 件のデータから一覧カードと記事ヘッダの両方を生成できる**。
   これは他のページ型には無い性質で、量産の効きが最も大きい
3. **作らないものが明確に決まった（§4-3）。** 保留時の懸念は「推測で型を作ると根拠のない構成を配る」
   だった。いま、数値タイル・引用枠・目次を**作らない根拠**が実測にある。
   これは「作る根拠」と同じくらい重要な成果である

スライスの粒度としては 1 スライス（新規部品 1 + リファクタ 1 + パターン 1）で収まる。
実装時に必ず併せて行うこと:

| 項目                                                                                         | 理由                                                                                                     |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `LANDING_PAGE_PATTERNS` の網羅テスト（`guidelines-sync.test.ts`）の更新                      | `Record<LandingPagePattern, …>` が型で網羅を保証しているため、`DEFAULT_TONES` に足せば型が落ちて気づける |
| ページ単位 VRT の基準追加（desktop / mobile）                                                | 新しいページ型ストーリーが増える。`vrt:update` で撮り、Netlify プレビューで目視                          |
| Storybook ストーリーは**日英両方**（`packages/ui-web/CLAUDE.md`）                            | ラベル文言（「関連事例」「一覧に戻る」）は Props で注入し、ハードコードしない                            |
| changeset（`@siracusahq/gtm-design-system` minor）                                           | 新規パターンの追加は利用者から見える変更                                                                 |
| `composition-redesign.md` §3-1 の表に 6 つ目の型として追記し、末尾の未決着リスト #5 を閉じる | 保留の記録を、実測で解決した記録に更新する                                                               |

## 5. 判断できなかったこと・残課題

1. **1 サイト 3 記事は、そのサイトの全記事を代表しない。**
   一覧の 1 ページ目（新着順の先頭付近）から採っている。古い記事は別テンプレートかもしれない。
   「サイト内一貫性 97.6%」は**同時期に作られた 3 本の一致率**であって、
   「そのサイトの全記事の一致率」ではない。

2. **ANDPAD の記事ヘッダを 1 度取り逃した（§1-3c）。**
   入れ子の `<header>` を除外条件が拾ってしまった。他 8 サイトは `h1` が取れているので
   同じ取り逃しは無いはずだが、**「サイト共通ヘッダを除く」という前処理は
   記事ページでは危険**だという教訓が残る。次回の計測ではセマンティクスではなく
   幾何学（ページ上部の位置）で判定すべき。

3. **写真の枚数は下限値である。** `<img>` を数える方式では、カミナシのような
   CSS 背景描画の写真を取り逃す（§1-3d）。カミナシは手で数え直したが、
   他サイトにも同種の実装が混ざっている可能性は排除できていない。

4. **モーダルの影響を完全には除去できていない（§1-3e）。**
   Chatwork・カミナシは初回訪問モーダルが 1 画面目を覆う。
   ヒーロー写真の寸法はスクリーンショットで補正したが、
   モーダル下の要素の座標が押し下げられている可能性は残る。

5. **サマリーの「有無」は判定に解釈が入っている。**
   ANDPAD の「課題 / 効果」は会社プロフィール表の続きに `th` として置かれており、
   独立したブロックと呼ぶかは判断が割れる。HRBrain の「課題背景」も同様。
   §3-1 では 5/9 と数えたが、厳しく採れば 3/9（SmartHR・バクラク・freee）である。

6. **PC 1440px のみ。** SP でサイドバーがどこへ回り込むか（SmartHR・カミナシ・MF・kintone は
   サイドバーを持つ）、読み幅がどう変わるかは未検証。
   **記事は SP での閲覧比率が高いはずのコンテンツ**なので、実装前に SP の実測を足す価値がある。

7. **記事の更新頻度・本数の実測をしていない。**
   「量産される」という仮説の「量」の部分（1 サイト何本あるか、月に何本増えるか）は測っていない。
   一覧のページネーションから概算はできるが、本調査の範囲外とした。

8. **Bill One 型（PDF + フォーム）をどう扱うかは決めていない。**
   9 サイト中 1 サイトは Web 記事を持たず、事例を資料ダウンロードの餌にしている。
   これは `lead-gen` パターンで既に表現できるが、
   「事例一覧 → 資料フォーム」という導線を `case-study-list` が想定していない
   （`CaseStudyListItem.href` は記事を指す前提）。実装時に確認すること。

9. **英語ページでの構成は未調査。** 本調査は日本語ページのみ。
   バイリンガル対応（`packages/ui-web/CLAUDE.md`）の観点では、
   英語版の事例記事が同じ構成かどうかは分かっていない。
