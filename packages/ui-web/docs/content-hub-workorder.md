## 0. スコープ

**対象**: `ContentHubSection` 1部品と、既存ページ型 `product` / `product-portfolio-top` への
任意スロット `contentHub` の追加。

**対象外**:

| 除外するもの                         | 理由                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------ |
| **新しいページ型**                   | 回遊は独立ページではなく**製品系ページ末尾のセクション**。ページ型は 11 種のまま         |
| **カード部品の新設・統合**           | Slice 0（2026-08-15）で確定。既存カードを流用し、見た目の二重実装を作らない               |
| `lead-gen` への追加                  | 実測 0/2。広告着地で回遊させると獲得が漏れる、というこの型の存在意義とも一致              |
| `corporate-top` への追加             | 実測 n=1（LayerX）。1件で型を配らない。スロット追加は非破壊なので実測が増えたら足せる     |
| 一覧・詳細ページ型への追加           | 記事系・事例系は `related` が既にあり役割が重複。獲得系詳細は「フォームの手前で逃がさない」 |
| ハブ内の絞り込み・検索・ページ送り   | **実測 0/11 ページ・0/17 枠**（§9 G1-8）。絞り込みは一覧ページ型の仕事                   |
| CMS 連携・データ取得                 | このシステムは表示層のみを配る                                                           |

## 1. 狙い

製品系 LP の多数が末尾に資料・セミナー・コラム・News の回遊を持つ。国内 BtoB の強い特徴で、
LP の末尾がメディアハブ化している。現行のシステムはこの部品を持たず、
`product` / `product-portfolio-top` で組んだ LP は実測の最大公約数を再現できなかった。

**遷移先はすでに全部ある。** 11 ページ型のうち `article-list` / `article-detail` /
`resources-library` / `seminar-list` / `seminar-detail` / `case-study-*` は 2026-08-15 までに完成しており、
`article-pages-workorder.md` §1 が挙げていた「リンク先が宙に浮く」問題は解消済み。
残っていたのは入口だけだった。

## 9. 実装で判明した事項

**この節がこのスライスの経緯の正本。**
`research-lp-anatomy.md` は調査時点の記録であって、実装の記録ではない。

### 9-1. ゲート結果（実ブラウザ計測 16ページ・2026-08-15）

手順は `research-case-study-detail.md` §1-1 に準拠（1440×1000 / `domcontentloaded` + 3秒 /
600px 刻みスクロール → 先頭へ戻して 1.2秒 → 計測）。**取得失敗 0。**

| # | 測ったもの           | 結果                                                                            |
| - | -------------------- | ------------------------------------------------------------------------------- |
| G1-1 | グルーピング形態  | **系統ごとに別ブロック 11/11。混在1グリッドは 0/11**                           |
| G1-2 | 系統数            | 1ページあたり中央値 2・**最大 5**（SmartHR = 資料+セミナー+コラム+News+外部メディア） |
| G1-3 | 件数              | アイテムカード枠 n=17 で中央値 **3**（最頻3 = 9/17）。News のみ中央値 4        |
| G1-4 | 一覧導線          | ページ単位 10/11・**枠単位 14/17**。文言は **12通りで全部違う**                |
| G1-5 | 系統見出し        | News 7/7 が保有し「お知らせ」に 6/7 で収束。資料5通り・セミナー4通りに割れる    |
| G1-6 | 表示形            | サムネイル: 資料/セミナー/コラム **9/10**、**News 0/7**。例外なし              |
| G1-7 | 表示要素          | 日付は News 7/7・資料 **0/4**。カテゴリピル 6/17。**種別ラベル 0/17**         |

| G1-9 | 事例の出現        | **0/17**                                                                        |
| G2   | 面と位置          | **11/11 が最終CTAの前**。白8枠 / 淡色7枠 / 濃色3枠。**濃色は入口タイル型の枠だけ** |

**分母の訂正**: `[LP]` の「コンテンツ回遊 9/12」は**分母を再現できなかった**。
製品系の日本語ページを列挙すると 13 本で、保有 9・非保有 4 = **9/13**。
どのページを母数から外したかは記録に書かれていない。

**設計判断への影響は無い。** 9/12（75%）→ 9/13（69%）はどちらでも
「多数が保有・ただし 100% ではないので必須セクションにしない」という結論を変えない。
非保有ページが 5/5 で**フッターに逃がしている**事実は、
「ハブ無しのページも成立する」ことの追加の裏付けになる。

**リサーチファイルは書き換えない。** `[RS]` の「7/7 詳細ページ経由」を
`acquisition-pages-workorder.md` §9-1 で訂正したのと同じ形式で、本節を正本とする。

### 9-2. 予想と違ったこと

1. **「4系統を1グリッドに混ぜ、種別バッジで区別する」形は実在しなかった**（0/11）。
   事前イメージだった ContentHub は実測に無い構成だった。実測は
   「系統ごとに塊を作り、塊ごとに見出しと一覧導線を持つ」
2. **カードは2種類あった。** アイテムカード（個票へ、n=17）と**入口タイル**（一覧へ、n=6 / 5社）。
   5社が個別コンテンツを1件も出さず入口タイルだけで済ませている枠を持つ
3. **News だけ構造が別物。** サムネ 0/7・日付 7/7 の行リスト。
   `ArticleCard` をそのまま流用すると実測から外れる
4. **ハブ内の資料カードは個票を経ずフォーム直行が Bill One 3/3・Chatwork 3/3。**
   `acquisition-pages-workorder.md` §9-1 の「`ResourceListItem.href` の遷移先を固定しない」が
   ハブ内でも追認された。型の変更は不要

### 9-3. Slice 0 の決定を1点改めた

**ContentHub の union を「4系統」から「3系統 + News + 入口タイル」に改め、`case`（事例）を外した。**

Slice 0（`composition-redesign.md` 末尾）は「ContentHub は4系統のカードを union で受け取る」と
決めたが、それは**ハブ未計測時の決定**であり、記録自身が
「突き合わせ相手が1つ欠けた状態での決定であることを明記しておく」と留保していた。
今回の計測でハブ内の事例出現が **0/17** と分かったため、
`sold-out` 0/29・`permanent` 1/21 を型に含めなかった前例に倣う。

**非破壊。** union へのメンバー追加は型の拡張であり、既存の呼び出しは影響を受けない。
`CaseStudyListItem` は既存型として存在し続けるので、実測が採れた時点で1行足せばよい。

### 9-4. 確定判断を実装で1点読み替えた（**要レビュー**）

Fable の確定判断7は「面は**枠単位**で指定可能にし、白=`default` / 淡色=`muted` / 濃色=`dark` を
`Section` バリアントに対応させる。アイテムカード枠には `dark` を型で許さない」だった。

**実装では ContentHub 全体を1つの `<Section>` とし（面は `Page` のリズムに任せる）、
濃色は入口タイル側の `tone="brand"` が持つ形にした。** 読み替えの根拠は2点。

1. 実測の記述が「濃色／グラデ: 3枠 — SmartHR のティールグラデ**大型カード**、
   Sansan の青グラデ**帯**、kintone の淡グラデ」であり、
   **濃色として観測されたのはタイルそのものの色**であってページ面ではないと読める
2. `Page` の面リズムは `React.Children.toArray` で子を数えて割り当てる。
   ContentHub が複数の `<Section>` を返すとフラグメント1個として数えられ、交互リズムが崩れる。
   `markPageSurface` で申告できるのはセクション単位の `default | dark | accent` だけで、
   「枠ごとに面が違うセクション」を表現する口が無い

**結果として「アイテムカードを濃色にできない」という制約は型で担保されている**
（`tone` は `kind: 'index'` にしか存在しない）ので、判断7の意図は満たしている。
ただし「淡色（muted）を枠単位で選ぶ」ことはできなくなった。
**この読み替えの妥当性は Fable のレビュー待ち。**
