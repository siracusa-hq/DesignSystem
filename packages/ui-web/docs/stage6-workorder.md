## 1. 狙い

CLAUDE.md はこのリポジトリの中でしか効かない。パッケージを入れた先の
AI エージェントに規範を届けるため、配布物（files）に機械可読ファイルを同梱する。

役割分担の原則:

- **型と dev 警告が守れるもの** → 文書に書かない（負け筋）。「守られていること」の一覧だけ示す
- **API では表現できない判断**（型の選択・素材の判断・コピーの書き方・トーンの選択）→ ここだけが文章の仕事
- **正本は1つ**。同じ内容を2ファイルに書かない（AGENTS.md は薄い入口、GUIDELINES.md が本文）

## 3. GUIDELINES.md の構成（確定）

1. **思想（3点）**: ①構成の判断はシステムが持つ（AI の仕事は埋めること）
   ②すべてのルールに実測根拠がある（国内 BtoB SaaS の配信 CSS・19ページ実測）
   ③守りは機械が担う（型エラー → dev 警告 → VRT の3段。人間のレビューは内容に集中する）
2. **ユースケース別ガイド（ページ型5つ）**: それぞれ「いつ選ぶ」「用意する素材チェックリスト」
   「Do」「Don't」。例: lead-gen は広告着地専用・ナビを剥がす実測 2/2・オファーは1つ
3. **横断の Do's & Don'ts**: CTA（ラベル2種・反復自由・FV 2本）/ 面と余白（境界は面差のみ・
   線を引かない 実測0/11・暗面3連続禁止）/ ロゴと数値（0社に振り切るか6社以上・1〜5社は事例カードへ・
   数値には asOf）/ フォーム（用途別に分ける・ラベルはオファー名・既定日本語）/
   色（primary=操作 / brand=装飾。明背景のテキストに brand 禁止）。**各項に実測根拠を1行**
4. **なぜ選べないのか（期待値調整）**: className が無い / 順序を変えられない / 列数・色・余白を
   指定できない — 理由（品質の標準化はデザインシステムの存在意義そのもの）と、
   本当に必要になったときの正しい経路（DS 側に部品/パターンを追加する = このリポジトリに PR）
5. **Astro での使い方**: styles.css 1行 / `.astro` 直置き禁止（リズムが効かない。実測 §7-11）/
   対話部品は client:visible / フォームは静的出力が Netlify に検出される
6. **守られていることの一覧（読むだけでよい）**: 型エラー一覧・dev 警告9種・VRT。
   「これらは文書を読まなくても機械が止める」ことを明記
