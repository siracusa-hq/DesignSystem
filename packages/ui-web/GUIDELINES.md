# GUIDELINES.md — 判断のための規範

`@siracusahq/gtm-design-system` で LP を作るときの Do's & Don'ts。入口は [AGENTS.md](./AGENTS.md)。

**このファイルに書いてあるのは、API では表現できない判断だけ**である。型で落とせるもの・警告で止まるものは書かない（§6 に一覧だけ置く）。すべてのルールに実測の根拠を1行添えてある。根拠を引けないルールは書いていない。

**語彙**: ブランド4 = `corporate` / `polastack` / `peerdesk` / `peerdesk-taxpeer`。トーン3 = `trust` / `product` / `campaign`。ページ型5は §2 に1節ずつある。

実測の原典（本文の数値はすべてここから引いている）:

- `docs/research/research-lp-anatomy.md` — 国内 BtoB 19 ページのアナトミー調査（2026-08-02）
- `docs/research/research-cta-band.md` — 中間 CTA 帯の CSS 実測（国内 11 ページ、2026-08-06）
- `packages/ui-web/docs/composition-redesign.md` — 上記から導いた設計方針の正本

## 1. 思想（3点）

**① 構成の判断はシステムが持つ。書き手の仕事は埋めること。**
セクションの順序・面と余白のリズム・CTA の配置は、パターン（`defineLandingPage`）とページコンテナ（`<Page>`）が決める。旧 API は 18 セクションが背景 4 通り × 余白 5 通りを独立に受け取っており、10 セクションの LP で 20^10 ≈ 10兆通りの見た目が表現できた。成立するのはそのうち十数通りしかない。**選択肢を減らしたのは制限のためではなく、選ぶ必要をなくすため。**

**② すべてのルールに実測の根拠がある。**
「一般に良いとされる」は採らない。国内 BtoB SaaS の配信 CSS と DOM を直接読んだ 19 ページの実測が根拠であり、実測で反証されたルールは撤回してある（例:「プライマリ CTA はページに2箇所まで」は該当ページ 0 件だったため撤回）。逆に、検証できていないことは「自分たちの決定」と明示している（面の交互リズムがこれ）。

**③ 守りは機械が担う。人間のレビューは内容に集中する。**
**型エラー → dev 警告 → ページ単位 VRT** の3段。型で落ちるものは文章で二重に禁止しない。レビューで見るべきは「コピーが正しいか」「数値の出典が正しいか」であって、余白や色ではない。

## 2. ユースケース別ガイド（ページ型5つ）

### `product` — 単一製品の LP

**いつ選ぶ**: 検索・指名流入で「この製品を評価しに来た人」が着地するページ。製品名でランディングし、機能と料金を比較して検討に進む導線。実測で最多の型。

**素材チェックリスト**

- hero: 見出し + リード文 + **オファー1〜2本**（ラベルは §3 の2種ルールに従う）
- proof: **数値3〜4点 + `asOf`（基準時点）**、またはロゴ6社以上のどちらか
- features: **機能3〜6点**（各 title + description）
- pricing: 料金プラン（任意）
- reasons: 「選ばれる理由」3〜4点（任意）
- cases: 導入事例1〜3件（任意）
- faq: 任意
- closing: 締めの CTA（見出し + オファー。省略不可）

| Do                                                              | 根拠                                                                     |
| --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 料金を事例より前に置く（パターンが自動でそうする）              | 両方持つページで 料金→事例 が4件、事例→料金 が1件                        |
| FAQ は必要なときだけ足す                                        | 製品系12ページ中5ページ（42%）にしかない。必須セクションではない          |
| 締めの CTA 面を必ず置く                                         | フッター直前の最終 CTA 面は 10/12（83%）                                 |
| 数値には必ず `asOf` を渡す                                      | 実測ではほぼ全社が時点を併記。景品表示法上、時点のない実績表示は不当表示になりうる |

| Don't                                                                 | 根拠                                                                 |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 社会的証明（ロゴ帯・数値訴求）を両方とも省く                          | 19/19 のページが何らかの数値訴求を持つ。例外は1ページも無かった      |
| 機能セクションに10点以上を並べる                                      | 列数は件数から導出される。7件以上は3列に流れて1件あたりの情報が薄くなる |

### `product-portfolio-top` — 複数プロダクトの玄関

**いつ選ぶ**: コンパウンド企業のトップページ。複数の製品を持ち、**カードグリッドで下層の製品 LP へ分岐させる**のが中核。`corporate-top` でも単一 `product` でもない独立した型で、実測 19 ページ中 7 ページ（バクラク / SmartHR / Bill One / カミナシ / ANDPAD / HRBrain / kintone）がこれ。Polastack もピアデスクシリーズも、まずこの型を必要とする。

**素材チェックリスト**

- hero: 会社・シリーズ全体のキャッチ + オファー1〜2本
- proof: 全社合計の数値（導入社数・シェア）+ `asOf`、またはロゴ帯
- products: **製品カード（`brand` / `name` / `description` / 下層 LP への `href`）**。省略不可
- features / cases / midCta: 任意
- closing: 締めの CTA（省略不可）

| Do / Don't                                                                             | 根拠                                                                       |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Do**: 製品カードの `brand` に各製品のブランドキーを渡す                              | カードのチップとリンクだけがその製品の色になる。ページ全体の色は親の `brand` のまま |
| **Do**: 数値は「製品単体」ではなく「全社・シリーズ合計」を出す                          | 玄関ページの役割は分岐であって、単一製品の説得ではない                     |
| **Don't**: 特定の1製品の機能詳細をここに書く                                            | 下層 LP の仕事。玄関で書くと分岐の判断材料が埋もれる                       |

### `lead-gen` — 獲得専用 LP（広告着地）

**いつ選ぶ**: **広告から直接着地させるページ**。資料ダウンロードや問い合わせだけを取る。`product` との分岐はここ — 検索・指名流入なら `product`、**広告着地なら `lead-gen`**。

**素材チェックリスト**

- hero: 資料タイトル + 何が分かるか。オファーはフォームへのページ内アンカー1本のみ（0本でもよい）
- contents: **資料の中身の箇条書き**（省略不可）
- stats: 数値訴求（任意だが実測 2/2 が残している）
- form: `ResourceRequestForm` / `ContactForm` / `DemoRequestForm` のいずれか（省略不可）

| Do / Don't                                                              | 根拠                                                                          |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **Do**: グローバルナビを付けない（型に `header` が無い）                | 実測 2/2 がナビを剥がしている。広告着地でサイト内を回遊させると獲得が漏れる    |
| **Do**: オファーを1つに絞る                                             | 迷わせないための型。`product` と違い分岐の余地を作らない                       |
| **Do**: 数値訴求を残す                                                  | 2/2 がナビを剥がしても数値訴求は残している                                    |
| **Don't**: フォームを省いて別ページへ飛ばす                             | この型の存在意義がフォームの同居にある（別ページ遷移なら `product` でよい）    |

### `case-study-list` — 導入事例の一覧

**いつ選ぶ**: 事例を**一覧で見せて絞り込ませる**ページ。個別の事例記事ではない。

**素材チェックリスト**

- page: **短いページタイトル**（キャッチコピー型のヒーローは使わない）+ 説明文
- list: 事例カード（`pickup` / `filterAxes` / `pageSize` は任意）
- closing: 末尾 CTA（任意。ヒーローが無くオファーを再利用できないため `actions` は必須）

| Do / Don't                                                                          | 根拠                                                                     |
| ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Do**: フィルタ軸は「サービス / 業種 / 従業員規模 / 課題」から選ぶ                 | 実測 2/2（SmartHR・バクラク）がこの4軸で共通していた                    |
| **Don't**: キャッチコピー型のヒーローを付ける                                       | 実測 2/2 とも短いページタイトルから始まる。この型だけ hero を持たない     |
| **Don't**: 個別事例記事をこの型で作る                                               | 個別記事は調査で1本も取得できておらず、構成のデータが無い（型を用意していない） |

### `corporate-top` — コーポレートトップ

**いつ選ぶ**: 運営会社のトップページ。読み手は投資家・採用候補・パートナーであって、製品の買い手ではない。

**素材チェックリスト**

- hero: **ビジョンステートメント**（製品訴求ではない）。offers は「私たちについて」「採用情報」等
- services: 事業紹介カード（省略不可）
- stats: 事業規模の数値（任意）
- about / closing: 任意

| Do / Don't                                                            | 根拠                                                                         |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Do**: 数値は事業規模・市場規模にする                                | 実測（LayerX）の数値は市場規模・利回りであって導入実績ではない                |
| **Don't**: コンバージョン CTA を置く                                  | 実測でこの型には資料 DL も問い合わせも無い。導入ロゴも 0 社                   |
| **Don't**: 製品スクリーンショットを主役に置く                         | 訴求対象が買い手ではないため、製品ビジュアルが要らない                       |

## 3. 横断の Do's & Don'ts

### CTA

| ルール                                                                       | 根拠                                                                                    |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| **プライマリ CTA のラベルは2種類まで。反復は自由**（目安4〜6回）             | 総 CTA 数の中央値は 15〜16 本で「2箇所まで」のページは 0 件。一方ラベル種類は 2 種が最頻 |
| **ファーストビューのオファーは2本**                                          | FV 2本が 13/17（76%）。型でも最大2本に制約している                                     |
| 2本の組み方は「軽+重」でも「軽+軽」でもよい                                  | 軽+重 が7件、**軽+軽（資料DL 2本）が4件**。後者は軽重ではなく「何の資料か」の分岐       |
| ラベルは行動を書く（「送信」ではなく「資料をダウンロード」）                 | 送信ボタンのラベルをオファー名と一致させるのが実測の作法                                |
| kicker（`＼5分でわかる資料をプレゼント／` 等）で重さを下げてよい             | 実測で7種確認。「ご相談だけでもOK お問い合わせ」のように重い CTA を和らげる慣行がある   |
| **面を持つ CTA 帯（`CTABand`）の反復は中間1〜2回まで**                       | 面を持つ CTA 帯を3回以上反復しているサイトは 0 件。4〜6回の反復は面を持たない CTA の領分 |

### 面と余白

| ルール                                                     | 根拠                                                                                       |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| **セクションの境界に線を引かない**                         | セクション面を上下の線で区切る国内 BtoB SaaS は 11 ページの CSS 走査で **0 件**            |
| 境界は「面の色差」だけで作る                               | 淡い面（対比 1.12:1）を線なしで成立させている実例がある。手段は余白の確保と中身の濃さ       |
| **暗い面を3つ連続させない**                               | 可読性の問題。他社実態ではなく自分たちの確定規則                                            |
| 面の交互リズムは `<Page>` に任せる                         | 交互リズムは他社実態が未検証のため「自分たちの決定」として実装しており、基準はページ単位 VRT |
| **セクション見出しの区切りは飾り線（既定・自動）**。eyebrow は見出しから内容が読み取れないときだけ・日本語で | ピル型ラベルは 41 セクション実測で 0 件（ピル型は CTA の肩コピーの記号）。飾り線採用サイトは適用率ほぼ100%（docs/research/research-eyebrow.md） |

### ロゴと数値

| ルール                                                                          | 根拠                                                                                 |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **社会的証明はロゴ帯か数値訴求のどちらかを必ず置く**                            | 19/19 のページが数値訴求を持ち、両方無いページは 0 件                                |
| **ロゴは 0 社に振り切るか、6 社以上出す**                                       | ロゴ 0 社（数値に振り切る）が 6/19（32%）。1〜5社は日本語ページに実例 0 件           |
| 少数しか出せないなら、ロゴ帯にせず事例カードに紐付ける                          | SmartHR 6社 / Bill One 8社が事例セクション内に置く形を採っている                     |
| ロゴを載せるなら中央値は約20社。14社以上は自動でカルーセルになる                | 掲載時の中央値 ≒ 20社、14社以上の5ページはいずれもカルーセル                         |
| **数値には `asOf`（基準時点）を必ず添える**                                     | 景品表示法。時点の分からない No.1 表示・実績表示は不当表示になりうる                 |
| 数値は「導入規模」「No.1・シェア」「継続率」「削減率」の4型から選ぶ             | 19 ページの数値訴求はこの4型に整理でき、規模+順位の同時掲出が最頻（10/19）           |

### フォーム

| ルール                                                              | 根拠                                                                                  |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **用途ごとにフォームを分ける**（問い合わせ / 資料請求 / デモ）      | SmartHR 3本・Bill One 2本・freee人事労務 3本。1フォームに用途セレクタを付ける社は無い |
| 送信ボタンのラベルをオファー名に一致させる                          | 「送信」等の汎用語は実測の作法から外れる（dev 警告の対象）                            |
| `product` 系ではフォームを別ページに置いてよい                      | 15/19（79%）が別ページ。埋め込みは `lead-gen` の主役であって product の必須部品ではない |
| **言語は既定 `ja`。英語にするときだけ `lang="en"` を渡す**          | 静的出力（SSG）でブラウザの `document` を覗けないため、明示指定でしか決定できない     |

### 色

| ルール                                                                        | 根拠                                                                    |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **`primary`（`#008575`）= 操作用**。ボタン背景・リンク・フォーカスリング      | 白文字 4.55:1 で WCAG AA 適合                                          |
| **`brand`（`#13c3a0`）= 装飾用**。グラデーション・グロー・ダーク背景上のみ    | 白背景での対比は 2.25:1 しかない                                       |
| **明背景のテキスト・ボタン背景に `brand` を使わない**                         | 同上。CI（`src/tokens/tokens.test.ts`）がコントラスト比を実計算して落とす |
| CTA は別色でもよい（`--color-bg-cta` スロット。未指定なら操作色にフォールバック） | 実測でブランド主色が青（`#0360e5`）でも CTA の塗りが黄（`#ffdb22`）の社がある |

### 和文コピー

| ルール                                                              | 根拠                                                                       |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **見出しに `<br>` を手で入れない**                                  | 改行位置はシステムが `text-wrap: balance` で処理する。手動改行は文言差し替えで崩れる |
| 負の字送り（`letter-spacing` のマイナス）を持ち込まない             | 和文で負の字送りを使っている国内 BtoB 企業は 8社中 **0 社**                |
| 本文に 14px 未満を使わない                                          | デジタル庁 DADS が「原則として許容されない」と明記                          |
| **セクション内の散文は見出し1文だけ。説明は箇条書き（最大3点）と数値に分解する** | AirPocketFeature の再設計で確立（2026-08-11 ブランド決定）。散文の段落スロットは廃止済み — 説明を書きたくなったら「要点3つに割れないか」「数値にできないか」を先に考える |

## 4. なぜ選べないのか（期待値調整）

このシステムには、他のライブラリなら普通にある口が意図的に無い。

| 無いもの                                     | 代わりに                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------- |
| `className`                                  | 見た目はトークンとトーンが決める                                   |
| セクションの順序を変える口                   | ページ型（`pattern`）を選び直す                                    |
| 背景・余白を指定する props                   | `<Page>` が前後関係から割り当てる                                  |
| 列数・カードの見た目を指定する props         | 件数と位置から導出される                                           |
| 自由な色指定                                 | `brand` と `tone` の組み合わせで表現する                           |

**理由は1つ。品質の標準化がデザインシステムの存在意義そのものだから。** 逃げ道を1つ残すと、そこが最短経路になる。旧 API は `className="bg-neutral-900 py-40"` ですべての規約を迂回でき、しかもそれは静かに起きていた。

**本当に足りないときの正しい経路**は、逃げ道を探すことではなく **DS 側に部品またはパターンを追加すること**（このリポジトリへの PR）。追加には「なぜ必要か」と一緒に**実測または明示的なブランド判断**が要る。根拠のない選択肢を増やすと、10兆通りに戻る。

なお「選択肢を消す」判断は実際に何度も撤回している（ロゴ6社未満の警告、CTA 2箇所ルール、CTABand の上下線）。**根拠が出れば規範は変わる。** 変えたいときは根拠を持ってくること。

## 5. Astro での使い方

```ts
import '@siracusahq/gtm-design-system/styles.css';
```

1行だけ。PostCSS も Tailwind も設定しない。**この1行で足りることは CI の Astro 消費側ビルドで実測している**（`packages/astro-consumer-test`）。

**`.astro` にセクションを直接並べてはいけない。**
`<Page>` の面リズムは `React.Children` で子を1件ずつ見る実装であり、Astro は子を「レンダリング済み HTML の塊」として渡すため、`Page` から見た子が不透明な1件になる。実測では `.astro` に5セクションを直接並べたページで muted 面の出現が **0 件**（`defineLandingPage` 経由は1件）。同じ理由で暗面3連続・h1 重複・CTA ラベルの各警告も働かない。**リズムも規範ガードも外れたただの部品置き場**になる。

推奨形は2つだけ。

1. `defineLandingPage()` + `<LandingPage>`（LP 量産の本線）
2. セクションの並びを `.tsx` のコンポーネントにまとめ、`.astro` からはそれを1つ置く

**対話部品には `client:visible` を付ける。** FAQ のアコーディオン、事例一覧の多軸フィルタ、数値のカウントアップは JS が要る。静的なセクションには付けない（送るバンドルが増えるだけ）。

**フォームは静的出力のまま置く。** Netlify Forms はデプロイ時に静的 HTML の生コントロールを解析して受け口を作るため、`client:*` を付けると検出されない。フォームの言語は既定 `ja` で、明示的に `lang="en"` を渡したときだけ英語になる。

### Storybook に載るもの・載らないもの

Storybook は **ビジュアルデザインの採用判断の場**（人間と AI の共通認識づくり）。
載る基準は2つ: (1) ビジュアルが明確にわかり採用可否を判断できる
(2) 例示の役割が他と被らない。構造でガードされているもの（型エラー・dev 警告・VRT）は
ストーリーにせず、本ガイドラインの §6 だけが説明する（2026-08-10 ブランド決定）。

## 6. 守られていることの一覧（読むだけでよい）

**以下は文章を読まなくても機械が止める。** 覚える必要はなく、止まったときに理由が分かればよい。

### 型エラーで落ちるもの

- `className` を渡す（公開インターフェース全件で `Omit<…, 'className'>`）
- 背景・余白・列数・eyebrow のスタイルなど、見た目を選ぶ props を渡す（存在しない）
- ファーストビューのオファーを3本渡す（`offers` は最大2要素のタプル）
- ページ型ごとの必須スロットを欠く（`product` の `features` / `closing`、`lead-gen` の `contents` / `form` など）
- `brand` / `tone` / `pattern` に一覧外の文字列を渡す
- `lead-gen` に `header` を渡す（型に無い）

### dev ビルドでコンソール警告が出るもの（9種）

| # | 警告                                              | 出る場所        |
| - | ------------------------------------------------- | --------------- |

### そのほか

- **ページ単位のビジュアル回帰テスト**（Playwright、desktop 1280×800 / mobile 390×844）。和文の最悪ケース（異常に長い / 異常に短い / 英語）を含むページ全体のスナップショットが CI で比較される
- **配布物の検証**: SSR での描画、CSS Modules のマッピング、Netlify Forms 属性、Astro での実ビルド出力を CI が毎回確認している
- **色の検証**: `brand` の誤用（明背景のテキスト・ボタン背景）と WCAG コントラスト比を CI が実計算して落とす
