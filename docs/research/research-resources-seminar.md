# 資料（資料DL）/ セミナー系ページ型 実測調査 — 「獲得のためのコンテンツ」の型

対象: 日本のBtoB SaaS の **Web / LP 面のみ**（`@siracusahq/gtm-design-system` 側）。
母集団は [LP アナトミー調査](./research-lp-anatomy.md) /
[事例記事調査](./research-case-study-detail.md) /
[News・ブログ調査](./research-news-blog.md) と同じ核（同じ 10 社を候補にした）。

調査日: 2026-08-14
調査手法: **`WebFetch` による HTML / テキスト取得と構造の読み取り**（実ブラウザ計測ではない。§1-1）
出典記号: **`[RS]`**（Resources / Seminar 調査。`composition-redesign.md` 冒頭の「実測の出典表記」表に倣う）

## 0. 調査の動機

`[NB]` 調査（News / ブログ）が終わった時点で、
LP 末尾のコンテンツ回遊（`[LP]` 9/12）が指す遷移先のうち、まだ 2 系統が空いている。

**資料ダウンロード**と**セミナー / イベント**である。

この 2 つは他の系統と性格が違う。事例記事・News・ブログが「読ませて信頼を作る」面なのに対し、
**資料とセミナーは、フォームでリードを取ることが目的**の面である。
`[LP]` 調査で FV の 2 オファーのうち「重いオファー」の実体として最頻だったのが、
まさにこの 2 つだった。**LP の CTA が指す先そのもの**が、このシステムに存在していない。

一方 `composition-redesign.md` §3-1 のページ型には `lead-gen` がある。
これは**資料DLの単票 LP**（`packages/ui-web/src/patterns/define-landing-page.ts` 106〜117 行目）で、
`contents` / `stats` / `form` を持ち、**グローバルナビを剥がす**（実測 2/2）設計になっている。

本調査の問いは 3 つ。

1. 資料DLの一覧（ライブラリ）と、セミナーの一覧・詳細は、記事系と同じくらいフォーマット化されているか
2. **資料の個票は、既存の `LeadGenInput` で足りるのか。** 足りるなら新設は「一覧」だけで済む
3. セミナーは**開催予定と開催終了で別のページ型が要るのか**、1 つの型の状態違いで済むのか

このリポジトリの鉄則は「実測なしに構成を推測しない」。
`case-study-detail` が一度「データが無いから作らない」と保留され、
実地調査を経て解除された前例に従う。

## 1. 手法と限界（先に読むこと）

### 1-1. 元調査との手法の違い

**本調査は実ブラウザ計測ではない。** `[NB]` と同じく、環境の制約により Playwright 等の
ブラウザ自動化を使えないため、`WebFetch`（URL 取得 → Markdown 変換 → 構造の読み取り）で代替した。

| 項目                                                | `case-study-detail` 調査 | `[NB]`                | 本調査 `[RS]`                 |
| --------------------------------------------------- | ------------------------ | --------------------- | ----------------------------- |
| 取得手段                                            | ヘッドレス Chromium      | `WebFetch`            | `WebFetch`                    |
| `getComputedStyle` の実値（font-size / 読み幅 ほか） | **取得した**             | 取得していない        | **取得していない**            |
| 要素のページ絶対座標（y 座標）                      | **取得した**             | 取得していない        | **取得していない**            |
| スクリーンショットによる目視確認                    | 29 ページ                | 0 ページ              | **0 ページ**                  |
| JS 描画後の DOM                                     | 反映される               | 反映されない場合がある | **反映されない場合がある**    |
| セクション順序・見出し階層                          | 取得した                 | 取得した              | 取得した                      |
| フォームの入力項目名                                | 取得した                 | 対象外                | **ほぼ取得できていない**（§1-3f） |
| 開催状態（受付中 / 終了）の表記                     | 対象外                   | 対象外                | 取得した                      |

**したがって本調査が主張できるのは「構成・情報設計・語彙」だけである。**
余白 px・フォントサイズ・読み幅・色は 1 つも測っていない。

### 1-2. 事実として記録したもの

- **資料一覧**: `h1` の文言と型 / フィルタ軸の名前と選択肢 / カードの表示項目
  （サムネイル・カテゴリ・**資料形式表記**・日付・抜粋・バッジ）/
  **遷移先が資料詳細ページかフォーム直行か** / ピックアップ枠 / ページネーション / 検索ボックス
- **資料個票**: `h1` / パンくず / 表紙画像 / 資料の中身の説明の形式 /
  **フォームが埋め込みか別ページか** / 「こんな方におすすめ」 / 関連資料 /
  **グローバルナビの有無** / セクション順序
- **セミナー一覧**: `h1` / **開催予定と終了アーカイブの分離方式** / フィルタ軸 /
  日時の書式 / **開催形式（会場・オンライン・ハイブリッド）の表示** /
  **満席・受付終了の表示** / ページネーション
- **セミナー詳細**: セクション順序 / 開催日時（単一 / 複数日程）/ 申込締切 / 開催形式 /
  **開催状態の表記** / 「こんな方におすすめ」 / アジェンダ / 登壇者ブロック（人数・肩書き・顔写真）/
  **申込フォームが埋め込みか別ページか** / 参加費 / 定員 / 関連セミナー / 主催・共催 / 注意事項 /
  **終了後の同一 URL の姿**（録画視聴への切替・資料DLへの切替・そのまま）

### 1-3. 取得できなかったもの・失敗の記録（**必ず読むこと**）

取得できないこと自体が実測結果である。以下は隠さず全部残す。

**a) URL の推定が 5 回外れた。** `[NB]` と同じ轍を踏んでいる。

| 試した URL                          | 結果                                 | 正しい URL / 実際                             |
| ----------------------------------- | ------------------------------------ | --------------------------------------------- |
| `bakuraku.jp/download`              | **404**                              | `bakuraku.jp/resources/`                      |
| `hrbrain.jp/download`               | **404**                              | `hrbrain.jp/whitepaper`                       |
| `andpad.jp/posts/documents`         | **404**                              | `andpad.jp/downloads`                         |
| `hrbrain.jp/seminar`                | **404**                              | `hrbrain.jp/event`                            |
| `jp.sansan.com/seminar/`            | **404**                              | `jp.sansan.com/event-seminar/`（中身は取得不可） |
| `jp.sansan.com/multi_resources/`    | **404**                              | 検索結果に残っていた旧 URL                     |

**b) `go.chatwork.com/ja/download/` は資料一覧ではなかった。**
`[NB]` で「ブログのみ取得成功」だった Chatwork は、`/download/` が
**アプリ（PCブラウザ版・デスクトップ版・モバイル版）のダウンロードページ**だった。
「ダウンロード」という語が資料DLを意味しない実例である。
自社ドメイン上の資料ライブラリは特定できず、見つかったのは
`assistant.chatwork.com/document/`（**Chatwork アシスタントという別サービスの面**）のみ。
**Chatwork は資料・セミナーとも分母から外す。**

**c) `andpad.jp/seminars` は `asb.andpad.jp` へ 301 されていた。**
ANDPAD のセミナーは「**ANDPAD セミナー放送局**」という**別ドメインのメディア**に切り出されている。
個別セミナーの URL も `asb.andpad.jp/campaign/{id}/apply` と、
本体（`andpad.jp`）とはまったく別の体系になっている。
`[NB]` で ANDPAD の News が 2 系統あったのと同じ性質。

**d) Sansan は資料・セミナーとも中身に到達できなかった。**
`jp.sansan.com/resources/` と `jp.sansan.com/event-seminar/` は
**どちらも `<title>` しか返らず、本文が 1 件も描画されていない**。
`[NB]` §1-3e で News 一覧が「該当の記事がありません」を返したのと同じ症状で、
JS でのフェッチ後に描画する実装だと考えられる。
**Sansan は 3 調査連続で本文に到達できていない。**

**e) HRBrain のセミナー一覧は 2 回とも途中で切れた。**
`hrbrain.jp/event` は `h1「セミナー」` までは取れたが、以降が
`[Content truncated due to length...]` で欠落。`[NB]` §1-3f の News 一覧とまったく同じ症状で、
**このサイトは一覧ページが `WebFetch` の長さ上限に引っかかる**と考えられる。
**HRBrain のセミナー一覧は「骨格のみ」で記録し、詳細ページは検索経由で 3 本取得した。**

**f) フォームの入力項目名をほとんど取得できなかった。**
資料個票 6 本・セミナー詳細 21 本のいずれでも、フォームは
Marketo / HubSpot 等の外部埋め込みで、`WebFetch` の Markdown 変換後には
「フォームが表示されない場合は…」という注記だけが残り、**入力項目名が落ちる**。
唯一取れたのはバクラクの 1 本（会社名・姓・名・メール・電話・部署の 6 項目）。
**「フォームの項目構成」は本調査の結論に使っていない。**

**g) `kintone.cybozu.co.jp/material/` は 2 ページに分かれており、片方しか取れなかった。**
`h1「フェーズ / 属性でさがす」` は取得できたが、
併設されている「絞り込んでさがす」の中身に到達できず、カードの構成が確認できていない。
**kintone の資料一覧は「部分取得」として扱い、集計 n=7 の分母から外した。**

**h) バクラクの資料ライブラリには「資料でないもの」が混ざっている。**
一覧から拾った `bakuraku.jp/resources/how-to/clm-trial/` は、開けてみると
**「『バクラク契約管理』無料トライアルお申し込み」ページ**だった。
パンくずは「ホーム > お役立ち資料ダウンロード > 本ページ」で、
**資料ライブラリの配下にトライアル申込が同居している。**
個票の集計 n=6 の分母からは外したが、**設計上は重要な観測**である（§4-2）。

**i) 「開催終了後の姿」は静的取得で見える範囲に限定される。**
CEO のブリーフにある「同一 URL が終了後にどう変わるか」は、
**同じ URL を時間差で 2 回取得したわけではない。**
すでに終了しているページと、まだ開催前のページを**別々に取得して並べた**ものである。
「このページは終了前にはこう見えていたはず」という推定は一切していないが、
**同一ページの前後比較ではない**ことは明記しておく。

**j) 満席（`SOLD OUT`）の実例を 1 件も採取できなかった。**
一覧・詳細を通じて「満席」「定員に達しました」の表示は **0 件**。
存在しないのか、たまたま調査時点で満席の回が無かったのかは**切り分けられていない**。
**「0 件だった」ことは記録するが、「存在しない」とは結論しない**（§7-3）。

**k) 資料の中身（PDF 本体）は 1 つも開いていない。** 測ったのはランディング面の構造だけ。

**l) 1 サイト 1〜6 ページは、そのサイトの全ページを代表しない。** `[NB]` と同じ制約。

**m) PC / SP の区別が無い。** レスポンシブの検証は一切していない。

**n) 「その構成が良いか」は測っていない。** 測ったのは
「何が、どの順で、どれだけ使われているか」だけである。

## 2. サイトごとの記録

### 2-1. SmartHR — 資料は「詳細ページ + 埋め込みフォーム」、セミナーは**配信形態をフィルタ軸にする**

**資料一覧**（`smarthr.jp/resources/`）: `h1「お役立ち資料」`。
フィルタは**タブ 2 つのみ**（サービス紹介資料 / ノウハウ・トレンド資料）。
サムネイル必須。バッジは「人気」「NEW」の 2 種。
**日付・資料形式（PDF / ページ数）の表記は無い。** 「PICK UP」枠に 3 点セット資料。
ページネーション無し・検索ボックス無し。カードは `/know-how/ebook/ebook_305-30/` のような
**資料詳細ページ**へ遷移する（フォーム直行ではない）。

**資料個票**（`/know-how/ebook/ebook_305-30/`）:
`h1「SmartHRのご紹介」`（= 資料名）→ 説明文 → **「こんなことが分かります」箇条書き 4 項目** →
サンプル表示 → **埋め込みフォーム**。**パンくず無し・関連資料無し。グローバルナビは有る。**

**セミナー一覧**（`smarthr.jp/know-how/event/`）: `h1「イベント・セミナー」`。
本調査で**最も軸が多い 3 軸**を持つ。

| 軸           | 選択肢                                                             |
| ------------ | ------------------------------------------------------------------ |
| **配信形態** | LIVE / いますぐ視聴可能 / **受付終了**                             |
| 開催場所     | オンライン配信 / 東京 / 関西 / 東海 / 九州 / 中四国 / 北海道       |
| テーマ       | 労務 / タレントマネジメント / 採用 / AI / セキュリティ ほか 17 以上 |

**開催予定と終了を「フィルタ軸の 1 つ」として持つのは本調査で SmartHR だけ**である。
カードは サムネ + ステータスバッジ「受付中」+ 配信形態 + テーマタグ + タイトル +
開催地アイコン + `開催： 2026/08/20 (木)` + 「詳しく見る」。番号ページャ（15 ページ）。

**セミナー詳細 5 本**は、**URL 体系が 2 つに分かれている**のが最大の特徴である。

| URL                          | 状態             | 中身                                                      |
| ---------------------------- | ---------------- | --------------------------------------------------------- |
| `/know-how/event/live/376926/` | LIVE           | 第3回 人事と労務のオンライン展示会。8/20(木)13:00-15:50。登壇者 1 名（顔写真 + 経歴）。プログラム 4 部。**協賛 8 社**。無料 |
| `/know-how/event/live/517078/` | LIVE           | **会場開催**（SmartHR 東京本社）。8/26(水)15:00〜17:30。**定員 30 名・1 社 2 名まで**。登壇者 **3 名**（顔写真 + 所属 + 肩書き + 経歴）。プログラム 5 部 |
| `/know-how/event/live/418062/` | LIVE           | オンライン（Zoom）。8/25(火)12:00-12:40。**申込締切 8/25(火)12:00 まで**。登壇者 1 名。時間割型プログラム |
| `/know-how/event/movie/104628/` | いますぐ視聴可能 | **「本コンテンツは 2026 年 4 月 21 日に開催されたセミナーの再配信です」**。視聴期限 8/31。**「資料等の配布はございません」と明記**。トピックス（約 45 分） |
| `/know-how/event/movie/791307/` | いますぐ視聴可能 | 「2025 年 11 月 17 日に開催したセミナーの一部再放送」。視聴期限 11/30。トピックス（約 35 分） |

**`/live/` と `/movie/` でパスが分かれている。**
つまり **SmartHR は「終了後に同じ URL が変わる」のではなく、別 URL のアーカイブ面に作り直している。**
セクション順序は 5 本とも一致する（概要 → 開催要項 → こんな方におすすめ → 登壇者 → プログラム → 注意事項 → フォーム）。
フォームは **5/5 が埋め込み**。

### 2-2. カミナシ — セミナーで**同一 URL のまま「受付終了」に変わる唯一の型**

**資料一覧**（`kaminashi.jp/download`）: `h1「お役立ち資料」`。
フィルタは**業界 1 軸のみ**（食品製造 / 機械製造業 / ホテル・宿泊業 / 飲食業 / その他）。
サムネ + タイトル + ダウンロードボタン。**日付・形式表記・カテゴリ表示は無い。**
カードは `/download/{slug}` の**資料詳細ページ**へ遷移する。

**資料個票**（`/download/measures-against-human-error`）:
`h1`（= 資料名）→ 説明文 → **表紙画像** → 詳細説明 → **「こんな人にオススメ」3 項目** →
**埋め込みフォーム**。パンくず無し・関連資料無し。ヘッダーは有る。

**セミナー一覧**（`kaminashi.jp/seminar`）: `h1「セミナー」`。
**開催予定と終了を別セクションに分けず、同一リストの中で「開催終了」バッジで区別する**
（本調査で唯一）。フィルタ 3 軸（業務課題 4 / 業界 6 / テーマ 2）。
「もっとセミナーをみる」。**カードに日時・開催形式・登壇者を出さない**（本調査で最も情報が少ないカード）。

**セミナー詳細 6 本**は、**開催前 4 本と終了後 2 本が、まったく同じ構成**である。

```
h1（セミナー名 + サブタイトル）
 → ステータス（受付中 / 受付終了）
 → こんな方におすすめ
 → セミナー概要
 → プログラム
 → 開催要項（日時・参加方法・参加費）
 → 講師情報
 → 申し込みフォーム（別ページへのボタン）
```

- **6/6 が「複数日程」**（例: `2026年8月25日（火）13:00-14:00／8月27日（木）13:00-14:00／8月28日（金）13:00-14:00`）。
  本調査で複数日程を全件で使うのはカミナシだけ

## 5. 設計提案

### 5-1. 方針

既存 2 調査の方針をそのまま継承する。

- **ページごとの構成の選択肢は作らない。** 順序はパターンが決める。呼び出し側が渡すのは内容だけ
- **実測に無いものは作らない。** 冒頭の数値タイル（**0/81**）・資料の関連コンテンツ（0/6）・
  セミナーの関連セミナー（1/21）・無限スクロール（0/31）は**作らない**
- **一覧と詳細で語彙を共有する。** カテゴリ・開催状態は両方で同じ型を使う
- **実測に存在しない組み合わせを型で許さない。** `[NB]` の `kind` と同じく、
  セミナーは `status` による判別ユニオンにする

### 5-2. 何を新設するか — **3 つ**（資料は一覧のみ）

| 案                                                          | 型の数 | 評価                                                                                                    |
| ----------------------------------------------------------- | -----: | --------------------------------------------------------------------------------------------------------- |
| `article-list` / `case-study-list` を拡張して資料も扱う     |     +0 | **不可**。カードの語彙が違う（日付 0/7 ⇄ 記事 14/14、表紙必須 7/7）。必須フィールドを緩める破壊的変更になる |
| **`resources-library`（一覧のみ）**                         | **+1** | **推奨。** 個票は既存 `LeadGenInput` で足りる（§3-2）                                                    |
| `resources-library` + `resource-detail`                     |     +2 | **不要**。`LeadGenInput` との差分が「ヘッダーの有無」1 点しかない（§5-3）                                |
| `seminar-list` を予定用とアーカイブ用で 2 つ                |     +2 | **不可**。実測は 8/8 が**同じ一覧**で両方を扱う。別ページに分ける型は 0/8                                |
| **`seminar-list` + `seminar-detail`（`status` 判別ユニオン）** | **+2** | **推奨。** 揺れの 7 箇所すべてが開催状態の境目にあり（§3-6）、型で分けるのが実測に合う                  |
| `seminar-detail` 1 つ（全部 optional）                      |     +1 | **不可**。「開催日時の無い開催予定セミナー」「視聴期限のある LIVE」が型で許される                       |

**新設は 3 つ: `resources-library` / `seminar-list` / `seminar-detail`。**
**資料の個票は新設しない。**

### 5-3. 資料の個票 — `LeadGenInput` を 1 点だけ緩める

§3-2 の照合結果を、そのまま既存型に当てる。

| `LeadGenInput` のフィールド                | 資料個票の実測      | 判定                                            |
| ------------------------------------------ | ------------------- | ----------------------------------------------- |

| `hero.image`                               | 表紙画像 **6/6**    | ✅ そのまま（実測は必須級だが型は optional のまま） |
| `hero.subtitle`                            | 説明文 6/6          | ✅ そのまま                                     |
| `hero.offers?: [OfferAction]`              | ページ内アンカー    | ✅ そのまま                                     |
| `contents: Slot<FeatureGridProps>`         | 「この資料でわかること」箇条書き **6/6** | ✅ そのまま（§5-6 に注記）  |
| `stats?: Slot<StatsSectionProps>`          | **0/6**             | ⚠️ 出番が無い。optional なので**害は無い。残す** |
| `form: React.ReactElement`                 | **6/6**             | ✅ そのまま                                     |
| **`Omit<LandingPageCommon, 'header'>`**    | **ヘッダー 6/6 で有り** | ❌ **実測と真逆。ここだけ緩める**              |
| （`closing` を持たない）                   | 末尾 CTA **0/6**    | ✅ 設計が実測に合致していた                     |
| （`related` を持たない）                   | 関連資料 **0/6**    | ✅ 設計が実測に合致していた                     |

**`header` の扱いだけが実測とずれている。**

`LeadGenInput` の「グローバルナビを剥がす」は `[LP]` 調査の**実測 2/2** に基づく判断だが、
その 2 件は**キャンペーン専用 LP**（広告の着地点）だったはずである。
一方、**資料ライブラリの配下にある個票は 6/6 でヘッダーを持つ**。
これは一覧へ戻れる必要があるサイト内ページだからで、**性質が違う。**

**提案**: `LeadGenInput` に `header?: MarketingHeaderProps` を**任意で戻せるようにする**。
既定は「剥がす」のまま（キャンペーン LP の実測 2/2 を守る）で、
**資料ライブラリの個票では明示的に渡す**。破壊的変更にならない。

```ts
/** 獲得専用 LP。既定ではグローバルナビを剥がす（実測 [LP] 2/2）。締めはフォーム */
export interface LeadGenInput extends Omit<LandingPageCommon, 'header'> {
  pattern: 'lead-gen';
  /**
   * ヘッダー。省略時は剥がす（キャンペーン LP の実測 [LP] 2/2）。
   * **資料ライブラリ配下の個票では明示的に渡すこと**
   * （実測 [RS] 6/6 がグローバルナビを持つ。docs/research/research-resources-seminar.md §3-2）。
   */
  header?: MarketingHeaderProps;
  …
}
```

### 5-7. 未検証: 登壇者の型を事例記事と共有できるか

**実装前に確認すべき点として明記する。**

`CaseSpeakerList`（事例記事の話者。実測 9/27・最大 4 名）と
セミナーの登壇者（実測 16/21・最大 3 名）は、
**氏名 + 所属 + 肩書き + 顔写真 + 経歴という語彙が一致している。**

ただし違いも 2 つある。

1. 事例記事の話者は**顧客企業の人**、セミナーの登壇者は**自社 + 社外パートナー**（社外 7/16）
2. セミナーには **HRBrain のように「組織名だけ」の登壇者**（1/16）が実在する

**`CaseStudyMeta` を `case-study-list` と `case-study-detail` で共有したのと同じ効き方をする可能性が高い。**
実装前に `CaseSpeakerList` の定義を読んで、そのまま使えるか判断すること。

### 5-8. 推奨

**`resources-library` / `seminar-list` / `seminar-detail` を 9・10・11 番目のページ型として
作ることを推奨する**（`article-list` / `article-detail` が 7・8 番目として承認済みの前提）。

根拠は 3 つ。

1. **これは LP の CTA が指す先そのものである。**
   `[LP]` 調査で FV の 2 オファーの「重い方」の実体が資料DLとセミナー申込だった。
   記事系（信頼形成）より**コンバージョンへの距離が近い**。
   GTM の観点では、`article-*` より優先度が高いと判断する余地すらある
2. **既存型の拡張では済まないことが実測で確定した（§4）。**
   獲得系は章 `h2` 0/27・公開日 0/27・関連コンテンツ 1/27 で、
   記事系の中核をひとつも持たない。**逆に記事系はフォームを 0/42 で持たない**
3. **一方で「個票は新設不要」も実測で確定した（§3-2）。**
   `LeadGenInput` は 10 項目中 9 項目が実測と合致しており、
   **ずれているのは `header` 1 点だけ**。ここで新しい型を増やすのは重複になる。
   **`case-study-detail` が「実測に無いものは作らない」で得た規律を、
   ここでは「実測に有るものも、既存で足りるなら作らない」に拡張して適用する**

**ただし実装前に埋めるべき穴が 2 つある。**
① CSS の実測値を 1 つも持っていない（§1-1）。
② **「満席」の実例を 1 件も採れていない**（§1-3j）。
セミナーで満席表示が必要になるのは実運用が始まってからで、
**型に入れるかどうかは実ブラウザ計測が可能になった時点で判断すること**（§7-3）。

## 8. 判断できなかったこと・残課題

1. **CSS の実値を 1 つも持っていない（§1-1）。**
   読み幅・フォントサイズ・行間・色・余白は本調査の対象外。
   資料個票は `lead-gen` の実装値を、セミナー詳細も同じ扱いで流用する前提で進める。

2. **「Bill One 型（フォーム直行）」を検証しきれていない。**
   本調査の 7 サイトは **7/7 が資料詳細ページを経由**しており、フォーム直行は 0/7 だった。
   だが**その前例の提供元である Sansan の本文に到達できていない**（§1-3d）。
   **「Bill One 型は存在しない」とは結論していない。** 実ブラウザ計測が可能になったら確認すること。

3. **「満席」の実例が 0 件（§1-3j）。**
   一覧 8 ページ・詳細 21 本を通じて満席・定員に達しましたの表示を 1 件も採れなかった。
   **存在しないのか、調査時点でたまたま無かったのかは切り分けられていない。**
   `SeminarStatus` に `'sold-out'` を含めなかったのはこの実測に基づくが、
   **実運用で必要になる可能性は高い**。追加は非破壊的にできるので、実測が採れてから足すこと。

4. **同一ページの「開催前 → 終了後」の時系列比較をしていない（§1-3i）。**
   §3-5 の結論は、**終了済みのページと開催前のページを別々に取得して並べたもの**である。
   「カミナシの `/seminar/detail/20260626` は、開催前にはこう見えていた」という推定はしていない。
   同一 URL を時間差で 2 回取得すれば、より強い根拠になる。

5. **Sansan は 3 調査連続で本文に到達できていない。**
   `[NB]` の News、`[RS]` の資料・セミナーのすべてで JS 描画後の DOM に届かなかった。
   候補 10 社のうち Sansan と Chatwork の 2 社が本調査で完全に欠けている。

6. **フォームの入力項目を測っていない（§1-3f）。**
   資料DLとセミナー申込で入力項目が違うのか（例: セミナーだけ「参加する日程」を選ばせるのか）は
   分かっていない。`form: React.ReactElement` で外に出す設計なので当面は影響しないが、
   `ResourceRequestForm` / `SeminarApplicationForm` を作るなら実測が要る。

7. **セミナーの本数・開催頻度を測っていない。**
   SmartHR のページャが 15 ページ、バクラクの資料が 23 ページという数字は取れたが、
   1 ページあたりの件数を確認していないため総数は出せない。
   `case-study-detail` §5-7・`[NB]` §7-6 と同じ残課題。

8. **`tone` の判断に実測の裏付けが無い（§7-1）。**
   `resources-library` / `seminar-*` を `campaign` にするのは判断であって実測ではない。

9. **登壇者の型を `CaseSpeakerList` と共有できるか未検証（§5-7）。**
   語彙は一致しているが、実装前に定義を突き合わせること。
   **`CaseStudyMeta` を `case-study-list` と `case-study-detail` で共有したのと
   同じ効き方をする可能性が高い。**

10. **`OfferTaxonomy` / `OfferPagination` を `[NB]` の `ArticleTaxonomy` /
    `ArticlePagination` と統合すべきか未決。**
    構造は完全に同じだが、意味する軸が違う（記事は年別 6/7、資料・セミナーは年別 0/15）。
    **ContentHub（LP 末尾の回遊セクション）の実測と合わせて、
    3 系統のカードとタクソノミーをまとめて設計し直すのが正しい**可能性がある。
    `[NB]` §7-8 と同じ残課題。

11. **HRBrain の「見逃し配信の集約ページ」を型で扱っていない。**
    実測 2/9 で、**複数の過去セミナーを 1 ページにまとめて再公開する**形式がある。
    これは `seminar-detail` でも `seminar-list` でもない中間物で、
    本ドラフトでは `seminar-list`（status が全件 archive）で表現できると判断したが、
    実測はそれを支持していない（登壇者もアジェンダも持たない別物だった）。

12. **英語ページでの構成は未調査。** `case-study-detail` §5-9・`[NB]` §7-9 と同じ。

13. **SP / PC の区別が無い（§1-3m）。**
    とくに**セミナー詳細の「開催要項」の定義リストと登壇者ブロックが SP でどう畳まれるか**は
    実装判断に直接効く。実測が無い。

14. **`ResourceCard` / `SeminarCard` / `ArticleCard` / `CaseCard` の 4 種を
    本当に別部品にすべきか。** §4-2 のとおり語彙は全部違うが、
    「表紙 + ラベル + タイトル + 任意のメタ」という骨格は共通している。
    **1 つの `ContentCard` に slot を切る設計もありうる**が、
    `[NB]` §4-5 が `ArticleCard` を新設と判断した流れを本調査でも踏襲した。
    実装時に 4 つ並べて再検討する価値がある。
